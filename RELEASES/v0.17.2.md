# v0.17.2 — the tunnel was eating the credential

**Released:** 2026-08-01 · **Previous:** [v0.17.1](v0.17.1.md)

v0.17.1 shipped a working mobile API and a working app. Every call from a phone
still came back **HTTP 200 carrying the Desk's `/me` page**, and the app reported
it as a decoding failure, which is the least useful true thing it could have
said.

The credential was never wrong. It was never presented.

This release is one fix and its paperwork. **No new capability. No schema
change. No migration required.**

---

## What was actually happening

The Tailscale `serve`/`funnel` proxy **removes the `Authorization` header**. So
Frappe authenticated nobody, the session was Guest, and `is_whitelisted` refused
the call *before the whitelisted method ran* — at which point Frappe did what it
does for an unauthenticated browser and rendered the login page. 200, `text/html`,
`sid=Guest`.

### Proven three ways, 2026-08-01

| # | Where from | Header sent | Result |
|---|---|---|---|
| 1 | inside the container, `http://localhost:5300/…` | `Authorization: token key:secret` | **correct JSON**, full user context |
| 2 | outside, `https://umbrel.tail2b0bb0.ts.net/…` (public funnel) | the same | HTML `/me`, sets `sid=Guest` |
| 3 | a Mac **on the tailnet**, same URL (funnel edge bypassed) | the same | HTML `/me`, sets `sid=Guest` |

**Probe 3 is the one that settles it.** That request never leaves the tailnet, so
the public funnel edge is not the culprit — it is the `serve` proxy step itself.
Nothing on the Frappe side, and nothing this repo could configure, was going to
change that.

### Why "just use the tailnet" was not an option

Farm Ops has to work on cellular, on the LAN and on the tailnet — same binary,
same enrolment, whichever way a phone happens to be reaching the site that
morning. A fix that only works on one of the three is a different product. **The
fix had to survive whatever the proxy does to headers.**

---

## The fix: one credential, three carriers

The app sends the identical `<api_key>:<api_secret>` pair three ways. The server
takes the first that resolves and stops.

| | Carrier | Read by | When it wins |
|---|---|---|---|
| **a** | `Authorization: token <key>:<secret>` | Frappe's own auth layer | whenever it survives the proxy — **nothing in this app runs** |
| **b** | `X-FarmOps-Token: <key>:<secret>` | `erpnext_mcp/api/fallback_auth.py` | `Authorization` was stripped |
| **c** | `"_auth": {"api_key": …, "api_secret": …}` in the POST body | the same | neither header survived |

`Authorization` is special to every intermediary on earth. `X-FarmOps-Token` is
special to nobody. And a layer that rewrites a request **body** is not a proxy,
it is an attack.

### It is a second door, not a bypass

This is the part worth your scrutiny, so it is stated plainly.

`fallback_auth` answers exactly one question — *which Frappe user is this?* — and
answers it **with Frappe's own scheme**: look the `api_key` up on User, read the
stored `api_secret` back through the framework's own accessor, compare with
`hmac.compare_digest`, refuse a disabled account. It grants nothing.

**All seven gates from v0.17.1 then run, unchanged, on the user it establishes:**

| # | Gate | Still applies on the fallback path |
|---|---|---|
| 1 | `farm_ops_mobile_enabled` kill switch | ✅ tested |
| 2 | Not Guest | ✅ this *is* the check being satisfied |
| 3 | Role gate (`Field Worker` / `Farm Worker` / `Foreman` / `Farm Manager`) | ✅ tested |
| 4 | **Active Mobile Access Grant** | ✅ tested |
| 5 | Rate limit per user per method | ✅ tested |
| 6 | Entity scoping on every argument and every returned row | ✅ tested |
| 7 | MCP Action Log row + secret strip | ✅ tested |

A wrong secret is **Guest, not an error** — same as Frappe — so the caller learns
nothing about whether the key existed. **An admin holding every role on the site
still cannot get in through the new door**, because gate 4 has not moved: v0.17.1's
headline check is re-run against v0.17.2's entry point and still refuses.

### Why it could not be done inside the endpoint

The obvious implementation — check the header at the top of `guard.endpoint` —
**would never have run.** `is_whitelisted` refuses a Guest *before* dispatching a
whitelisted method; `@frappe.whitelist()` without `allow_guest=True` throws in the
framework, not in the method. A fallback written in `guard.py` alone would have
sat behind a door that never opens. **The `/me` page you were getting IS that
refusal.**

So resolution runs as an **`auth_hooks` entry** — Frappe's own extension point for
custom authentication, executed by `validate_auth()` after the session is
established and before the handler decides whether the caller may reach the
method. Identity is settled in exactly the window Frappe settles it in.

`guard.endpoint` calls the same resolver a second time as a belt. It is
idempotent (it returns immediately when the session is already somebody), and it
is what makes the standalone suite exercise the real resolver rather than a mock.

### The one request-lifecycle hook this app has ever installed

`auth_hooks` runs on **every** request to the site, which is as intrusive as
`hooks.py` gets. It is bounded to the point of dullness:

- it reads one attribute and returns for anything that is not
  `/api/method/erpnext_mcp.api.*` — every Desk page, every other app's endpoint,
  `mcp.handle` itself,
- it **never** overrides an identity Frappe already established,
- it grants no permission of any kind,
- **it cannot raise.** An exception in an auth hook is an exception on every page
  of the site, not a failure of one endpoint.

## Two judgement calls that differ from the brief

### 1. The audit tag goes on the row that already exists, not into Audit Event

The brief asked for an **Audit Event** per fallback authentication. This ships the
tag on the **MCP Action Log** row `guard` already writes for every mobile call:

```
success — ana@fafo.farm (fallback_auth: header)
success — ana@fafo.farm (fallback_auth: body)
success — ana@fafo.farm                          ← Authorization survived
```

**The reason is arithmetic.** If the proxy strips the header — which is the entire
premise of this release — then *every* mobile call takes the fallback path. A row
per fallback is a row per call: forty phones polling a task list would put tens of
thousands of authentication records a day into "Audit Event", which on this site is
the **compliance register a GlobalGAP auditor reads**. That is the same argument
`api/guard.py` already makes about not putting mobile traffic there at all, and it
does not get weaker because the rows would be about authentication.

The fact you asked for is preserved exactly, on a row that was being written
anyway, in the log you already open to answer *"what did this credential do"*.
**Filter MCP Action Log on `tool_name` starting `mobile:` and read the summaries.**
If the tags stop appearing, your tunnel stopped eating headers.

### 2. Failed verifications are metered per key, not per address

Ten wrong answers for one `api_key` inside a minute close the fallback path **for
that key** for the rest of the minute. Successes never touch the counter, so a
phone with a good credential cannot be locked out by anybody else's traffic.

The counter is deliberately **not** keyed on the caller's IP. Every phone on the
farm arrives from the funnel's single address; an address-keyed limit would let
one phone with a stale credential take the other thirty-nine off the air. The key
is stored as a SHA-256 fingerprint, so no credential lands in a cache key.

## What you need to do — in this order

### 1. Push, then build — in that order, the Dockerfile depends on it

`fafo-umbrel-store/fafo-erpnext/build/Dockerfile` pulls erpnext_mcp from GitHub
`main` and cache-busts on the **pushed** commit. A local-only commit leaves the
layer cached and you will build the old code and not be told.

```sh
cd "~/Desktop/Development Comms Folder/erpnext_mcp"
git push origin main
```

```sh
cd "~/Desktop/Development Comms Folder/fafo-umbrel-store/fafo-erpnext/build"

docker build \
  --build-arg ERPNEXT_MCP_VERSION=0.17.2 \
  --no-cache \
  -t polehntim/erpnext-umbrel:15 \
  .

docker push polehntim/erpnext-umbrel:15
```

> **Check the platform flag against what your Umbrel actually runs** — add
> `--platform linux/amd64` or `linux/arm64`. No recorded build command in the
> store repo pins one, so this note does not guess.

### 2. Restart the app on the Umbrel

```sh
ssh umbrel@umbrel.local

sudo umbreld client apps.stop.mutate --appId fafo-erpnext
sudo umbreld client apps.start.mutate --appId fafo-erpnext
```

`sudo umbreld client apps.restart.mutate --appId fafo-erpnext` is the one-liner
the store README uses and does the same job; the stop/start pair is here because
it is what you asked for and because it makes "did it actually come down" a thing
you can see.

Give it a minute to come up before the next step.

### 3. Migrate, then restart the workers

**`bench migrate` is not strictly required — there is no schema change in this
release** — but it is what makes Frappe re-read `hooks.py`, and `auth_hooks` is a
new key in it. Run it. The `supervisorctl restart all` afterwards is the part that
is genuinely required: the hook cache lives in the running gunicorn workers.

```sh
docker exec -u frappe fafo-erpnext_server_1 \
  bench --site frontend migrate

docker exec fafo-erpnext_server_1 \
  supervisorctl restart all
```

### 4. Verify from a CLI, before you touch a phone

Take a live pair from `create_mobile_user` (or re-issue one with
`generate_api_token`). Then, **from a machine that is NOT on the tailnet** —
cellular tether, a friend's wifi, anywhere outside:

```sh
KEY=<api_key>
SECRET=<api_secret>
HOST=https://umbrel.tail2b0bb0.ts.net
```

**a. The old way — this is expected to still fail, and that is the diagnosis:**

```sh
curl -s -o /dev/null -w '%{http_code} %{content_type}\n' \
  -X POST "$HOST/api/method/erpnext_mcp.api.mobile.get_current_user_context" \
  -H "Authorization: token $KEY:$SECRET" \
  -H "Accept: application/json"
```

`200 text/html` means the proxy is still stripping `Authorization`. That is the
bug this release routes around, not one it fixes at the proxy.

**b. The new way — this is what must work:**

```sh
curl -s \
  -X POST "$HOST/api/method/erpnext_mcp.api.mobile.get_current_user_context" \
  -H "X-FarmOps-Token: $KEY:$SECRET" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json" \
  -d '{}'
```

Expect JSON, not HTML — a `message` object in the shape `UserContext` decodes:

```json
{"message": {
  "user": "ana@fafo.farm",
  "full_name": "Ana Ramos",
  "employee": "EMP-0007",
  "roles": ["Field Worker"],
  "mobile_roles": ["Field Worker"],
  "companies": [{"name": "…", "abbr": "…"}],
  "default_company": "…",
  "skills": [],
  "enabled": true,
  "grant_state": "Active"
}}
```

The quickest one-eyed check that it worked at all:

```sh
… | head -c 200
```

`{"message":` is the fix landing. `<!DOCTYPE html>` is the bug.

**c. The body fallback — belt to (b)'s braces:**

```sh
curl -s \
  -X POST "$HOST/api/method/erpnext_mcp.api.mobile.get_current_user_context" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json" \
  -d "{\"_auth\": {\"api_key\": \"$KEY\", \"api_secret\": \"$SECRET\"}}"
```

Same JSON. No headers involved at all.

**d. A wrong secret must be refused, and must not say why:**

```sh
curl -s \
  -X POST "$HOST/api/method/erpnext_mcp.api.mobile.get_current_user_context" \
  -H "X-FarmOps-Token: $KEY:not-the-secret" \
  -H "Content-Type: application/json" -d '{}'
```

Expect a permission refusal reading *"This endpoint requires an enrolled Farm Ops
credential."* — the same words a caller gets for a missing role and for a revoked
grant, on purpose.

**e. Read the log and confirm which door they came in through.**

Desk → **MCP Action Log**, filter `tool_name` starts with `mobile:`. The rows from
(b) and (c) carry `(fallback_auth: header)` and `(fallback_auth: body)`. If you
ever see a row with no tag, that request's `Authorization` header survived — which
would mean the proxy behaviour changed.

### 5. Apply the iOS change — see below — then verify from a phone off the LAN

Sign in, pull to refresh, open a task, complete one. Nothing about the app's
behaviour changes; it just stops getting HTML.

## The iOS change Tim applies separately

**One file. One line added. Nothing removed.**

`FarmOpsKit/Sources/FarmOpsKit/Networking/FrappeClient.swift`, in the request
builder (around line 122 — the block that sets `Authorization`):

**Before**

```swift
        var request = URLRequest(url: url)
        request.httpMethod = "POST"
        request.timeoutInterval = FarmOpsConfig.requestTimeout
        request.setValue(credentials.authorizationHeader, forHTTPHeaderField: "Authorization")
        request.setValue("application/json", forHTTPHeaderField: "Content-Type")
        request.setValue("application/json", forHTTPHeaderField: "Accept")
```

**After**

```swift
        var request = URLRequest(url: url)
        request.httpMethod = "POST"
        request.timeoutInterval = FarmOpsConfig.requestTimeout
        request.setValue(credentials.authorizationHeader, forHTTPHeaderField: "Authorization")
        // The Tailscale serve/funnel proxy strips `Authorization`, so the same
        // credential goes out again under a header name no intermediary has an
        // opinion about. Server side: erpnext_mcp/api/fallback_auth.py (v0.17.2).
        request.setValue("\(credentials.apiKey):\(credentials.apiSecret)",
                         forHTTPHeaderField: "X-FarmOps-Token")
        request.setValue("application/json", forHTTPHeaderField: "Content-Type")
        request.setValue("application/json", forHTTPHeaderField: "Accept")
```

`apiKey` and `apiSecret` are already `public let` on `ServerCredentials`
(`FarmOpsKit/Sources/FarmOpsKit/Auth/ServerCredentials.swift`), so nothing else
needs to change.

**Optional, and only if you want the third carrier too.** The server accepts
`_auth` in the POST body, and a body always survives. If you want that belt as
well, in the same `callRaw(_:params:)` — its signature is
`params: [String: Any]`, so this type-checks as written — replace:

```swift
        if !params.isEmpty {
```

with

```swift
        var params = params
        params["_auth"] = ["api_key": credentials.apiKey, "api_secret": credentials.apiSecret]
        if !params.isEmpty {
```

The server drops `_auth` before it binds any argument and keeps it out of the
audit row, so it cannot collide with a method's parameters. **The header change
alone is enough** — this is only worth doing if you would rather not have to
touch the app again the next time a proxy changes its mind.

### If you would rather add it in one place instead

A tidier variant, if you prefer the header to live beside its sibling: add to
`ServerCredentials.swift`, next to `authorizationHeader`:

```swift
    /// The same pair, under a name no proxy has an opinion about. v0.17.2 —
    /// Tailscale serve/funnel removes `Authorization`.
    public var farmOpsTokenHeader: String {
        "\(apiKey):\(apiSecret)"
    }
```

and then in `FrappeClient.swift`:

```swift
        request.setValue(credentials.farmOpsTokenHeader, forHTTPHeaderField: "X-FarmOps-Token")
```

Either is fine. The wire format is identical.

## What this release deliberately does not do

- **It does not touch the funnel config.** You manage that, and nothing here
  needs it changed — the paths were already reachable, which is exactly why the
  symptom was a 200 rather than a 404.
- **It does not make the mobile methods `allow_guest`.** That was the other way
  to get past `is_whitelisted`, and it would have published eleven methods to
  anonymous callers and relied entirely on `guard.py` catching them. The
  `auth_hooks` route settles identity *before* the framework's own check instead,
  so the whitelist posture is exactly what it was in v0.17.1.
- **It does not add a schema field, a doctype, or a scheduled job.** Four
  scheduled jobs before, four after.
- **It does not change the QR payload.** `LoginQRParser` already receives
  `api_key` and `api_secret` separately; the app builds both headers from what it
  already has. Changing that payload is how v0.17.0 broke enrolment.
