# v0.20.0 planning spec — iOS UX grouping + shared evidence tray

**Status**: SPEC, NOT BUILT. Approved architectural direction 2026-08-02 (see `project_inspection_ux_plan.md` in memory).

**Purpose**: Worker walks into a cabin ONCE and does all the tasks there without fighting the UI. Emergent grouping — the app groups related work by location, shared evidence carries across tasks in the visit, compliance records still land as separate audits-ready artifacts.

## The design tension this resolves

Worker POV: "I walked into MC-Cabin-01 and did everything in one visit."
Compliance POV: "The Housing Inspection is one record, the Detector Test is another, the Water Test is a third — each with its own regulatory cadence and audit trail."

Both are correct. iOS UX presents ONE visit; backend produces THREE records.

## Backend changes

**Optional but recommended** (does not block v0.20.0 if omitted):
- New field on `Farm Task Assignment`: `visit_id` (Data, nullable) — a UUID iOS mints when a worker starts a visit, applied to every completion submitted from that visit. Purely for traceability + reporting; no logic depends on it.
- New MCP read tool: `list_visits(company=None, worker=None, date_range=None)` — returns visit-shaped rollups grouping completions by `visit_id`.

**Not needed**: no changes to `complete_task_via_mobile`, `stage_file_chunk`, evidence handling, or compliance rule engine. The backend already supports one File attached to multiple parent records (v0.18.4+).

## iOS changes (the substantial work)

### 1. Location-grouped task views

Available and My Tasks tabs get a segmented control at the top: **Visits** (default) / **Tasks** (existing list view).

**Visits mode:**
- Groups tasks by `location` field
- Each visit card shows: location name, company badge, task count, sum of estimated_duration_minutes, urgency-max badge (Critical > High > Normal)
- Tap → visit detail (list of tasks scoped to that location)
- Sort options: nearest first (if worker's GPS known), oldest task first, urgency-first

**Tasks mode** stays exactly as current — flat list — for workers who prefer it.

### 2. Visit session (iOS-side state)

New model `VisitSession`:
```swift
struct VisitSession: Codable {
    let id: UUID
    let location: String
    let company: String
    let startedAt: Date
    var completedAt: Date?
    var completedTaskIDs: [String]  // Farm Task Assignment docnames
    var sharedEvidence: [LocalEvidenceFile]  // photos + signature usable across tasks
    var sharedSignatureFile: LocalEvidenceFile?  // signed once, applied to all
}
```

- Persisted in local storage (SwiftData / CoreData); survives app kill
- Started when worker taps into a task from Visits mode OR taps "Start visit" from any task detail
- Ended when: all tasks at location completed, worker taps "End visit", OR 12 hours of inactivity

### 3. Per-visit shared evidence tray

**Photo tray**:
- Photos captured in ANY task within the visit go to `sharedEvidence`
- Task detail's "Add photo" button gets a second option: "Choose from visit tray"
- Each photo in the tray shows which tasks it's already attached to (badge count)
- Photos NOT attached to any task at visit-end are optionally deleted (worker prompt)

**Signature**:
- Worker signs once at any point in the visit
- Subsequent task completions offer "reuse visit signature" checkbox (default checked)
- Backend receives the same signature File token on multiple completions — v0.18.4 permission cascade handles the multi-parent link automatically

### 4. Visit UI chrome

- Home tab shows an active visit banner at top when in a visit: "In visit: MC-Cabin-01 · 2 of 3 tasks done · 32 min elapsed"
- Task detail (when inside visit) gets Prev/Next task buttons at the bottom for fast walk-through
- "End visit" action always visible in visit context

### 5. Offline resilience

- Visit state persists offline
- Photos and signatures stored locally until upload
- Completing a task inside a visit still queues the standard PendingMutation the SyncEngine already knows how to drain
- No new offline sync logic

## What this does NOT try to do

- Does NOT change the compliance record model
- Does NOT introduce a "parent task" or subtask relationship
- Does NOT template the tasks that appear in a visit — the visit is emergent from tasks that happen to share a location, not from a template that spawned them
- Does NOT wrap multiple completions into one submission — each task still calls `complete_task_via_mobile` individually so evidence contracts are checked per-task and records are produced independently

Those things are the v0.21.0 "Cabin Inspection templated session" release — different scope.

## Tests

**iOS side** (new):
- UI test: 3 tasks at MC-Cabin-01 render as one visit card in Visits mode
- Integration test: capture photo in task A → open task B in same visit → verify tray offers the photo → attach → complete B → verify server sees same File attached to both Housing Inspection and Detector Test parent records
- State test: kill app mid-visit → relaunch → visit resumed with photos intact

**Backend side** (new, tiny):
- If `visit_id` field added: `list_visits` returns groups keyed correctly; deduplicates evidence Files across parent records in the visit report

## Rollout notes

- No migrate needed if `visit_id` field skipped
- iOS deploys via TestFlight — Tim + one pilot worker walk a real cabin end-to-end before wider rollout
- Backward-compatible with v0.19.0 API contract; older iOS builds continue working in Tasks mode without knowing about Visits

- iOS: ~1 week (Visits view + VisitSession model + tray + chrome + tests)
- Backend `visit_id` + `list_visits`: half day, optional
- Total: ~1 week if backend optional bits skipped; ~1.5 weeks if included
