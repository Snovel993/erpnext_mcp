# v0.37.0 — the model may draft it, and it may not turn it on

**v0.21.0 declared `propose_inspection_template_from_regulation` and left it
refusing. v0.22.0 did the same for `propose_compliance_rule`. Both said, in the
sentence they refused with, exactly what would eventually fill them. This is
that.**

One new MCP tool (332 total: 153 read, 179 mutating) — `approve_inspection_template`,
the counterpart the templates half was missing. Two declared surfaces filled,
which moved no count, because they were always tools. One new pure module,
`erpnext_mcp/proposals.py`. Six new fields across two DocTypes. No new DocTypes.

---

## The thing to be clear about first: nothing here calls a model

It would be easy to read "AI-proposed compliance rules" as *this app now asks a
language model what the rules should be*. It does not, and it never will — that
is the whole architecture of the Configurable Compliance Framework, and this
release is the part of it that was always going to be misread.

**The AI doing the proposing is the MCP client.** Claude reads a regulation.
Claude drafts a record. Claude passes it here as structured arguments. What the
tool does is the part the proposer cannot do for itself:

* refuse the draft where it is the wrong shape;
* stamp the provenance the proposer does not get to choose;
* land it **off**;
* put what needs a second pair of eyes onto the record, where the approver will
  see it and not where the tool result went an hour ago.

So the honest description of `propose_compliance_rule` is: **a validator and a
gate**. Not an author. The sentence "an AI wrote this rule" is true of the draft
and stays true after approval; what approval adds is a person's name.

The runtime is exactly as deterministic as it was the day before this shipped.
Every alert still traces to a rule, a citation, an approver, and the specific
field that crossed a threshold.

## The four rails, and each one is a refusal

They live in one file — `erpnext_mcp/proposals.py`, pure, no database — because a
rule proposal and a template proposal must not drift into being safe in different
amounts.

**IT LANDS OFF.** `enabled` / `active` is forced to 0 whatever was passed. The
Compliance Rule DocType has refused `enabled` without an approver and a date
since v0.22.0, so this is a belt to that brace. It is written down anyway,
because a rail that exists in one place is a rail one refactor away from not
existing.

**IT SAYS WHO WROTE IT.** `authored_by` is forced to `AI-proposed`. A caller
passing `Operator` is **refused rather than quietly corrected** — that argument
is an attempt to launder provenance, and a tool that silently fixed it would
teach the caller nothing.

**IT SAYS WHERE IT WAS READ.** `ai_source_citation` is required, built from a URL
and a section, or from a section alone, or written out by hand. A short excerpt
of the regulation's own words is quoted onto the record beside it. A proposal
with no source is a claim with no source, and the whole point of the human
approval is that somebody can check the draft against the text — which they
cannot do if the draft does not say which text.

**IT CANNOT SIGN ITSELF.** `human_approved_by`, `human_approved_on`,
`approver_employee` and the approver's signature are refused as arguments. There
is exactly one door those fields go through, and it is the approval tool, which
records whoever the request authenticated as rather than whoever is named in the
arguments.

## Propose new, or propose an update. Never a delete and never a disable

A proposal for a `rule_id` that already exists is an **update proposal**. It is
drafted at version+1 and **touches nothing**: the live rule goes on running, on
its own definition, on tonight's sweep, until a person approves the replacement.
The result carries the field-by-field diff, because what a reviewer of an edit
needs is not the draft — it is what changed.

The supersession happens **at approval**, by the person approving. That is where
the old row is disabled and pointed at the new one, in the same order and by the
same mechanism `update_compliance_rule` has used since v0.22.0, and every alert
the old rule raised is left exactly where it was. Switching a rule off is not
evidence that anybody did the work; neither is replacing one.

There is no propose-a-delete and no propose-a-disable anywhere in this app, and
not because it was left out. The two tools that stand something down —
`deactivate_compliance_rule`, `deactivate_inspection_template` — take a written
reason from a person. A model that has decided a rule is obsolete can say so in
prose. It cannot act on it.

## `custom_python` is flagged, and the flag has teeth

The sandbox has refused what it refuses since v0.22.0: no imports, no filesystem,
no network, bounded in steps and in wall clock, checked at authoring time rather
than at two in the morning in a report nobody reads. What the sandbox **cannot**
say is whether a program that runs perfectly asks the right question.

That is a reading job, so:

* a proposal carrying `custom_python` — or a `producer_assigned_to_expression`,
  which is the same sandbox and the same kind of judgement — gets a flag written
  onto the row in a new read-only `ai_review_flags` field;
* `approve_compliance_rule` **refuses** that draft until the approver passes
  `accept_ai_authored_code`;
* the refusal **prints the program back at them**. An acknowledgement of code
  nobody displayed is not one.

The gate is on code a *model* wrote. A rule somebody typed here was already read
by the person typing it, and gating that too would train everybody to pass the
argument every time — which is how a gate stops being one.

The flags travel across an edit. `update_compliance_rule` carries
`ai_review_flags` onto the new version rather than reading them from arguments,
because otherwise superseding a flagged draft would be a way to launder it clean:
a hole shaped exactly like the gate it bypasses.

Two more flags are labels rather than gates — `supersedes_live_rule` /
`supersedes_live_template`, and `sections_without_evidence_contract`, which names
a drafted section that asks the worker for nothing checkable. A section with an
empty contract can be filed empty and still looks complete, which is the failure
an inspection template exists to prevent. And `no_regime_named`, because a rule
tagged with nothing appears in no regime-filtered sweep and no audit packet.

## The templates half needed an approval tool, so it got one

`approve_compliance_rule` has existed since v0.22.0. There was no equivalent for
Inspection Templates, which was fine while every template was typed by the person
who wanted it and stopped being fine the moment a model could draft one — a
template is **live the instant it is written**, so the only thing between a
plausible draft and a worker's screen is that a proposal lands inactive, and the
only thing that makes inactive useful is a way to turn it on with a name against
it.

`approve_inspection_template` activates one, records the approver and the date on
the record, and where a live template already holds the name at a lower version,
deactivates it and points it here. Superseded, never edited — so every session
already worked from it stays readable against the sections the worker actually
saw, and every compliance record they produced stays in the register and in the
audit packet.

It works on any inactive template, not only a proposed one. Reinstating one
somebody withdrew is the same act and deserves the same name against it.

## What is on the records now

**Compliance Rule** gains one field: `ai_review_flags`, read-only, a JSON list
written by the proposal tool and never typed.

**Inspection Template** gains five, and they are the same three words and the
same two approval columns the Compliance Rule has carried since v0.22.0:
`authored_by` (System / Operator / AI-proposed), `ai_source_citation`,
`ai_review_flags`, `human_approved_by`, `human_approved_on`. The seeded templates
this app ships now say `System`, because a seeded row reading `Operator` puts the
words in somebody's mouth.

Both are additive. Every existing row reads exactly as it did, and
`list_compliance_rules` and `get_inspection_template` return everything they
returned before.

Every call goes through `registry.dispatch`, so every proposal and every approval
is already an MCP Action Log row with its arguments — which is what an auditor
asking "who put this in front of us, and who accepted it" reads.

---

## The switches

Both proposal tools and the new approval tool ship **off**, like every mutating
tool in this app. An operator ticks `allow_propose_compliance_rule`,
`allow_propose_inspection_template_from_regulation` and
`allow_approve_inspection_template` by hand, and can untick any of them without
touching the other two — "let the model draft rules" and "let somebody turn a
drafted form on" are two decisions, and an operation that wants the first and not
the second is entitled to have it.

## Tests

`tests_standalone/test_ai_proposals.py`, 67 tests in seven classes, each one an
attempt to break a rail: a draft that asks to be enabled, one that calls itself
operator-authored, one that fills in its own approver, one with no source, one
naming a DocType this site has not got, one carrying a program the sandbox
refuses, one carrying a program it does not, an edit that tries to launder the
flags off a flagged draft, a proposal against a running rule, and the approval
that supersedes it while leaving every alert standing.

`ApprovingIsWhereTheTeethAre` is the class to read if you only read one.

`tests_standalone/harness.py` gained `sections` in `REHYDRATED_CHILD_FIELDS`: the
new approval re-reads a template it did not write and saves it, so the controller
walks the section rows, which needs them to be documents on the second read as
well as on the first. A faithful gap in the double, filled deliberately.
