# v0.74.0 — the account survives the reconnection

One endpoint, one column, and the end of an identifier that goes dead without
saying so.

---

## The gap

v0.73.0 moved reconciliation authority into ERPNext and gave Bank Account seven
Custom Fields to hold what the aggregator knows: which account this is
(`plaid_account_id`), its last four digits, its type, its subtype, and whether
the pipe is pulling it. `push_account_pairing` writes all of them.

Two things were still missing, and only one of them was visible.

**The visible one: the aggregator id goes dead and nothing records that it did.**
When a bank connection is re-linked — an auth change, an expired consent, a
migration the bank ran on a Tuesday — the aggregator issues *new* account ids for
the same real accounts. ERPNext goes on holding the old one. On the farm's own
••6030:

```
ERPNext      ZE4ZoOpA5bUKEkPd5Lb8hDMg4b7e84Ubx7Jeb
Bank Bridge  jN7xBz83JaHPyQ5k1oVJSVeeraMO63tRE55ek
```

Two systems naming the same bank account with two identifiers, neither of which
knows about the other. Overwriting is the right answer to *which id is live* and
the wrong answer to everything else: a year of already-stored feed rows, the
aggregator's own support logs and the pipe's push history all name the dead id,
and once it is overwritten nothing connects any of them to this account. The
overwrite looks exactly like a successful sync from every direction.

**The less visible one: the only endpoint that could write that metadata could
also repoint a pairing.** A nightly refresh saying "this is what the aggregator
calls this account today" had to go through a method whose other half can rewrite
which two accounts are companions — a relationship an operator sets by hand, once.

## What shipped

### `push_account_metadata`

```
POST /api/method/erpnext_mcp.bank.push_account_metadata
```

`bank_account`, `plaid_account_id`, `plaid_account_mask`, `plaid_account_type`,
`plaid_account_subtype`, `sync_enabled`, `plaid_account_id_history` — or a list
of those as `accounts` to push a whole sync in one call.

It is `push_account_pairing` with the pairing taken out, over **one shared
implementation**, so the two can never drift on what "only the keys actually
sent are written" means.

**It refuses `paired_bank_account` and `pairing_type` by name**, and it *declares*
them in order to do so. That is not a contradiction: Frappe hands a whitelisted
method only the kwargs its signature names and drops the rest without a word, so
a pipe that sent a pairing to an endpoint that had never heard of the key would
get the same `200` as one that sent nothing — and would go on believing it had
written a relationship that does not exist. Naming them is what turns that
silence into a sentence saying which endpoint to call instead.

**The ERPNext docname is the identifier, and the Plaid id is not.** This is why
the write keys off `bank_account`: an endpoint that found its target by
aggregator id would stop finding it precisely when the record most needs
correcting. `bank_account` also takes a four-digit mask, and refuses it when two
accounts share one — a metadata write onto the wrong account of two ending in
6030 looks exactly like a right one.

### `plaid_account_id_history` — an eighth Custom Field

Small Text, read-only and hidden, a JSON array of the ids this account used to
have, oldest first. Appended **in the same write** that installs the new id,
because a push interrupted between two writes would leave the new id recorded and
its predecessor gone.

It is the only one of the eight that is hidden, and deliberately: the other seven
are facts an operator may want to set by hand, and this one is machine-maintained
bookkeeping where a hand edit silently changes what the next push thinks it
replaced. It stays readable through `get_account_pairing` and the API, which is
where "was this account once known as X" is actually asked from.

- **Idempotent.** A nightly push of an unchanged id appends nothing. The history
  is a chain of identities, not a log of syncs.
- **The first id ever pushed supersedes nothing.** An empty history is the
  correct state for an account that has never been re-linked.
- **An id that becomes current again leaves the history.** A re-link can land
  back on a connection the account already had; an id that is both current and
  superseded reads as two accounts to anything matching on it.
- **A hand-typed value is not parsed away.** Somebody who typed a dead id into
  the column answered the same question this field asks, so a value that is not
  JSON is read as one legacy entry rather than as nothing.
- **Capped at 100, dropping the oldest** — a ceiling for the case where something
  re-links in a loop, not a number anybody reaches honestly.
- **Not part of the pairing gate.** A site that will not take this one column
  still pairs and still records metadata; it just cannot answer "was this account
  once known as X", which is worth less than the writes it would otherwise block.

Both push endpoints maintain the chain, and both name the change in their reply:

```json
"repointed": [{"bank_account": "Operating - Example Bank",
               "was": "ZE4ZoOpA5bUKEkPd5Lb8hDMg4b7e84Ubx7Jeb",
               "now": "jN7xBz83JaHPyQ5k1oVJSVeeraMO63tRE55ek"}]
```

A re-link is the one thing in a metadata push that changes what an identifier
*means*. A sync log that did not name it would leave an operator diffing two id
columns to find out whether it happened.

`get_account_pairing` returns the history on every account, so the chain is
readable without a round trip to the pipe.

### A chain the pipe kept, pushed explicitly

Both endpoints gain an optional `plaid_account_id_history` — a JSON array (or a
list) of ids this account used to have. Both declare it, because Frappe drops a
kwarg a whitelisted method does not name and answers `200` anyway; an endpoint
that took the chain silently into the bin would be the same bug in a new place.
It is optional **in both directions**, which is the point:

- Send nothing and the chain still forms. A `plaid_account_id` that differs from
  the one on file appends the old one automatically, so the ERPNext side captures
  every re-link it witnesses whether or not the pipe was ever taught to track
  them.
- Send it and the two chains are **merged, not replaced**. Neither source is
  trusted to be complete. The pipe's chain reaches back before this site was told
  about the account and is the only place the early ids can come from; the
  observed half is what this site watched happen and is the only thing that
  survives a pipe that sends nothing. A pipe pushing a short chain must not
  truncate ids this site saw retired, and a site that missed a re-link — it
  happened between syncs, or before the column existed — must not stay ignorant
  of ids the pipe kept.

Ordering is oldest-first with the pushed chain laid down first, since it predates
anything observed here. Re-sending the same chain every night appends nothing,
and a pushed history naming the *live* id drops it rather than recording an id
that is both current and superseded. A push that only backfills history is **not**
reported under `repointed` — a backfill is not a re-link, and a sync log that
called it one would put a reconnection on the day somebody ran the backfill.

## Upgrading

`bench migrate`. The eighth column is created by the same installer hook as the
other seven, and — because the presence check now covers every column the
installer creates — it appears on sites that already have v0.73.0's seven. It is
also created on first use, so a bench that pulled the code without migrating
works the first time something pushes.

Nothing to change on the pipe side. `push_account_pairing` keeps every parameter
it had, gains the id chain, and gains one optional parameter
(`plaid_account_id_history`) that an existing pipe can go on not sending — the
chain forms from what this site observes either way. A pipe that wants the
narrower authority points its metadata refresh at `push_account_metadata` and
sends the same payload minus the pairing keys.

`TheMetadataEndpoint` — 34 tests over the metadata write, the mask resolution,
the refusals, the batch behaviour, the audit rows, the id chain across one,
several and looping reconnections, and the merge of a pushed chain with the

The one that matters most is
