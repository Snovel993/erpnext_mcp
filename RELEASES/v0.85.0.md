# v0.85.0 — the language a worker reads, and the copy their supervisor keeps

Two features, six tools, two doctypes, one new mobile route. They arrived in one
release because they answer versions of the same question: **can somebody other
than the person doing the work understand what happened?**

For the picker holding the phone, that means the screen has to be in a language
they read. For the foreman, the manager and the owner above them, it means a copy
of what happened has to reach them — and has to still say what it said when they
acknowledged it.

---

## 1. Multilingual support

### Why not Frappe's own `Translation` doctype

Frappe ships one, and it is right for the job it does: translating the
**framework's** interface, keyed by the **source string**. You write "Submit" and
it finds the Spanish for "Submit".

That key is wrong for an application's strings, and not for stylistic reasons.
Three failures, all of them silent:

**Rewording the English orphans the Spanish.** A farm that changes "Bucket
rejected — coverage too low" to "Bucket not counted — not full enough" has just
detached the Spanish for it. Nothing errors. Spanish-reading pickers start seeing
English, and the first person to find out is a picker.

**Two English strings that are the same and two Spanish ones that are not.**
"Open" as a shift status is *abierto*; "Open" as a button is *abrir*. One source
key cannot hold both, and whichever was written second wins for both.

**"What is missing?" has no answer.** Keyed by source text there is no register
of *keys* — only a register of translations that happen to exist. You cannot ask
a question whose subject does not exist.

So `Farm Translation` is keyed by a **stable dotted key** the app writes:
`shift.status.open`, `error.task.already_done`, `task_type.harvest`. The English
is a row like any other; rewording it is editing that row and the Spanish stays
attached. `list_translations(language='es', missing_only=true)` answers the third
question in one call, which is the question an operator actually has.

**Nothing here touches `tabTranslation`.** `frappe._()` still does what it always
did for Desk labels. The two registers answer different questions and a site has
both.

### Fall back, and be loud about it

A missing translation **serves the English and says so**. The three alternatives
are each worse:

| | why it is worse |
| --- | --- |
| A blank | a screen a worker cannot act on and cannot report |
| The raw key (`error.task.already_done`) | what a system shows when it has given up; indistinguishable from a bug |
| A refusal | a crew locked out of a flow over one untranslated sentence |

Every read path reports what fell back — `fell_back`, `untranslated`,
`missing_keys` — so the gap is findable from the Desk rather than discoverable by
somebody standing in front of a screen they cannot read.

A **missing key** is a different failure and is refused by name. A key the app
asks for that nobody seeded is a bug or an un-run migrate; a key with English and
no Spanish is a translator's to-do. Conflating them files the first as the second
and nobody looks at it again.

### Whose language, and why `Accept-Language` loses

`Employee.preferred_language` is the authority. `Accept-Language` is consulted
**only where that column is empty**.

That ordering is a compliance position rather than a preference. OSHA
1910.1200(h) and the Worker Protection Standard (40 CFR 170.501) both require
hazard communication and pesticide safety training "in a manner the employee can
understand", and this app's claim to have done that rests on a column somebody
**filled in about a person** — not on a device setting. A phone set to English by
whoever handed it over says nothing about who is holding it now.

The header is honoured on an empty column because a site that has not filled it
in yet is better served by the phone's guess than by English, and because a
worker who set their own phone to Spanish has told us something. Every answer
carries `language_source` — `explicit`, `employee`, `header` or `default` — so
"why is this person seeing English" is answerable without reading the server. A
`header` answer comes with a note saying plainly that a guess is not evidence.

`Employee.preferred_language` now **defaults to `en` on a new record**. It does
not backfill: every existing blank stays blank, and a blank still means "nobody
asked", which is a different fact from somebody saying English.

### Wizard labels can point at the register

A wizard label of the form `tr:wizard.field.photo` is a **reference**, resolved
through the register at read time. Anything without the `tr:` prefix is a literal
and behaves exactly as it did before this release — which is what makes the
change safe on a site whose wizards an operator has already edited.

The per-wizard `label_en` / `label_es` columns stay right for a string that
belongs to one wizard. The prefix is for the string that appears in nine —
"Photograph", "Signature", "Block" — where nine copies drift and the ninth is the
one nobody fixed. A fall-back through a reference is reported on the same
`untranslated` channel a column fall-back is, so one gap looks the same to a
reader wherever it came from.

### Errors carry a key

A mobile refusal now sets `error_key`, `error_message` and `error_language` on
the response, **beside the unchanged English sentence**. The English stays
because it is what an operator finds in a log and what a model corrects itself
from; replacing it would make every existing client's error handling worse to
make one client's better.

The key is the contract and the string is the courtesy: a handset switches on
`error_key` and shows its own wording, and falls back to `error_message` for a
key its release predates.

**The enrolment refusal deliberately has one key for all three of its causes.**
Guest, no field role, and no Active grant have always produced one identical
message on purpose — telling an unauthorised caller which check they failed hands
them a free oracle for the one fact worth probing — and a translation key that
distinguished them would give back exactly what the English withholds.

### Seeded

206 rows across six categories: farm task types, wizard labels, compliance form
labels, shift status messages, the mobile error catalogue, and units. Every
shipped key has **both** languages; a shipped key with no Spanish would appear in
`missing_only` beside an operator's own gaps and nobody could tell which was
which.

The seeder's non-overwrite rule has two halves and both matter. A row flagged
`operator_edited` is **never touched again** — a farm that reworded a phrase its
crew kept misreading keeps the rewording. A row that is not flagged **is brought
up to date**, which is what lets a later release fix a shipped mistranslation on
every site that never edited it.

### Tools

| Tool | | |
| --- | --- | --- |
| `list_translations` | read, **on** | the register, and with `missing_only` the gap |
| `get_translation` | read, **on** | one key resolved, plus every language's version |
| `update_translation` | write, **off** | write or correct one string |

`/mobile/get_translation_bundle` is what a handset pulls once at login instead of
asking for one label at a time.

## 2. The shadow log RACI feed

### It is not a notification

A notification tells you to go and look at a record. A **Shadow Log Entry**
carries a frozen copy of the record's values *at the moment of the event*, and
the recipient reads the copy.

That single difference is the whole feature, and three things follow from it:

**What was acknowledged is what was shown.** A supervisor who ticked a session of
412 buckets acknowledged 412. If a recount later makes it 380, the
acknowledgement did not silently become an acknowledgement of 380 — which is
exactly what a notification pointing at a live record does, and which is
indefensible the moment somebody disputes a piece rate. The controller refuses
any change to a snapshot after insert, and `snapshot_hash` makes "frozen"
**checkable** rather than merely promised.

**It is a backup.** Three levels hold three copies. Losing the Bucket Log Session
— a bad migration, an over-enthusiastic delete, a doctype uninstalled — does not
lose the account of that morning. This is why `source_doctype` and `source_name`
are `Data` and not Links: a Dynamic Link would let a delete cascade into the
backup, which would make the backup worthless in precisely the case it exists
for. `get_shadow_log_entry` says plainly when the source has gone.

**The chain is evidence.** "Did anybody above this crew know?" comes up in an
OSHA interview, a wage claim and an audit, and the honest answers are "yes, on
this date" and "no, nobody was told". Both are answerable here and neither is
answerable from a feed that only kept the latest state.

### The chain is `Employee.reports_to`, and it may be short

```
event about ANA ──▶ level 1  her direct supervisor
                ├──▶ level 2  their supervisor
                └──▶ level 3  the one above that — on a farm this size, the owner
```

**The level is a distance, not a job title.** A crew whose chain is two deep
produces two copies, not three with the third addressed to whoever happened to be
around; inventing a recipient puts somebody's name against work they were never
told about. A person appears at most once — where a chain doubles back, the
nearer level wins.

**A cycle is survived and reported.** `reports_to` is operator-maintained, and
two people who report to each other is a data-entry error somebody makes rather
than a hypothetical. The walk carries a `seen` set and stops. A recursion that
blew the stack inside a bucket sync would take a morning's picking with it.

**An event about the operation rather than about a person** — a stale water test,
an uninspected cabin, an overdue filing — has no chain to walk, and goes to
whoever sits at the top of the company **at level 3 only**. Filing it as a level
1 would put a water test in a foreman's direct-report feed beside the crew
events.

### The four events

`sync_bucket_entries`, `end_shift`, a newly raised `Compliance Alert`, and
`complete_farm_task`.

The alert copy is raised **only on "created"**, never on a refresh. The nightly
sweep refreshes every open alert every night; a copy per refresh would be one row
per alert per night forever, and a feed that grows without bound is a feed nobody
opens.

### Propagation can never fail the work being filed

Every call site is somebody's real work: a picker's piece-rate record, a
foreman's signed shift, a completed job with its evidence. None of them may fail
because a supervisory copy could not be written. `propagate` catches everything
and returns a report; the callers put it in their result under `shadow_log`, so
what could not be done is **visible on a result that succeeded**.

That is the same trade `bridge_to_attendance` makes and for the same reason: the
compliance act is the thing being filed, and the convenience built on top of it
does not get to veto it.

### Idempotence is a unique index, not a check

`shadow_key` derives from the event, the source record and the recipient —
**never from a timestamp**. A handset that timed out and resent a batch is the
ordinary case on the bucket route, and a resend must not put a second copy of one
morning in front of the same foreman. A pre-check would lose the race between two
workers syncing at once, which on a crew of forty is a Tuesday.

**The first snapshot wins and is never refreshed.** Re-raising the same event
would otherwise migrate a supervisor's acknowledgement onto values they never
saw. A genuinely new fact about the same record is a new event with its own key.

### Acknowledgement is one-way

"I saw this" is a statement about the past, and un-seeing it is not an event that
can happen. A supervisor who acknowledged something they now dispute files the
dispute against the source record, where somebody will read it; clearing the tick
would leave no trace of either the seeing or the dispute.

It is **safe to retry**: a second call changes nothing and says so with
`x_idempotent`, because a phone that lost its response must not have to choose
between retrying and being correct.

### Tools and the switch

| Tool | | |
| --- | --- | --- |
| `list_shadow_log_entries` | read, **on** | by recipient, level, or acknowledgement |
| `get_shadow_log_entry` | read, **on** | the snapshot, its integrity, and whether the source survives |
| `acknowledge_shadow_log` | write, **off** | one-way, retry-safe, writes nothing to the source |

`shadow_log_feed_enabled` in **ERPNext MCP Settings** switches the propagation
itself off for an operation that does not run a chain of command — a two-person
orchard where everybody is the owner. It is a **feature** switch and not a tool
switch: the two reads stay live for rows already written. It ships **on**,
because the feed is the release, and it fails **on** rather than off — the
opposite of every security gate in this app, and correct here, because nothing is
exposed by writing a copy and a settings read that failed mid-migrate silently
switching off an audit trail is the worse of the two failures.
