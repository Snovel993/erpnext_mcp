# v0.48.3 — the I-9 said Complete and there was nothing behind it

Every photograph and every signature the onboarding wizard collected was
reported as filed and stored nowhere. Not some of them, and not intermittently:
all six per hire, on every device, for as long as the wizard has existed.

This release ends that. It is one defect with three fixes, and the third one is
the only reason to trust the first two.

---

## 1. What actually happened

`FrappeClient.uploadFile` POSTed multipart to Frappe's own
`/api/method/upload_file`. That is one URL and it is the whole story.

`api/fallback_auth.py` exists because the Tailscale funnel strips the
`Authorization` header — the module's own header explains it at length, with the
three probes that proved it. The compensation is `X-FarmOps-Token`, read by an
`auth_hooks` entry. But that hook's first act is a path check:

```python
_PATH_PREFIX = "/api/method/erpnext_mcp.api."
```

`/api/method/upload_file` is not under that prefix. It is Frappe's own endpoint,
not this app's, so the hook returned immediately and the token was never read.

What arrives at Frappe is then a request with no credential at all. Frappe's
answer to an unauthenticated call at a whitelisted method is not 401 — it is
**HTTP 200 carrying the Desk login page**, with `sid=Guest`. And the old
`uploadFile` did this:

```swift
switch http.statusCode {
case 200...299:
    return          // <- the body was never looked at
```

So: the app uploaded, got 200, returned success, and the wizard advanced. The
I-9 Form reached `Complete` on schedule. The evidence behind it did not exist.

**The six files, per hire:** the Section 1 signature, the List A document
photograph *or* the List B and List C pair, the Section 3 reverification
signature, and the photographed W-4. Under 8 U.S.C. §1324a(b)(3) the retained
document is the point of the exercise; a form that says a passport was examined
and holds no image of it is worse evidence than an empty file, because it
asserts something.

## 2. The fix, part one: one upload path, and it is the one that authenticates

The staged path — `stage_file_chunk` then `finalize_staged_file` under
`/farmops/api/files/` — has worked since v0.14.0 and carries task evidence
today. It is on the sidecar, so the sidecar's auth applies; it chunks at 512 KB,
so a photograph survives a truck moving between blocks; and it verifies the
SHA-256 the app computed at capture, so what assembles is what was photographed.

`ChunkUploader.upload(_ data:fileName:kind:)` is new and takes bytes the app is
holding rather than a file it has stored. The onboarding wizard's captures live
in `Data` on the view model and never reach `EvidenceStore`, which is why the
existing uploader could not carry them and why the multipart path existed at
all. Both entry points now share one staging loop.

`FrappeClient.uploadFile` is **deleted**. There is no second upload path left to
drift.

## 3. The fix, part two: something to attach the file to

`api/files.finalize_staged_file` deliberately commits evidence UNATTACHED, and
its module docstring is emphatic about why: forwarding an attachment target from
a handset would let a field worker hang a file off a Journal Entry, another
entity's lease, or a Governance Document. Task evidence gets attached afterwards
by `complete_task_via_mobile`, which checks the task is theirs.

Onboarding had no equivalent call. That absence is what sent the wizard to
Frappe's endpoint in the first place.

**`attach_onboarding_document`** is that call, and it is narrow on purpose:

* it names **one** parent doctype, in code — `Employee`, not an argument;
* the docname is proved to be an Employee inside the caller's own entities
  (`guard.require_scoped_doc`, so another entity's worker is *not found* rather
  than *refused*);
* the **HR role is required with no exception**, not even for the caller's own
  record — an account that could file its own identity documents could file
  anything as its own identity documents;
* **no bytes cross it.** It takes the `file_token` that `finalize_staged_file`
  handed back, exactly as `upload_signed_i9` does;
* the File is made **private** on the way in, through the document rather than
  through `db.set_value`, because flipping `is_private` MOVES the bytes between
  `public/files` and `private/files` and rewrites the URL. A passport photograph
  on a public URL is a breach nobody has to guess a password for;
* a File **already attached elsewhere is refused** — re-pointing it would take
  evidence off the record it was filed against, and both records are federal;
* a File already on **this** employee is a **no-op** that says so
  (`already_attached: true`), because a phone whose call timed out does not know
  whether it landed.

The signed paper I-9 goes somewhere better now. `upload_signed_i9` has existed
since v0.47.1 and attaches the photograph to the **I-9 Form** itself, pointing
`signed_pdf` at it. `OnboardingAPI.attachSignedI9` carried a long comment saying
no such endpoint existed and the file had to go on the Employee instead; that
had been untrue for two releases, and the file it produced was landing nowhere
regardless.

## 4. The fix, part three: a 200 is not evidence that anything happened

This is the part that matters more than either of the others, because parts one
and two are a fix for one call and this is a fix for the class.

`FrappeClient` now refuses any 2xx whose body is not a JSON object, on every
path it has — `callRaw`, `postResource`, `putResource`, `getResourceList`,
`getResourceDoc`. **HTML is reported as `unauthorized`, not as a decoding
error**, because that is what it has meant every single time it has happened: a
Frappe site answering an unauthenticated API call renders the login page.
"The farm server sent something Farm Ops didn't understand" is the least useful
true thing this client could say, and it is what v0.17.x said for a fortnight.

This closes a hole wider than the one it was written for. `callVoid` discards
the body by design, and **every** onboarding write goes through it —
`submit_i9_section_1`, `submit_i9_section_2`, `submit_w4`,
`link_badge_to_employee`, and every staged chunk. On any path where the
credential stopped arriving, all of them would have reported success on a login
page in exactly the same way. They cannot now.

And `attach_onboarding_document`'s answer is **decoded**, not discarded:
`OnboardingAPI.AttachedDocument` declares `file_token` non-optional, so a
response without one throws. A method whose answer nobody decodes is a method
whose failure nobody sees — which is the sentence this release was written to
delete from `UndecodedResponseModel`'s docstring, where `upload_signed_i9` had
been sitting.

## 5. What is asserted, and where

`test_farmops_api.TheOnboardingEvidenceActuallyLands` drives the whole path over
a real WSGI stack, because in-process the bug was invisible: no server-side test
can see which URL a phone chose, and every test in this repo passed on the day
the defect shipped.

* stage → finalize → attach, with a credential, leaves a **File on the site,
  private, attached to the Employee**;
* **each of those three calls, with no credential, answers 401 and JSON** — the
  assertion this release is about, since the old path answered 200 to exactly
  that request;
* a refused attach leaves the File where it was, so a 401 that had already
  written cannot be worse than the silent success it replaces;
* a picker without the HR role is refused (400, and 400 rather than 401 on
  purpose: the credential is real, the app stays signed in, and the day's queued
  work survives);
* another entity's Employee is a 404.

`test_ios_contract.test_42_*` mirrors the iOS `Codable` key by key, pins the
retry as a no-op, pins the cross-record refusal, and asserts that **no byte-
carrying argument exists on the endpoint** — the property that keeps there being
one upload path rather than two.

`test_api_mobile` and `test_farmops_api`'s closed-surface assertions caught this
route being added, in both directions, which is what they are for.

## 6. What this release does not fix

**A handset running an older build still loses its evidence.** The server change
cannot help it: the fix is that the app stops calling
`/api/method/upload_file`, and a shipped build goes on calling it. Adding that
path to `fallback_auth._is_mobile_path` would make the old build work — it is
the same credential and the same user — but it would extend this app's auth hook
over a Frappe core endpoint that none of `guard.py`'s seven checks cover, for
the benefit of builds that are about to be replaced. That is a decision to take
deliberately or not at all, and it is not taken here.

**Evidence already lost is lost.** There is nothing on the site to recover: the
bytes never arrived. Any I-9 completed through the wizard before this release
should be treated as having no document images, and the affected hires
re-photographed.
