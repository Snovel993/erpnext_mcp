# v0.50.1 — a bucket is full or it is not, and now the tests say so

Tim's clarification, written down where it cannot be lost:

> Bucket counting is a **binary gate**. A bucket is either full or not full.
> There is no percentage, no partial credit, no coverage percentage in the pay
> calculation. Full counts as 1 bucket, not-full counts as 0. Piecework pay is
> `number_of_full_buckets × piece_rate`.

**The code already did this.** That is the first thing to say, because it decides
what this release is: an audit, a set of assertions and a correction to how the
rule was described — not a change to anybody's pay. Nothing in this release
alters a figure on a slip.

## What was checked

Two independent paths turn a Bucket Log Entry into piece units, and both were
already binary:

| Path | How a bucket becomes units |
|---|---|
| `bucket_bridge.entries_to_payroll_shape` → `payroll_integration._piece_units_for` | one row per Accepted entry, **no count column**, and `_row_units` reads a row carrying none of `_UNIT_KEYS` as exactly `1.0` |
| `tools/payroll.py::_bucket_log_rows` (the production loader) | `units = 1.0` unless the doctype carries an actual unit column; Bucket Log Entry as this app ships it does not |

`coverage_percent` appears in neither. It is not in `_UNIT_KEYS`
(`piece_units, units, quantity, qty, bucket_count, count, bins`) and
`entries_to_payroll_shape` never emitted it. `get_piecework_summary` reports
`piece_units = total_accepted`, a count. `reconcile_bucket_payroll` counts rows.

## What was missing, and is the actual content of this release

**Nothing asserted it.** The guarantee rested on two facts staying true in two
modules that do not import each other's constants — and the failure mode is the
worst kind: silent. Pay would still come out. It would be wrong by a fraction
nobody could see without recomputing a period by hand.

`test_bucket_bridge.TheGateIsBinary` closes that, written against
`payroll_integration._UNIT_KEYS` **itself** rather than a copy, so a key added on
one side and a row grown on the other cannot drift into agreement:

- a capture at 51% and one at 99% are both worth exactly one bucket
- a Rejected capture at 99.9% is worth nothing
- a capture with **no** coverage at all is a whole bucket
- ten accepted captures at ten different coverages are `10.0` units, and the
  total is asserted to be a whole number
- `coverage_percent` reaches neither the payroll row nor `_UNIT_KEYS`
- the payroll row's keys are exactly `{employee, entry_uuid}`, checked against
  every spelling in `_UNIT_KEYS`
- and one test that exists only to show *why* the others matter: `_row_units`
  honours a count column where one exists, so the whole guarantee rests on the
  payroll row not having one

The end-to-end test in `test_badges.py` now gives its three captures three
different coverages (51%, 99%, and a Rejected 97%) so `piece_units == 2.0` is a
statement about the gate rather than a coincidence — 51% + 99% would be 1.5 if
anything anywhere multiplied.

`BucketPipelineTests` carries the phone half: `accepted` is the only field a
capture is worth anything on, all four `AutoVerdict` cases collapse to one bucket
or none, and the sync payload carries no unit count of any spelling for the
server to multiply by.

## Where the rule is now written down

`bucket_bridge.py`'s module docstring (a section of its own, with the
arithmetic), `validate_bucket_entry` (the verdict decides; coverage is
range-checked so bad units are caught, not because the figure buys anything),
`entries_to_payroll_shape` (why the row is built key by key rather than copied —
one forgotten field is one `coverage_percent` reaching `_row_units`), the
`sync_bucket_entries` registry description, `docs/tool-catalog.md`, and
`BucketEntry.swift` on the phone.

## Three places the interface implied partial credit

Documentation was not the only thing saying the wrong shape.

- **The verdict pill** on the committed capture read `Full — 94%`. A percentage
  next to a verdict invites "this bucket is worth 94% of something". It now reads
  **`Full — counts as 1 bucket`**.
- **The bucket history** put the coverage percentage in the headline position
  beside each row's verdict. It now shows **`1`** or **`0`** — what the row is
  actually worth — with a running "N bucket(s) counted" header, and coverage
  demoted to a `model read 94%` caption where a diagnostic belongs.
- **The live aiming meter** is kept, because it is a viewfinder aid: it tells a
  picker when the model is about to fire so they know when to hold still. It
  gains a line saying **`Full — will count as 1`** once it crosses the threshold,
  so what the number is for is unambiguous.

## The v0.50.0 changelog entry was misleading and is corrected

v0.50.0 found a real bug — `BucketEntry.coveragePercent` is the model's fraction
(0…1) and the server's column is a percentage (0…100), so an unscaled value would
have been stored as "0.94% full" — and described it as though it mattered to pay.
It does not. It made the **model-audit trail** read as nonsense, which is worth
fixing and is a different thing. The entry now says so.

## Upgrading

Nothing to do. No doctype change, no settings change, no tool signature change,
no change to any computed figure. `bench --site <site> migrate` is not required
by this release.
