# v0.18.4 — chunk size ceiling + evidence file permission cascade

**Two fixes bundled — both discovered tonight after v0.18.3 shipped, both
blocking the same iOS→compliance-record path.**

Tim's Farm Ops Settings tab surfaced the actual iOS-side error tonight
(v0.18.3 fixed the permission but the phone was already failing on the *next*
constraint): seven queued completions, each with the error text
"chunk_base64 is 699052 characters, over…". The ceiling was hit, iOS marked
every mutation Failed and stopped retrying.

## Root cause

`tools/uploads.py` set `MAX_CHUNK_BASE64 = 200 * 1024` — 200 KB of base64 per
chunk. The comment on that constant explained WHY: "200 KB is roughly where a
model's own context stops it composing a larger argument". True for MCP tool
callers (Claude Desktop composes each `stage_file_chunk` invocation as one
JSON argument in its context window), completely irrelevant to iOS.

Farm Ops iOS uses `FarmOpsKit.FarmOpsConfig.uploadChunkBytes = 512 * 1024` —
512 KB of raw file bytes per chunk. Base64-encoded that's ~699,050 characters
per chunk, more than 3× the server's cap. Every iPhone photo upload hit the
400 wall.

## Fix

`tools/uploads.py` — `MAX_CHUNK_BASE64` from `200 * 1024` to `800 * 1024`,
with the comment rewritten to say the true story: the ceiling accommodates
iOS's shipped chunk size + a margin; MCP callers self-limit to their own
context window, which is the real constraint, not this one.

Total file cap moves from `600 × 200 KB base64 ≈ 90 MB` to
`600 × 800 KB base64 ≈ 360 MB`. Housing inspection photos are ~2-5 MB, so
plenty of headroom.

## Fix 2 — Evidence Files unreadable by anyone except the uploader

The first fix let the Housing Inspection through. Tim opened HI-2026-08-00002
in Desk and saw the two evidence rows (Photo 642d9b2fed + Signature
140858afdc), but clicking to preview either got:

    Not permitted
    Not allowed via controller permission check
    User tim.polehn@gmail.com does not have access to this document:
    File - 642d9b2fed
    Insufficient Permission for File 642d9b2fed

**Root cause.** iOS uploads Files as **private**, owned by the mobile user who
took the photo. Left that way, the File records have no relationship to the
Housing Inspection they were captured for — the only link is a Farm Task
Evidence child row that references the File by docname. Frappe's
`File.has_permission` doesn't traverse child-table references, so it falls
back to "does this user own the file?", answers no for anyone but the mobile
uploader, and refuses the preview. **An auditor opening a compliance record
sees the child rows but cannot see the photos.**

**Fix.** New helper `_link_evidence_files_to_parent` in `tools/inspections.py`
sets `File.attached_to_doctype = <the record's doctype>` and
`File.attached_to_name = <the record's name>` on every evidence File after
the parent is inserted. That is Frappe's own idiom for "this file belongs to
that record" — `File.has_permission` then answers yes for anyone who can read
the parent. Uploader still owns the File, still marked private, but the
parent record's permission is now the gate.

Called from `build_housing_inspection`, `build_detector_test`, and
`build_water_test` — the three inspection record builders that share the same
Farm Task Evidence child doctype. One helper, three call sites.

## Post-deploy — clearing the failed queue

After the deploy lands, turn wifi back ON. iOS's SyncEngine will still see the
7 items as **Failed** (from earlier attempts that hit the old 200 KB ceiling)
— failed items are NOT retried automatically. Tap **Sync now** in the Farm Ops
Settings tab; that calls `queue.retryAllFailed()` which flips each item back
to Waiting and re-attempts.

If Sync now doesn't clear them (some might have references to evidence bytes
already deleted from the phone), just re-open each In-Progress task, tap
Complete, capture a fresh photo, submit. The queue will drain on the next
sync cycle.

Then check `http://umbrel.local/app/housing-inspection` — records should
finally appear with attachments.
