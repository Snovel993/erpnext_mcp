## Item 1 — `record_training` MCP tool

**Why now.** Flagged as HIGHEST value in the v0.18.1 HR MCP roadmap. Expiring
certificates become the same shape of thing as overdue inspections — one board,
one worker, one refusal when the credential lapses.

**Doctype decision.** Frappe HR ships a `Training Result` doctype but it's
oriented around Training Events (a scheduled class an instructor delivers to
multiple employees) rather than the "here's a cert, here's when it expires"
shape farm operations actually need. Create a new **Employee Training Record**
doctype in `erpnext_mcp/erpnext_mcp/doctype/employee_training_record/`.

Fields:
- `employee` (Link → Employee, required)
- `employee_name` (fetched)
- `company` (Link → Company, fetched from employee)
- `training_type` (Data, required) — free-text, e.g. "OSHA 30", "Forklift Certification", "Pesticide Applicator"
- `training_source` (Select: Internal / External / Contractor, default Internal)
- `completed_date` (Date, required)
- `expires_date` (Date, optional) — null means "does not expire"
- `instructor` (Data, optional)
- `certificate_file` (Attach, optional)
- `notes` (Text, optional)
- `status` (Select: Active / Expiring / Expired, read-only, auto-computed)

Auto-status hook (before_save):
- If `expires_date` is None → Active
- If `expires_date` < today → Expired
- If `expires_date` <= today + 90 days → Expiring
- Else → Active

**Compliance rule.** Add `training_expiring` to
`erpnext_mcp/alerts/rules.py`, patterned on `certification_expiring` (line 141+).
Rule ID: `training_expiring:Employee Training Record:<name>`. Severity:
- Expired → Critical
- Expiring within 30 days → Critical
- Expiring within 90 days → Warning

**MCP tools (three, all through the same guard pattern as create_employee):**
- `record_training(employee, training_type, completed_date, expires_date=None, instructor=None, certificate_file=None, notes=None, training_source="Internal")` — mutating, default OFF, role gate HR Manager/Farm Manager/System Manager, company scope via Employee.company
- `list_trainings(employee=None, company=None, status=None, expiring_within_days=None)` — read-only
- `get_training(name)` — read-only

**Register:** in `erpnext_mcp/registry.py` under the HR section (near
create_employee).

**Tests:** `tests_standalone/test_training.py`
- Insert + verify status auto-computed
- Insert with past expires_date → status Expired + compliance alert fires on next sweep
- Insert with expires_date 60 days out → status Expiring + Warning alert
- Role gate rejects non-HR user
- Company scope rejects cross-entity record
- Kill switch off → refuses

## Item 2 — Contract test suite

**Why now.** The v0.18.2 claim_task shape bug (backend returned `{"name": null,
...}`, iOS crashed) was preventable with a test that decodes every mobile
method's response against a Python model mirroring the iOS Codable. Same drift
already caught three times this month: QR schema (v0.17.1), transport (v0.17.2),
shape/evidence (v0.18.2).

**Structure.** `tests_standalone/test_ios_contract.py` — for each of the 11
mobile methods, define a Python NamedTuple or dataclass matching the iOS
Codable at `fafo_ios/FarmOpsKit/Sources/FarmOpsKit/Models/*.swift`:

| Method | iOS Codable | Strict fields (fail if None) |
|---|---|---|
| `get_current_user_context` | `UserContext` | `user`; each `AccessibleCompany.name` |
| `list_my_tasks` (each row) | `FarmTask` | `name` |
| `list_available_tasks` (each row) | `FarmTask` | `name` |
| `get_task` | `FarmTask` | `name` |
| `claim_task` | `FarmTask` | `name` |
| `start_task` | `FarmTask` | `name` |
| `complete_task_via_mobile` | `CompletionResult` | (all lenient today, but check) |
| `reject_task` | task/state summary | `task` (string) |
| `list_compliance_alerts` (each row) | `ComplianceAlertSummary` | `name` |
| `stage_file_chunk` | staged response | `chunk_index` or `next_expected_index` |
| `finalize_staged_file` | finalized response | `file_token` OR `file_url` |

Each test:
1. Create fixture data (Farm Task, Housing Unit, etc.) via existing tool
   functions
2. Call the mobile wrapper as an authenticated fixture user
3. Try to build the Python model from the response
4. Fail if any strict field is None with a message naming the method, the
   field, and pointing to the iOS Codable line

**Bonus:** the mirroring Python models become documentation. Adding a new
mobile method requires adding a Python mirror, which forces the contract to
be stated once in code.
