# v0.84.0 — what the block cost, and what it cost per acre

Ten tools, six doctypes, one engine. It answers the question a chart of accounts
cannot: **what did the Home Block cost per acre.**

---

## The one idea

Every farm can already say what it spent. Almost none can say what a block cost,
because the spend does not arrive labelled by block. It arrives labelled by
supplier, by account and — on a well-run site — by cost centre.

The usual workaround is to divide the overhead account by total acreage. That is
arithmetically fine and managerially useless: it charges the twelve-year-old Gala
and the newly grafted replant the same spray cost, when one was sprayed nine
times and the other four. The number it produces is not *approximately* right; it
is systematically wrong in the direction that flatters whichever block is worked
hardest, and there is nothing in the output that says so.

Activity-based costing answers it in two steps. Gather cost into a **pool** per
**activity** — spraying, pruning, irrigating, picking, packing. Then push each
pool out to blocks in proportion to how much of that activity each block actually
consumed: the **cost driver**.

```
GL Entry ──▶ Activity Cost Pool ──▶ ABC Cost Assignment ──▶ per acre, per phase
 (by account,     (by activity,          (by block,
  by cost centre)  one per year)          every intermediate stored)
```

Both steps are stored. That is the design decision the rest of this release
follows from.

---

## 1. The engine will not estimate a driver

This is the whole release, and everything else is machinery around it.

Two drivers are **derivable** from what this site already holds:

* **`Acres`** — each Field's acreage weighted by the days it was productive in
  the period. Computed by `services/sustainable_cf_per_acre.productive_acres()`,
  unchanged, so the ABC report and the Sustainable CF/Acre KPI cannot grow
  separate opinions about what an acre is. A block with no `productive_from_date`
  is **excluded** rather than assumed to be earning — the same posture v0.19.5
  took, for the same reason.
* **`Direct Assignment`** — the pool names the one block the cost was incurred
  for. This is the honest way to model a replant on a single field, rather than
  inventing a driver in order to spread it.

Every other driver — hours, machine hours, applications, bins, boxes, deliveries,
employees — is a **measurement somebody took**. Supply it:

```json
{"activity": "Hand thinning", "cost_object": "FIELD-0001", "quantity": 90}
```

…or the activity comes back `UNALLOCATED` with its full amount and the sentence
naming what would fix it. Its money lands in `unassigned_amount`: not in the
assigned total, and **not spread evenly across the blocks**.

That refusal is the point. An even spread is indistinguishable in the output from
a measured one. A report that quietly performed it would produce exactly the
answer this module was adopted to stop giving, and would produce it with the
confidence of a system that had done real work. `unassigned_amount` is the most
useful figure on the run: it is precisely the cost this operation cannot yet
attribute, and it names the measurement that would close the gap.

Supplying quantities for an `Acres` activity **overrides** the derived acreage,
and every line it touched says so in `driver_source`. Which half of a report is
evidence and which half is arithmetic over the Field table is never left to be
inferred.

## 2. The intermediates are stored, and that is why the doctype exists

A per-acre cost is a quotient of two numbers that **both moved during the year**.
An operation that keeps only the quotient can watch it rise for four seasons and
never learn whether the block got dearer or simply smaller.

So every `ABC Cost Assignment Line` carries the driver quantity, the driver
share, the pool, the amount assigned *and* the acres — the numerator, the
denominator and the working. `driver_quantity` is stored rather than recomputed
on read because the hours somebody measured in March are a fact about March, and
a report that re-derived them from today's Field table would quietly restate a
prior year.

Reruns **append**. The history of what this operation believed its costs were is
itself a record, which is what makes a corrected pool a visible event rather than
a silent overwrite. A consumed pool is flagged `Allocated` — the flag records that
a run happened; it does **not** lock the pool, because a corrected pool that could
not be re-allocated would freeze an error in place.

The arithmetic identity is stored rather than asserted:

```
total_assigned + unassigned_amount = total_pool_amount
```

Both halves are on the document, so a reader checks it without rerunning the
engine.

**The rounding residual is placed, not dropped.** £100 across three equal
consumers is 33.33 three times, which is 99.99. The residual goes to the largest
consumer, where it is proportionally smallest, so the lines add up to the pools
exactly. A run whose lines do not reach its pools is a run whose totals disagree
with themselves.

## 3. `field` narrows the rows and never the arithmetic

`compute_abc_allocation` takes a `field`, and it filters what comes back. It does
not filter what is computed.

A driver share computed against one block is **100% by construction**. Every
share above is computed against every block that consumed the activity, and the
stored document holds the whole run for the same reason — a stored partial run
would be a historical record of an allocation nobody performed.

---

## 4. Two kinds of evidence, kept apart

A **ledger** pool is totalled off `GL Entry` over the activity's cost centre and
accounts, and **itemised by account**, so the figure walks back to the books. The
scope is an **AND** and the trail is a **breakdown of it**: totalling each filter
independently would double-count every entry matching both and produce a
plausible pool whose evidence quietly disagreed with it. The controller refuses a
ledger pool whose sources do not reach its amount within a cent, because the trail
is the only reason to believe the figure and one that disagrees with the number
above it is worse than no trail at all — it reads as evidence.

A **manual** pool is a legitimate figure and an entirely different kind of
evidence. `amount_source` is a column rather than a footnote, and
`list_activity_cost_pools` separates the two totals, so nobody has to take a
report's word for which is which. An operation whose chart is not yet arranged
around its activities can still cost them.

A **negative** pool is refused: allocating it credits every block in proportion
to how much of the activity it consumed, which is arithmetic nobody asked for. A
**zero** pool is stored — "this activity cost nothing" and "nobody has computed
this activity" are different statements and only one is worth acting on. A
**Draft** pool is skipped and *said* to be skipped, because a draft pool is not a
zero pool either.

## 5. The per-acre view, and the denominator that changes under it

`get_abc_report` groups by field, activity or phase. The denominator is not the
same in all three, and that is the one thing about this report worth reading
carefully:

| `group_by` | Divided by |
| --- | --- |
| `field` | That block's **own** time-weighted productive acres |
| `activity` | The **whole operation's** productive acres |
| `phase` | The **whole operation's** productive acres |

"What did the Home Block cost me per acre" and "what did spraying cost me per
acre across the farm" are different numbers, and a reader who assumes the wrong
one is wrong by the ratio of one block to the farm. So `acres_basis` states which
was used **on every single row**.

Grouped by field, a block's acreage is taken **once**, not summed per line —
adding it once per activity would divide by the acreage several times over and
make a heavily worked block look cheap. A group with no productive acres reports
`cost_per_acre` as **null, never zero**: zero is a per-acre figure for a division
nobody performed.

The report **never computes**. It reads a stored run, so it cannot disagree with
the allocation it claims to be reporting.

## 6. The waterfall: read the shape, not the total

Cost does not land on a bin all at once. It accumulates as fruit moves
**Growing → Harvest → Post-Harvest → Packing → Sales**, and "where did this get
expensive" is a question about the accumulation rather than the sum. The total is
available from any ledger; the accumulation is not.

Each stage reports what it **added** and what the fruit is **carrying** as it
leaves — per acre always, and per unit when `units` is supplied.

**It will not invent a unit count.** With no `units` the per-unit column is null
and the report says why. Picking a denominator is the step that turns a costing
report into fiction, and that rule is inherited from `get_absorption_cost_report`
rather than reopened here.

**A phase nothing is mapped to is reported at zero with a note**, not omitted. An
unmapped phase and a free one look identical in a total and are not the same
finding. Unallocated pool money is broken out **by phase**, so a reader sees which
stage of the pipeline is under-measured rather than only that something is.

`phase` is therefore not a label on the activity. An activity in the wrong phase
does not lose money from the total — it reports real cost arriving at the wrong
moment, which is worse, because deciding where cost enters is the entire use of
the waterfall.

## What ships

**Six doctypes.** `Cost Activity` (+ `Cost Activity Account`), `Activity Cost
Pool` (+ `Activity Cost Pool Source`), `ABC Cost Assignment` (+ `ABC Cost
Assignment Line`).

**Ten tools** — six read, on by default; four mutating, off until an operator
turns them on:

| Tool | |
| --- | --- |
| `create_cost_activity` | **Mutating** |
| `get_cost_activity` | Read |
| `list_cost_activities` | Read |
| `update_cost_activity` | **Mutating** |
| `create_activity_cost_pool` | **Mutating** |
| `list_activity_cost_pools` | Read |
| `compute_abc_allocation` | **Mutating** (`dry_run` writes nothing) |
| `get_abc_assignment` | Read |
| `get_abc_report` | Read |
| `get_phase_waterfall` | Read |

**No new control point, deliberately.** Unallocated cost is a measurement gap
rather than a policy breach, and a compliance alert that fired every time
somebody had not yet counted their spray applications would be noise on a farm
mid-setup. The figure is reported prominently instead — in the run, in every
report, and broken down by phase in the waterfall.

**Nothing is posted.** Every tool here reads the ledger or writes to its own
registers. An ABC allocation is a management view of costs that are already
booked; an app that posted journal entries to move them would produce a second
set of books and no way to reconcile the two — which is the state cost accounting
exists to avoid, and the same argument `get_absorption_cost_report` makes in
v0.80.0.

**No changes to existing doctypes and no new custom fields.** This release reads
`Field`, `Cost Center`, `Account`, `GL Entry` and `Fiscal Year` and modifies none
of them.

---

## Where it sits beside v0.80.0

Phase 3 shipped `Standard Cost` and `get_absorption_cost_report`. Those answer
"what *should* this have cost" and "what did a bin cost including the packhouse
overhead it absorbed". Neither can say **which block** consumed the overhead,
because absorption divides one pool by one quantity.

ABC is the missing dimension, and it deliberately does not replace either. A
standard is still the benchmark, absorption is still the toggle on the read, and
an ABC assignment is now the answer to "which block, and on what evidence".
