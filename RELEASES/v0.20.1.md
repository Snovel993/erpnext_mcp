# v0.20.1 — the acknowledgement that never arrived

**Released 2026-08-03. `complete_task_via_mobile` is idempotent. A completion
that reaches the server and whose answer does not reach the phone can be re-sent
safely, which it could not be this morning.**

Tool surface **238 → 239** (107 read, 132 mutating) — one new read,
`list_visits`. Suite **3,984 → 4,055 passing**. Two additive columns on Farm Task
Assignment and one backfill patch. No existing behaviour changed.

---

## 1. What happened on an iPad

The evening of 2026-08-03, in the field:

- A worker completed their tasks with the wifi off. **The offline path was
  correct** — Tim confirmed it in as many words: *"It did work when I shut off
  the wifi."*
- The handset found signal and the sync queue began to drain.
- **The server processed every completion successfully.** Evidence filed,
  compliance records written, register moved forward.
- The connection dropped between the server's acknowledgement and the app's
  receipt of it.
- The app re-sent, which is the only thing a client can do.
- The server answered **`already Completed` as a hard error**.
- Three Failed entries per task in the sync queue, on work that was done, filed
  and evidenced the first time.

The refusal was not wrong as a data-integrity rule. It was wrong as an API
contract.

**A CLIENT CANNOT KNOW WHETHER ITS REQUEST LANDED.** Not with better retry
logic, not with a longer timeout, not with a more careful queue. The
acknowledgement is a second message and it can be lost independently of the
first. The only place that question can be answered is the server, and it can
only be answered by the server being able to recognise a request it has already
served.

The iOS half of this — queue dedup, treating "already Completed" as a sync
success, pulling server state on sync — ships in the parallel v0.20.1 app task.
This is the server half, and it is the half that makes the app's half correct
rather than merely quiet.

## 2. `completion_signature` — what makes two submissions one

A new Data column on Farm Task Assignment, written by the completion that
produces it. `erpnext_mcp/completions.py` computes it: one sha256 over five
components, unit-separated.

| Component | Why it is in the hash |
| --- | --- |
| The assignment docname | The completion is of one assignment |
| The worker (`assigned_to`) | A completion carries the completing worker's identity **as evidence** |
| The evidence, as sorted file references | What was filed |
| `findings_text` + `completion_narrative`, end-trimmed | What they said about the work |
| `completed_at` **as the client sent it** | Or empty, where the client sent nothing |

**The last row is the one that decides whether this works.** The server fills a
missing `completed_at` with `now()`, and `now()` is different on every attempt.
Hashing what the record ended up with rather than what arrived would make every
resubmission a conflict — the exact failure being fixed.

Three things are deliberately **not** in it. `farm_location_gps`: the second
attempt may carry a fix the first one lacked because the worker walked out of
the shed, and that is the same completion with a better location.
`clean_pass`: it must agree with `findings_text`, which is hashed. `visit_id`:
it groups completions, it does not identify one.

### File docnames, not content hashes

The obvious alternative is to hash the evidence bytes. Wrong twice over.

A File docname in this app is minted by exactly one function —
`api/files.finalize_staged_file` — and that function verifies the client's
declared sha256 against the assembled bytes before minting anything. The docname
is not a weaker identifier than the content hash; it is a token that **already
had the content hash checked against it**, by the only code path that can
produce one.

And a content hash cannot be backfilled. Farm Task Assignment's evidence child
table records `file` and `file_url` and has no hash column — `RELEASES/v0.17.1.md`
named that as an open follow-up and it is still open. A scheme whose backfill
could not run on the rows that already exist would leave every pre-v0.20.1
completion permanently unmatchable, which is most of what a stuck iPad is
carrying.

## 3. The new behaviour, and the refusal that survives it

```
task not Completed                       →  normal path, unchanged
Completed, signature matches             →  the existing completion, x_idempotent: true
Completed, signature does not match      →  refused, as before
Completed, no signature at all           →  refused, as before
held by somebody else                    →  refused, as before ("…is not chain of custody, it is a rumour")
```

**The idempotent branch writes nothing.** There is no `save` in it. No second
compliance record, no duplicated evidence rows, no state transition. The
response is rebuilt by reading the assignment that already exists, so three
rapid retries produce three identical answers and one record — asserted by a
census of every doctype on the site before and after, rather than by spot-checks
of the tables somebody thought of.

**A conflict is still a conflict.** Two people cannot file the same completion.
A second, different account of the same work is not the first one again. A task
genuinely completed twice by accident is something somebody should be told
about, not have quietly absorbed. Absorbing those would be a worse bug than the
one being fixed, and the whole value of the signature is that it separates them
from a phone asking the same question twice.

### The other half of the same bug

A completion ends the **live** assignment. So a retry carrying only a task name
found nothing live and was refused with *"has nobody holding it"* — a worse
answer than "already completed", and the same lost work. `_assignment_for` now
takes `or_completed`, passed by the completion path and by nothing else: starting
or rejecting a finished task is a genuine mistake and still says so.

## 4. The backfill, and what it refuses to guess

`erpnext_mcp/patches/backfill_completion_signatures.py`. **The rows this is for
are the rows most likely to be re-sent** — an iPad carrying a stuck queue since
before this release is carrying completions of v0.19 work. A feature that only
worked on data created after it shipped would have missed the actual complaint.

Four of the five components are on the row and are exactly what the client sent.
**The fifth is not knowable.** `completed_at` is stored, but nothing on the row
says whether the client chose it or the server did, and those hash differently.

So it does not guess. Backfilled rows get the **`v1b`** scheme, which leaves the
clock-out time out of the hash; `completions.matches` reads the prefix off the
stored value and compares under the same rule. Everything else is still
compared, so a legacy row re-submitted by a different worker, with different
evidence, or with a different account of the work is still the conflict it
should be.

Listed in `patches.txt` **and** called from `after_migrate`, the same pair
`migrate_training_types` uses: the patch entry records the first run in the Patch
Log, the hook catches a site that upgraded across the version. The second run is
a no-op — it only selects rows whose signature is empty, and **a row that already
has one is never rewritten**, not even where recomputing would produce the same
string. It writes with `update_modified=False`, because `_last_completion` orders
by `modified` and a backfill has no business reordering history.

It does not raise. Inside `bench migrate` an exception aborts the migration for
the whole bench, and a completion left unsigned is not broken — it behaves
exactly as it did in v0.19.7, which is where every one of those rows already was.

## 5. `visit_id` and `list_visits` — the trip, not the tasks

Deferred from the v0.20.0 spec. Additive.

**A worker does not go to a task, they go somewhere.** They drive to the north
block, walk five cabins, close five assignments and drive back. The board records
five completions with five timestamps, and every question about the morning — how
long was the trip, was the drive worth it, how many places did we send somebody
to twice — has to be reconstructed by guessing which completions belonged
together.

Guessing from timestamps is wrong in both directions and no threshold fixes it.
Two cabins forty minutes apart on one unhurried walk look like two trips; two a
minute apart from opposite ends of the property look like one. **The handset is
the only thing that knows** — it is there, it saw the worker arrive. So it mints
a `visit_id` and reuses it for every task closed before they leave.

`complete_task_via_mobile` accepts it, persists it to the assignment, and returns
it so the app can prove the round trip. **Unvalidated in v0.20.1 beyond being a
string**: the app mints it, and a server with opinions about somebody else's
identifier format would refuse a completion over the one field on it that carries
no evidence. v0.20.2 can tighten it once the iOS format is confirmed.

### `list_visits` (read, on by default)

`company`, `worker`, `location`, `from_date`, `to_date`, `limit`. Per visit:
the span, the places, the company, the completing worker, the assignment
docnames, the task count, the distinct evidence-file count, and the duration.

Three decisions worth naming:

**A completion with no `visit_id` is in no visit.** Not a synthetic one-task
visit, not an "unassigned" bucket dressed as a trip. Everything filed before
today has the column blank, and inventing visits for those would put fabricated
trips beside real ones with nothing to tell them apart.
`ungrouped_completions` reports how many, which is the honest version of the
same information.

**One-task visits are returned.** Somebody drove out, did one job and drove
back — which is precisely what a question about wasted travel is looking for.
Filtering to "visits worth showing" would mean the report answers that question
by hiding its evidence. `single_task_visits` counts them so a caller filters
knowingly.

**There is no `Farm Visit` doctype and there should not be one.** A visit has no
facts of its own — every field is derived from the completions in it. A row that
had to be created before them could not be created by a client that was offline
when the trip started. That is the same argument this codebase makes about Farm
Task Assignment being a doctype rather than a child table, run the other way:
the assignment holds facts nothing else holds, and a visit holds none.

`duration_minutes` is first completion to last and **says nothing about the drive
out or the walk in**; a one-task visit measures zero, because one completion is
one instant. `total_evidence_files` counts distinct **Files**, not evidence rows:
one signature filed against three cabins is one photograph.

## 6. What did not change

Every existing success path. The evidence-contract refusal, the empty-string
`findings_text` distinction, the `clean_pass` three-state rule, the
Awaiting-Review routing on a record that found something, the chain-of-custody
refusal, the concurrent-claim limit, the v0.19.1 location field. The idempotent
answer is a **new branch on a state that used to raise**, not a change to a state
that used to succeed — `TheFirstCompletionIsUnchanged` in
`tests_standalone/test_mobile_idempotency.py` asserts exactly that, and the
v0.18–v0.20.0 tests pass untouched.

The v0.19.x compliance rules, the weather service and the KPI computation are
not touched by this release.

## 8. Upgrading

```
bench --site <site> migrate
```

Adds `completion_signature` and `visit_id` to Farm Task Assignment, adds
`allow_list_visits` to ERPNext MCP Settings (default on, as every read is), and
signs the completions already on the site. Running it twice is a no-op. There is
nothing to configure and nothing to turn on.
