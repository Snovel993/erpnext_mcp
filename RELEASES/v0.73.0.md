# v0.73.0 — one system knows whether the bank data is complete

Three doctypes, fourteen tools, two whitelisted endpoints, and the end of a
split authority.

---

## The gap

Two systems held financial truth for the same farm.

**ERPNext** owned the Bank Transactions, the ledger, the companies and the audit
trail. **Bank Bridge**, a Flask sidecar, talked to the aggregator, parsed
statement PDFs, and kept its own database of *statement anchors* — the
period-by-period reconciliation record that says whether a month ties out. So
the question "does account ••6030 reconcile in October?" could not be answered
from the system that holds October's transactions. It had to be asked of the
sidecar.

That is not an inconvenience. It is two places where the same fact can be
recorded and nothing to say which is right when they differ — and the fact in
question is the one an accountant asks first.

**The thing ERPNext could not answer at all was completeness.** Every existing
bank tool answers a question about a transaction that is present: is it
allocated, is there a receipt behind it, what kind of expense was it. A
transaction the feed never delivered leaves no row to inspect, no gap in a
sequence, and no trace of any kind. The only thing that finds it is arithmetic
across a whole period:

```
anchored_opening + transaction_sum  =  computed_closing
anchored_closing - computed_closing =  variance
```

Where that variance is not zero, the difference **is** the missing movement, to
the cent, before anybody knows what it was.

## What shipped

### Three doctypes

| DocType | What one row is |

| **Statement Anchor** | one bank account, one statement period, and whether it ties out |
| **Statement Anchor Line** | one line as the *statement* printed it (child table, optional) |
| **Advisory Agreement** | the terms an investment account is managed under |

`pairing_type`, `plaid_account_id`, `plaid_account_mask`, `plaid_account_type`,

### Two endpoints

```
POST /api/method/erpnext_mcp.bank.push_statement_anchor
POST /api/method/erpnext_mcp.bank.push_account_pairing
```

After this the pipe holds no authoritative data. It parses, it pushes, and if
this site is unreachable it retries on the next sync.

## The four decisions worth arguing about

### 1. The variance cannot be asserted

`computed_closing`, `variance`, `reconciled` and `chain_gap_from_prior` are
read-only fields written by the controller on every save. A payload that arrives
carrying its own variance gets it **recomputed**, not adopted.

This is the whole feature. A pipe that could push its own variance could push a
zero, and a zero variance is indistinguishable from a reconciled account. The
value of a statement anchor is that the number is arithmetic over two inputs
somebody else supplied.

`test_a_pushed_variance_is_recomputed_and_not_believed` is the test, and it is
the only property here that is invisible unless somebody tries to lie.

### 2. `rebuild_anchor_chain` will not rewrite the anchored numbers

It recomputes the closing, the variance, the reconciled flag, the chain-gap
flags and the statement-line matches — every value that is a function of data
already on the record. It leaves `anchored_opening`, `anchored_closing` and
`transaction_sum` alone.

Those three came off a bank statement this app did not read. Rebuilding them
from the transaction feed would replace the independent record with a
restatement of the thing it exists to check, **after which every period ties out
perfectly and the chain proves nothing**. `recompute_transaction_sum=true`
overrides it for accounts whose anchors came from the feed to begin with,
reports the before and after per period, and warns in those words.

### 3. An explanation beats a wider tolerance

The default tolerance is a cent, which is rounding. A managed account whose
quarterly advisory fee is deducted outside the transaction feed is out by
$3,774.81 this quarter and a different number next quarter — so a tolerance wide
enough to swallow this one is wide enough to swallow a genuinely missing
deposit.

`set_anchor_variance_reason` records the sentence instead, and it does **not**
mark the period reconciled. `reconciled` stays arithmetic; the explanation sits
beside it; both are reported and neither overwrites the other.
`list_unreconciled_anchors` still lists an explained period, because a recorded
fact about an account is not a problem and hiding it makes somebody rediscover
it every quarter.

### 4. An empty list is not always a clean result

`list_unmatched_statement_lines` can only answer where a parser has pushed the
statement's own lines. Where none are on file it says so, loudly, instead of
returning `[]`. "Nothing is missing" and "we have nothing to check against" are
opposite answers and they look identical in an empty array.

## Categorization rules, restated and made bulk

`Bank Categorization Rule` grew the match vocabulary a bank pipe already speaks —
`merchant_exact`, `merchant_contains`, `description_regex`,
`plaid_category_matches`, `amount_range`, `combined` — beside the four operators
v0.71.0 shipped. **Nothing was migrated.** A rule that says `contains CHEVRON on
description` and one that says `merchant_contains CHEVRON` are the same rule, and
rewriting sixty of them would change what a site's audit trail says its rules
were.

Three things are worth knowing:

* **Direction and the amount bounds AND onto every match type**, not just onto
  `amount_range` and `combined`. That is what makes `amount_range` a match type
  rather than a modifier, and why a regex-plus-ceiling rule needs no special
  support.
* **The merchant match falls back to the description** where the feed left
  `bank_party_name` empty — which is disproportionately the small local suppliers
  a farm actually buys from. A rule that read only that column would match the
  national chains and miss the co-op.
* **`plaid_category_matches` is a PREFIX match.** `TRANSPORTATION` catches
  `TRANSPORTATION_GAS` today and `TRANSPORTATION_TOLLS` the day the aggregator
  adds it. A rule that had to enumerate leaves would go quietly stale.

`apply_categorization_rules` was quadratic and is not any more: it built a fresh
document and recompiled every regex **inside** the transaction loop. Sixty rules
over five hundred lines was thirty thousand document constructions to answer a
question that depends on sixty rules. The rules are now built once, the compiled
pattern is cached on the controller, and the inner loop is comparisons.

`create_bank_categorization_rules` takes an array. The point is not saving round
trips — it is that a single-rule call can only see the rules that already exist,
so thirty of them get their priorities wrong relative to each other. The batch is
vetted in full before anything is written: a batch produces the book you
described or produces nothing, because half a book categorises a month of
statement on its own and looks like it worked.

`seed_farm_categorization_rules` takes `categories` now. An orchard with no
livestock does not want a Feed rule that will never fire and will sit in
`never_fired` forever, looking like a problem.

## Advisory agreements

An advisory fee is the one recurring cost on a farm's books that arrives
**already deducted**. Nobody approves it, no invoice precedes it, and on a
statement it looks like every other line. The only thing that says whether it is
the right number is an agreement in a drawer.

`get_advisory_agreement_summary` computes what the terms say a period costs on
the assets actually under management — and always names its basis. Where no
portfolio value can be established the fee is **null, not zero**: a fee of zero
and a fee nobody can compute are opposite findings. A bank balance is
deliberately never used as a substitute, because it is a fraction of the
portfolio and a fee computed against it would be wrong and plausible.

Amendment is versioning. `update_advisory_agreement` creates a new record, links
`amended_from`, and marks the old one Superseded. Last quarter's fee was charged
under last quarter's terms, and an in-place edit would leave the site holding a
charge it cannot justify beside a record that says something else. `in_place=true`
corrects a description and refuses to touch a fee, a date or a status;
`terminate=true` ends an agreement without creating a version, because terms that
stopped did not change.

## The push endpoint

Idempotent on `(bank_account, period_start, period_end)`. A pipe retries. A parse
gets re-run. An operator triggers a sync by hand while the scheduled one is still
going. An endpoint that appended would leave the site holding two anchors for
October that disagree, which is the exact failure this release exists to end.

* **A batch tolerates a bad row; a single push does not.** Per-row tolerance is
  right for thirteen months and wrong for one — a single payload that failed and
  came back `200` with `failed_count: 1` is a pipe that believes it succeeded.
* **Statement lines are replaced, not appended.** A re-parse produces the same
  lines again, and doubling them would make every line match a transaction and
  the unmatched count — the entire product — quietly wrong. A push that says
  nothing about lines leaves them alone; `[]` clears them.
* **`variance_reason` is the one field a later push will not overwrite.** It
  lands on an anchor that has none — which is what makes a one-time migration of
  a pipe's own variance tags work — and never over one that does. After
  consolidation the sentence is a person's, and a nightly sync would otherwise
  erase it on the next run.
* **It creates no Bank Accounts.** An auto-created account has no GL account, no
  company anybody chose, and no way to be noticed — and the anchors hanging off
  it would look exactly like reconciliation.
* **The gate is Frappe's own permission**, the same choice `api/gis.py` makes: a
  named user plus `has_permission(..., "write")`, which respects a User
  Permission scoping a credential to one company. `api/guard.py`'s seven checks
  are built for a phone and include a Mobile Access Grant, which is the wrong
  gate for a server-to-server credential.
* **Every call writes an audit row, refusals included.** "Which credential pushed
  the October anchor" is the first question asked when two systems disagree.

## What this release does not do

**It posts nothing.** Not one of the fourteen tools writes a GL Entry, a Journal
Entry, a Payment Entry or an allocation — the same promise v0.71.0 made. An
anchor says whether the books tie out. Making them tie out is a Journal Entry
somebody decided on, with its own switch and its own review.

**It does not delete anything on the pipe side.** The sidecar's tables are
untouched by this release. The deletion is a later decision, after a parallel
period and an operator's sign-off.

**It does not store statement PDFs.** `statement_pdf` is an Attach field for
sites that want to, and it is empty by default. PDFs are source documents; this
app owns the reconciliation truth whether or not it owns the bytes.

## Upgrading

```bash
bench --site <site> migrate
```

That creates the three doctypes and adds the seven Custom Fields to Bank
Account. The pairing fields are also created lazily the first time
`pair_bank_accounts` or `get_account_pairing` runs, so a bench that pulled the
code without migrating still works.

Every new read tool ships **on**; every new write tool ships **off**, as always.
