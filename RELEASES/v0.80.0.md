# v0.80.0 — One desk, three tiers of paper

Sixteen tools, five doctypes, five mobile routes, seventy-one tests. Shipping
documentation for local, domestic and international loads, operated from a single
sales desk.

---

## The problem

Fruit leaves a farm three ways.

A truck to the packing house down the road. A truck across a state line. A reefer
on a vessel. **The fruit is the same fruit.** The paperwork is not: a local
delivery needs a scale ticket, a receipt, an invoice and a grade; an interstate
load picks up federal food-safety and cold-chain records; an export picks up
everything a border asks for, most of which is filed in somebody else's system
before the container is sealed.

The mistake this module exists to prevent is running those three out of three
places. A desk that keeps local deliveries in a spreadsheet, interstate freight
in a folder and exports in a broker's portal is a desk where **the export
paperwork is the only paperwork anybody checks** — because it is the only one
that lives somewhere that looks like paperwork.

Then a domestic load moves without a cold chain record and nobody notices until a
buyer asks for one, by which time the truck arrived three weeks ago and the
record cannot be made honestly. The paperwork that fails is never the paperwork
somebody is worried about.

So: **the tier decides how much paper, not which system.** One `Trade Shipment`,
one checklist built from the destination's own rules, one register of documents.

## The five doctypes

| Doctype | What it is |
| --- | --- |
| `Trade Document Template` | The SHAPE of a kind of paper — schema, source, signature rule, filing system |
| `Destination Document Requirement` | Shipping HERE needs THAT |
| `Trade Shipment` | One load, its route, and its frozen checklist |
| `Trade Shipment Document` | One checklist line |
| `Trade Document` | One piece of paperwork, any of the sixteen types |

### Why it is `Trade Shipment` and not `Shipment`

ERPNext core already owns the name `Shipment` — its parcel-service record — and
DocType names are unique across every installed app. A doctype called `Shipment`
here would not install alongside it. The name is longer and the app installs.

### Why thirteen document types are one doctype

A scale ticket reference, a phytosanitary certificate and an electronic bill of
lading share a lifecycle (drafted → reviewed → approved → sealed), a home (a
shipment), and an evidence requirement (who attested to what, over which
version). They share **almost no fields at all**.

So the lifecycle is columns and the content is `document_data`, because the
alternative is thirteen near-empty doctypes or one table that is ninety per cent
NULL for every row in it. That is the "maximal data science, avoid table sprawl"
call, made explicitly.

## Config, not code — the only way this survives contact with trade

A farm that lands a buyer in a country it has never shipped to before needs
documents it has never issued before, and it needs them **this week**. If that is
a release, the release is the bottleneck and the desk goes back to the broker's
portal.

**Nothing in this app's code names a country.** Adding Vietnam is:

```
create_trade_document_template(...)      # if the paper itself is new
set_destination_requirements(
    destination_tier="International",
    destination_country="Vietnam",
    requirements=["Import Permit Reference", ...])
```

Sixteen templates ship seeded across the three tiers, and **a shipped template is
never overwritten** once an operator has edited it — the same contract the wizard
definitions have, for the same reason. The requirements are seeded more
cautiously still: a rule is written only where none exists for that destination
and template **at all, enabled or disabled**, because an operator who turned a
document off did so on purpose and a seeder that put it back would overrule them
on every upgrade.

### A country's rules ADD to the tier's

The paper a country asks for sits on top of the paper an export always needs,
never instead of it. A lookup that returned only the country's rows would drop
the AES declaration from every shipment to a country somebody had written a rule
for — which is exactly the shipments most likely to need it. Company-scoped rules
compose the same way, and beat unscoped ones for the same template.

## Advisory by default, and the default is the load-bearing part

`update_shipment_status` is the only gate in this module, and it guards one
transition: **Ready to Ship**.

`trade_document_enforcement` on ERPNext MCP Settings **ships off.**

A two-truck operation locked out of its own delivery by a phytosanitary
certificate it will never need turns this module off within a week — and an
operation that has turned the module off gets no warnings either, which is
strictly worse than an advisory gate that reports the gaps and lets the truck go.
Advisory mode returns the **identical** readiness answer.

An operation big enough to want the gate turns it on, per site or per shipment
via the shipment's own `enforcement` field — which is what an operation shipping
mostly local and occasionally to Japan actually needs.

**The override is recorded.** Where enforcement is on, releasing anyway requires
`override_reason`, and it is written to the shipment and surfaced in
`list_shipments` as `released_with_override`. A bypass nobody recorded is a
bypass nobody can review, which is the difference between an advisory control and
no control at all.

### Where the two halves of the FSM live, and why they are split

| | Enforced by | Why |
| --- | --- | --- |
| The status walk | the doctype controller | The order of real events. A shipment is not delivered before it has departed, whatever anybody ticks, and a rule about the world belongs where every writer passes — the Desk included |
| The document gate | `update_shipment_status` | A policy. It is per-site and per-shipment, and overriding it takes a reason — none of which a `validate` can do, because a validate cannot ask the caller why |

A gate in `validate` would also mean an operator could not fix a mis-keyed
shipment in the Desk without first satisfying a customs requirement. That is a
rule that gets turned off within a week.

## Four ways a document that looks done is not

`get_shipment_readiness` names each, and every one has held a container:

1. **It is not approved.** The ordinary case.
2. **It has been voided.** A withdrawn certificate is not a certificate.
3. **It has expired.** A phytosanitary certificate approved in June for a
   September sailing is one a border rejects — and a checklist that counted it
   because its status column said `Approved` would report a shipment ready that
   is not.
4. **It requires an external filing and has no reference back.** This app files
   nothing; an ePhyto nobody lodged in PCIT is a row in a database.

Three and four are the ones a status column cannot see, and they are the reason
readiness is a computation rather than a `COUNT(*) WHERE status='Approved'`.

## This app files nothing, and says so everywhere it could be misread

An ePhyto is lodged in **PCIT**. An EEI is filed in **AES**. An eBL is issued on
a **DCSA** platform. This app records that somebody filed and what reference came
back.

A module that implied it had transmitted a certificate would be the most
dangerous thing in this repository — so any template whose document is finished
somewhere else carries `requires_external_filing`, `approve_trade_document`
returns a `filing_warning` when the reference is still missing, and the document
is reported outstanding however approved it looks.

### The standards are named, not implemented

| Document | Standard the field names follow |
| --- | --- |
| Phytosanitary Certificate (ePhyto) | IPPC ISPM-12 — certificate number, botanical name, additional declaration, treatment schedule, pest declarations |
| Electronic Bill of Lading (eBL) | DCSA data model — shipper, consignee, notify party, vessel, ports, containers |
| AES Export Declaration | AES/EEI 15 CFR 30 — ITN, USPPI, Schedule B, ECCN, licence code, port of export |
| Certificate of Origin | WCO origin criteria — producer, harmonized code, origin criterion |
| Bill of Lading | DCSA data model |
| FSMA Food Safety Record | FSMA 204 Subpart S shipping event |
| USDA Grade Certificate | USDA AMS 7 CFR 51 |

This is so a broker's schema and this app's can be reconciled **by reading**,
rather than by somebody guessing whether `consignee` here means the same as
`consignee` there. It is the standards' *names*. It is not UN/EDIFACT, and there
is no transport in this release.

## The seal

`seal_trade_document` fingerprints an approved document and closes it to editing.

Until a document is sealed, "this is the certificate we presented" is an
assertion about a record anybody could have edited since. After it, the claim is
checkable. **A sealed document refuses content edits** — a seal over a row that
can still change is a timestamp wearing a seal's clothes. Correcting one means
voiding it and issuing a replacement, which is also what happens to a real
certificate that is withdrawn.

Three properties worth stating:

- **The hash covers an allow-list**, stored beside it. Not "everything except a
  deny-list": a column added in a later version would silently join an
  all-columns hash and make every previously sealed document fail verification —
  an integrity check that fires on documents nobody touched is one nobody reads.
- **It recomputes on every read.** `get_trade_document` re-derives the hash
  rather than trusting the column, so a row changed underneath its seal reports
  the seal as **broken** instead of looking intact. The Desk is another door.
- **Only an Approved document can be sealed.** Sealing an unapproved one would
  certify that nobody had checked it.

`generate_shipment_packet` bundles a shipment's documents and hashes the bundle
over its members' hashes. It **refuses unsealed documents by default** — the same
argument `generate_audit_packet` makes about an open corrective action — and
`allow_unsealed=true` names them at the front rather than dropping them, because
a bundle that quietly omitted them would read as a shipment with less paperwork
than it has. A broken seal inside a packet is reported, not bundled quietly.

## Two things reported and never applied

**The checklist is a snapshot.** It is built once, at creation, and is never
silently rebuilt: a destination's rules changing in March must not quietly add a
requirement to a February shipment that has already sailed.
`get_shipment_readiness` reports `requirement_drift` instead — what the
destination asks for *today* that this shipment's frozen checklist does not have.
It never blocks.

**Removed requirements are disabled, not deleted.** A shipment made under a rule
is audited against what was asked for *then*, and a deleted rule cannot answer
"why did we need that".

## Approving is an attestation

`approve_trade_document` requires one of **System Manager, Farm Manager,
Compliance Officer, Sales Manager, Accounts Manager**. A commercial invoice is a
customs declaration and a phytosanitary certificate is a claim about a pest;
neither is anonymous, and neither is a picker's to sign off.

Where the template sets `requires_signature`, approval writes a **Signing
Evidence** row over the document's fingerprint — the same evidence chain a Form
I-9 signature uses. The fingerprint is taken **before** the approval columns are
written, which is the only moment that answers the question it exists to answer:
what did this person see when they certified it.

`update_trade_document` will not move a document to Approved or Sealed. Those are
acts with a principal behind them.

**Unfilled declared fields are reported, not refused.** A template's schema is
this app's reading of the document, and the person holding the actual certificate
is a better authority on what it needs than a JSON list is.

## The five mobile routes, and what is deliberately not among them

| Route | What it is for |
| --- | --- |
| `list_shipments` | What is going out, scoped to the caller's entities |
| `get_shipment` | One load in full, in the caller's language |
| `get_shipment_readiness` | The question somebody standing next to a truck actually has |
| `list_trade_documents` | The paperwork on a load |
| `confirm_shipment_movement` | A driver says "I have left" / "I have arrived" |

`confirm_shipment_movement` is named for what a phone does rather than after the
tool it delegates to, and the two are deliberately not the same shape.
`update_shipment_status` can release a shipment to Ready to Ship — the module's
one gate — can cancel one, and takes an `override_reason` that walks past an
incomplete checklist. **None of the three is forwarded, and none is in the
wrapper's signature**, so none can be bound from a request body.

A release is an assertion that the paperwork is in order, made by somebody with a
trade role at a desk. An account that could make it from a phone in a yard would
make the gate worth nothing. Same argument that keeps `cancel=true` off
`reject_farm_task`.

**`approve_trade_document` and `seal_trade_document` have no route at all.**

## Bilingual

Every template label and description carries `_en` and `_es`, and the reads
resolve them against the caller's `Employee.preferred_language`. A missing
translation **falls back to English and is listed** in `untranslated` — the same
contract `get_wizard_definition` has. Silently serving English means nobody finds
out until somebody misreads a document type; refusing to serve it locks the desk
out over a missing string.

The seeded templates ship with Spanish throughout.

Seven reads default **on**, nine writes default **off**, as every write in this
app does.

`Trade Document Template` joins the short list of doctypes this app does not
scope by company: a template is the SHAPE of a document and a shape belongs to no
entity — and the docname IS the key a requirement points at, so a per-company
template would mean either the same name existing several times or a name every
rule would have to spell. Per-company narrowing exists one layer up, on
`Destination Document Requirement.company`, which IS scoped by Frappe.

## Testing

Seventy-one new tests in `tests_standalone/test_trade_documents.py`, organised
around seven claims, plus nine mobile-surface tests in `test_api_mobile.py`.

Two real bugs were found by writing them:

1. `TradeDocumentTemplate.validate` tested a Check field with bare Python
   truthiness. A Check field arrives as the string `"0"` often enough, and
   `bool("0")` is `True` — so every template with the box *unticked* was refused
   at save. Now `cint`. This is the same trap `settings.as_bool` exists for, one
   layer down.
2. `update_trade_document` refused **every** edit to a sealed document, including
   the `Void` that the seal's own refusal message tells the caller to use. The
   escape hatch was named and unreachable. Voiding now gets through; everything
   else still does not.
