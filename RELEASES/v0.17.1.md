# v0.17.1 — the two halves of Sprint 9 are joined

**Released:** 2026-08-01 · **Previous:** v0.17.0

Sprint 9 ran two tracks in parallel and they landed incompatible contracts. The
backend worked. The app worked. They could not talk to each other, and the app
reported it to a worker as *"That task no longer exists — someone may have taken
it."*

This release is the join, plus the one compliance rule the app found a genuine
hole in. **No new capability is added.** Everything here is either a bridge to
something v0.17.0 already shipped, or a refusal.

---

## The two bugs

### 1. The login QR was missing one key, so enrolment was impossible

`generate_mobile_login_qr` emitted a payload with no `type` field.
`FarmOpsKit`'s `LoginQRParser` checks `type == "farm_ops_login"` as its **first**
test and refuses anything else by name, so every scan failed with *"That's a
different kind of QR code, not a Farm Ops login."*

The app's check is not pedantry. FarmCore and BucketLog issue their own
onboarding codes (`farm_app_nostr_link`) onto the same phones, and a scanner that
accepted any well-formed JSON would let two apps cross-sign each other's
credentials.

**Fixed** — `mobile_login_payload` now emits `"type": "farm_ops_login"` first, as
a module constant rather than an argument: a payload whose type a caller could
choose is a payload that could claim to be another app's.

### 2. Every call after enrolment was a 404, because the two tracks built
different transports

| | Wave A (backend) | Wave B (iOS) |
|---|---|---|
| Path | `/api/method/erpnext_mcp.mcp.handle` | `/api/method/erpnext_mcp.api.mobile.<method>` |
| Envelope | JSON-RPC 2.0 | plain Frappe whitelisted method |
| Entry | `X-MCP-Token` + CIDR allowlist | `Authorization: token <key>:<secret>` |
| Gating | per-tool `allow_*` switch | none — didn't exist yet |

Both are defensible. Neither is the other. iOS flagged the risk in its own
`API_CONTRACT.md` before it shipped.

**Fixed** — a new `erpnext_mcp/api/` package publishes exactly the eleven methods
`MobileAPI.swift` names, as thin guarded wrappers over the tools that already
existed. See **The new attack surface** below, which is the part worth your time.

## The new attack surface, and the seven things standing in it

**This is the honest headline of the release.** `security.authorize()` — master
switch, shared token, CIDR allowlist — is called by `mcp.handle`. A
`@frappe.whitelist()` method reached directly never passes through it. So these
eleven paths have **none** of the MCP endpoint's gates, by construction:

- no `X-MCP-Token` (the phone has never had one, and a shared secret on forty
  devices is a secret in name only),
- no CIDR allowlist (the point is a phone on LTE, outside every RFC1918 range the
  default list contains),
- no per-tool `allow_*` switch (those govern what the *AI* may do; a field worker
  is a different principal and gets a different gate).

Pretending otherwise would have been the dangerous move. The gate is rebuilt in
`erpnext_mcp/api/guard.py` and runs on **every call**:

1. **Global kill switch** — `farm_ops_mobile_enabled`, new Check field on ERPNext
   MCP Settings, **defaults ON**. Also readable from `site_config.json`; either
   source saying off means off. Answers **503**, not 401 — see below.
2. **A named human** — Guest is refused before a row is read.
3. **Role gate** — `Field Worker`, `Farm Worker`, `Foreman` or `Farm Manager`.
   Family Member and Advisor are real logins on this site and neither belongs on
   a dispatch board. Compliance Officer is deliberately absent: these eleven
   methods are field work.
4. **Enrolment gate** — an **Active Mobile Access Grant**. *This is what keeps
   your own account out.* Administrator holds every role there is, so the role
   gate alone would let the operator's login drive the field API by accident.
   You cannot call these endpoints until you enrol yourself on purpose, and
   `revoke_mobile_user` closes the door on the very next call.
5. **Rate limit** — per user, per method, per minute. Reads 60, writes 10,
   completion 20, upload chunks 120. Answers **429**.
6. **Entity scoping** — every company argument and every returned row checked
   against the caller's own Company User Permissions. **An account with no
   entities is refused, not shown everything** — this deliberately inverts
   Frappe's rule, where no User Permission means unrestricted. On an endpoint
   reachable from the internet, that default is exactly backwards.
7. **Audit + secret strip** — one MCP Action Log row per call including the
   refused ones, and every credential-shaped key removed from every response at
   any depth.

**Why 503 and 429 rather than 401.** `FarmOpsKit` treats 401 as *"credential
dead, sign out and re-scan"* and anything else as *"offline, keep working into
the queue"*. A kill switch that answered 401 would sign forty phones out and lose
every queued completion sitting on them.

### The surface is a closed list of eleven, and cannot grow by accident

There is **no dispatcher** in the package — no `call(tool_name, args)`, no
registry lookup. A method exists as a function or its path 404s, so the whole
reachable surface is eleven `@frappe.whitelist()` lines you can audit by reading
them. `create_journal_entry`, `convey_parcel`, `import_chart_of_accounts`,
`disable_je_gate` and the other ~195 tools are not reachable from a phone at any
path. A test asserts this by enumerating what the modules actually export.

### Arguments that are deliberately unreachable

Not passing an argument through is as much the design as the wrappers are. Frappe
drops body keys a whitelisted method does not declare, so an argument absent from
a signature is one no phone can send:

| Argument | Belongs to | What it would have allowed |
|---|---|---|
| `cancel` | `reject_farm_task` | a worker handing work back could delete it instead |
| `record_data` | `complete_farm_task` | the phone composing arbitrary fields on a compliance record |
| `worker_id` | every dispatch tool | filing somebody else's completion |
| `attach_to_doctype` / `attach_to_name` | `commit_staged_file` | hanging a file off any document on the site |
| `governance_document` | `commit_staged_file` | writing into the governance archive |
| `is_private` | `commit_staged_file` | a public signature capture |

Uploads additionally get an **extension allowlist** (`.jpg .jpeg .png .heic
.heif .webp .pdf` — no `.html`, no `.svg`, both of which execute script when
served) and filenames are reduced to a basename. The general path only checks
extensions when there *is* an attachment target, and these commits deliberately
have none.

### Three judgement calls you may want to overrule

- **Audit rows go to MCP Action Log, not Audit Event.** The brief said Audit
  Event; on this site that doctype is a *compliance* record — a GlobalGAP
  walk-through with an auditor, findings and corrective actions. Forty phones
  polling a task list would bury a real auditor's register under tens of
  thousands of API rows. MCP Action Log already has the exact shape (timestamp,
  actor, caller IP, arguments, status, summary) and already redacts secrets.
  Mobile rows are prefixed `mobile:` so they filter apart from the AI's.
- **The IP recorded is `security.caller_ip()`, not `frappe.local.request_ip`.**
  Frappe's is the *leftmost* `X-Forwarded-For` entry, which is whatever the
  client claimed. Ours is the rightmost, which the nearest proxy appended and a
  client cannot forge. An audit log holding an attacker's chosen IP is worse than
  one holding none, because it looks like evidence.
- **The role list says `Field Worker`, not `Farm Worker`.** This app has always
  defined six roles and the phone-only one is `Field Worker`; no site has a
  `Farm Worker`. Both names are accepted so neither spelling is a trap, but every
  enrolled worker on your site holds `Field Worker`.

## `clean_pass` — the spec contradiction, resolved

Sprint 8's rule: a compliance record's state is a function of its findings text.
Blank means Recorded, text means Corrective Action Required. That rule is right.

It breaks the moment an evidence contract **requires** findings text, as
MC-Cabin-01's habitability inspection does. Blank is then not a submittable
state, so the worker must type something, so **every completion of that task
would open a corrective action against a cabin that is fine**.

The app now asks outright ("Clean pass" / "Issues found") and sends the answer.
The server treats the answer as authoritative and does **not** re-derive intent
by parsing the text — a worker typing the literal words *"clean pass"* into a
mandatory field must not trip a corrective action, and no amount of
string-matching is a sound way to avoid that.

- `clean_pass=true` satisfies a mandatory `findings_text`, and the produced
  record's findings field is left **empty** — that is how `records.py` spells
  "nothing was wrong", and putting the attestation *in* that field would flip the
  cabin straight to Corrective Action Required. `"No findings reported by
  inspector."` goes in the record's **notes**, along with whatever the worker
  wrote.
- `clean_pass=false` with an empty `findings_text` is **refused**. "Issues found"
  with no issue named opens a corrective action that names no fault, which is the
  one thing an auditor cannot act on.
- **Absent is a third state, not a synonym for false.** Nobody was asked, and the
  original blank-means-clean rule applies exactly as before.

The worker's own words always survive on the Farm Task Assignment. That is the
evidence, and editing evidence is not the server's to do.

## Fields iOS decodes that the backend was not emitting

Found by reading `FarmOpsKit/Sources/FarmOpsKit/Models/*.swift` against what the
tools return. All closed on the **backend**, so no new iOS build is needed:

| Field | Model | Was | Now |
|---|---|---|---|
| `location_type` | `FarmTask` | only `location_doctype` | both emitted |
| `source_alert_explanation` | `FarmTask` | absent | the Compliance Alert's own `alert_message`, verbatim |
| `assignment`, `claimed_at`, `started_at` | `FarmTask` | on the assignment only | merged onto the task |
| `latitude` / `longitude` | `FarmTask` | absent | emitted for `Field` / `Irrigation Zone` (boundary centroid); **omitted**, not zeroed, where the site has none — 0,0 is a real place in the Gulf of Guinea |
| `roles` | `UserContext` | `mobile_roles` only | every role the account holds |
| `companies` | `UserContext` | list of strings | `[{name, abbr}]` |
| `default_company` | `UserContext` | `preferred_company` | both |
| `skills` | `UserContext` | absent | read from `Employee` where the site has such a field, else `[]` |
| `urgency` | `ComplianceAlertSummary` | `severity` (3 levels) | mapped — Critical→Critical, Warning→**High**, Info→Normal |
| `regulation` | `ComplianceAlertSummary` | absent | the alert rule's `framework` citation |
| `linked_task` | `ComplianceAlertSummary` | absent | newest Farm Task raised from the alert |
| `created_record_name`, `dismissed_alert`, `corrective_action_opened` | `CompletionResult` | `produced_record*` | mapped |

`source_alert_explanation` matters more than its row suggests: the app renders it
verbatim under "Why this task exists" and **hides the card without it**, and its
contract says an inspection with no stated reason is worse than none.

**`dismissed_alert` is not a claim that an alert was dismissed.** Nothing in this
app dismisses one directly — the record moves the register forward and the next
sweep notices the condition is no longer true. The field names the alert the work
*answered*, which is what the phone means when it says "cleared".

## One thing NOT carried onto the record

The app computes a SHA-256 of every evidence file at capture and sends it. It is
now **verified server-side** at `finalize_staged_file` — the commit is refused on
mismatch and the staged pieces are kept so the app can re-send one slice rather
than the whole file — and the verification is what the audit row records.

It is **not stored on the Farm Task Evidence row**, because that child doctype
has no hash column and adding one is a schema change to a compliance record,
which is not a hotfix. It is deliberately *not* stuffed into `caption`. If the
hash should live on the record itself, that is a one-field migration and a
follow-up.

# The cleanup sweep

Ten items were audited alongside the mobile work. **Six landed, four needed no
code** — and two of those four were already done and the brief was out of date.
Each landed item is its own commit so the diffs review separately.

## Landed

### 1. Entity scoping for `Housing Assignment` and `Family` — the real hole

`create_mobile_user` promises that one User Permission on Company "restricts
EVERY document that links to a Company, across every doctype". True, and the
load-bearing clause is *"that links to a Company"*.

Of the thirty-odd doctypes this app ships, **exactly two do not**:

- **`Housing Assignment`** — who sleeps in which cabin. It links to Housing Unit
  and Parcel, both of which carry `owning_entity`, but not to Company itself.
  `roles.py` READ-grants it to Field Worker, Foreman, Compliance Officer and
  Family Member and FULL-grants it to Farm Manager. **So a field worker scoped
  to one entity could list every camp bed assignment on the site** — names,
  cabins, wage-deduction status — across every other entity. Labour-camp
  personnel data, and the exact failure the v0.17.0 scoping release existed to
  prevent.
- **`Family`** — the family-office member register, READ-granted to Family
  Member, so one family's members could read another's.

Closed with `permission_query_conditions` + `has_permission` hooks in a new
`erpnext_mcp/permissions.py`, scoping each through the link it does have.

**Two hook keys that were forbidden are now allowed, under a narrower rule.**
`test_hooks.py` banned both outright on the grounds that "this app changes
nobody's visibility". The invariant actually worth keeping is about *other
people's* doctypes; the ban was a proxy and the proxy was wrong for a doctype
this app ships. It is replaced by a rule asserted directly: **every doctype
named in these hooks must be one this app created.**

Both handlers **fail open**. A query-conditions hook that raises does not fail
one query — it fails every list view of that doctype for everybody, forever,
including the Desk page you would open to fix it. A user with no Company User
Permission likewise gets no condition, which is Frappe's rule and what keeps
Administrator working. That is the *opposite* of `guard.accessible_companies`,
which refuses such a caller, and the difference is deliberate: the mobile API is
one endpoint on the open internet where fail-closed is affordable; this hook
applies to every reader forever.

*Auditing note:* the first pass of this audit grepped for a field **named**
`company` and would have wrongly flagged `Mobile Access Grant` too. It carries
`preferred_company`, a Link to Company, so Frappe scopes it like everything
else. What matters is the field's **type**, not its name — there is now a test
enumerating every doctype and failing if a third unscoped one ever appears.

### 2. The compliance sweep now runs hourly, not nightly

The sweep is what makes an alert **go away**: a completion writes a compliance
record, the register moves forward, and the next sweep notices the condition has
stopped being true. Nightly meant a worker who walked a cabin at eight in the
morning spent the rest of the day looking at a phone asking them to walk it. That
latency stopped being cosmetic the moment v0.17.1 put the calendar in front of
forty people who cannot see the Desk.

Eleven rules over a farm's registers is a cheap pass — about a second a day of
one worker. Safe at any cadence because the sweep is a full reconciliation, not
an increment; there is now a test for that property, because it is what makes the
cadence a tuning decision rather than a correctness one.

### 3. A weekly Journal Entry drift watch — **it reports, it never repairs**

ACC-JV-2026-00073's defining property was that nothing complained for a week.
v0.14.0 shipped the scan and the repair; neither fixes that. This is the smoke
alarm.

`repair_drifted_je_attributions` is **deliberately not called** from the
schedule. Repairing drift rewrites GL rows on submitted accounting documents, and
doing that on a timer with nobody watching is the single worst thing this app
could be talked into — a repair that got it wrong would be indistinguishable from
the bug it was fixing, applied to a year of ledger before anybody read the email.
A test asserts this against the module *source*, because the claim is that no
code path exists at all.

It scans a trailing 400 days and **says which dates it covered**, and says loudly
when it hit the entry cap: a job that silently truncated and reported a clean
bill of health would be worse than not running, because it produces a record
saying somebody checked.

Recipients come from the new **Drift Report Recipients** setting, or — empty,
which is a working configuration — every enabled System Manager. No outgoing mail
account falls back to the Error Log, because losing the one message that says the
ledger disagrees with itself would reproduce the original bug exactly.

### 4. Idle Farm Ops credentials are revoked after 30 days

**This reverses a decision v0.17.0 wrote down**, and the reversal is recorded
rather than quietly made. v0.17.0 said this app would install no such job
"because it would rewrite another app's User records on a timer with nobody
watching".

What changed is the threat. A key that only travelled to a laptop on the LAN
could be left to a human to review; v0.17.1 put forty of them in forty pockets on
the open internet, and a phone left on a truck seat and never mentioned is the
ordinary case. **A credential that stops working by itself is the only control
that does not depend on somebody admitting to the loss.** Every clause of the old
objection is answered: it rewrites only the two credential fields, only on
accounts this app created and minted a key for, and every revocation writes an
audit row and the run emails a summary — so "nobody watching" is no longer true.

It needed a clock that did not exist. **Mobile Access Grant gains `last_seen_on`**,
stamped by the mobile API gate **at most once a day** — a date comparison before
the write, so forty phones polling cost forty UPDATEs a day rather than forty an
hour. It works on *idleness*, not on the review date.

Four things it does not do:

- It does **not** disable the account, remove roles, or touch entity access. This
  is "your phone went quiet", not "you no longer work here". The worker is one QR
  away from working again.
- It does **not** touch a grant marked **Exempt From Idle Sweep** (new checkbox) —
  a winter caretaker's phone is legitimately quiet for months.
- It does **not** touch a non-Active grant or one with no live credential.
- It does **not** age a grant it has no clock for. Guessing an age and acting on
  the guess is the shape of mistake that ends with somebody locked out
  mid-harvest; those are reported instead.

Window is **Revoke Idle Mobile Credentials After (Days)**, ships at 30, and 0
switches it off. An unparseable value falls back to 30 rather than 0 — reading a
broken setting as "off" would silently disable a security control.

### 5. `onboard_employee` — one call for a new hire

Employee record, paperwork, scoped login with a credential, and optionally the
two first-day tasks (safety training, camp orientation — both demand a signature).

**The paperwork goes ON the Employee record as private attachments, never in the
governance archive.** That archive holds trust instruments, operating agreements
and SOPs — the documents describing the *business* — and an auditor, an advisor
and a family member browse it. Filing forty people's I-9s there would look tidy
and be a disclosure. Every document goes through
`attach_file_to_document(doctype="Employee")` with `is_private` hardcoded, and a
test asserts against the *parsed* module that no path to the archive exists.

It reuses an existing Employee rather than making a second one, reports every
step by name so a partial run says which part ran, and does **not** repeat the
credential in its result — `create_mobile_user` returns a secret exactly once,
and echoing it into a summary-shaped payload is how it ends up pasted somewhere.

Mutating, ships **OFF**. Catalogue is now 207 tools.

### 6. iOS response-shape audit

## Deferred to v0.18.0

## What you need to do — in this order

### 1. Tailscale Funnel — audit it yourself, this release does not touch it

Two possibilities, and **check which one you are on before doing anything**:

```sh
tailscale serve status --json
```

- **Whole-port funnel** (`"Handlers": {"/": {"Proxy": "http://127.0.0.1:5300"}}`,
  which is the usual shape). **Nothing to add — the new paths are already
  reachable.** The thing to notice is the other half of that sentence: so is
  `/app`, so is `/api/method/*` for every whitelisted method in every installed
  app. That was already true before this release; it is worth re-reading now that
  a phone depends on it.
- **Path-scoped funnel.** Then the two prefixes to add are:

```
/api/method/erpnext_mcp.api.mobile.
/api/method/erpnext_mcp.api.files.
```

Nine methods under the first, two under the second — the full list is in
`erpnext_mcp/api/mobile.py` and `erpnext_mcp/api/files.py`, one
`@frappe.whitelist()` per line. **Do not** funnel `/api/method/` as a whole
prefix to save typing; that publishes every whitelisted method of every installed
app.

`/api/method/erpnext_mcp.mcp.handle` stays exposed as before — the AI still uses it.

### 2. Push, then build — in that order, the Dockerfile depends on it

`fafo-umbrel-store/fafo-erpnext/build/Dockerfile` pulls erpnext_mcp from GitHub
`main` and cache-busts on the **pushed** commit. A local-only commit leaves the
layer cached and you will build the old code and not be told.

```sh
cd "~/Desktop/Development Comms Folder/erpnext_mcp"
git push origin main
```

```sh
cd "~/Desktop/Development Comms Folder/fafo-umbrel-store/fafo-erpnext/build"

docker build \
  --build-arg ERPNEXT_MCP_VERSION=0.17.1 \
  --no-cache \
  -t polehntim/erpnext-umbrel:15 \
  .

docker push polehntim/erpnext-umbrel:15
```

> **Check the platform flag against what your Umbrel actually runs** — add
> `--platform linux/amd64` or `linux/arm64` to the build. No recorded build
> command in the store repo pins one, so this release note does not guess.


### 4. Re-issue one QR and scan it

The v0.17.0 QRs in circulation have no `type` and the app still refuses them.

```
generate_mobile_login_qr(user="<worker>@fafo.farm")
```

`rotate_token` defaults true, so any phone already enrolled on that account must
re-scan.

### 5. Verify from a phone, off the LAN

Sign in, pull to refresh, open a task. If the "Why this task exists" card is
there, `source_alert_explanation` is landing. Then complete one clean pass on a
task whose contract requires findings text and confirm the Housing Inspection
comes out **Recorded**, not Corrective Action Required.

### The one-flip shutdown, if anything goes wrong

ERPNext MCP Settings → untick **Farm Ops Mobile API Enabled**. Or, without the
Desk:

```sh
docker exec -u frappe fafo-erpnext_server_1 \
  bench --site frontend set-config farm_ops_mobile_enabled 0
```

Takes effect on the next request. Every phone gets a 503 and keeps its queued
work; nothing is signed out. The MCP endpoint the AI uses is unaffected — they
are separate switches on purpose.
