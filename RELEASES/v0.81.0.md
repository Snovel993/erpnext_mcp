# v0.81.0 — the control that can be switched off

IPO Readiness, Phases 4 to 6: the governance domain. Seven doctypes,
twenty-nine tools, five control points. Every one of them is bypassable, and
that is the design rather than a concession.

---

## The one idea

A control that can only refuse gets switched off in its first busy week. A
control that can only report is one an auditor discounts. So every control here
runs at one of two strictnesses, through one code path:

```
                 evaluates   reaches a finding   files the alert   lets it through
ADVISORY            yes            yes                 yes               yes
ENFORCED            yes            yes                 yes               no
```

Read the first three columns again. Nothing differs. An operation that spends a
season in Advisory ends it holding **exactly the register of findings it would
hold had it been enforcing** — which is what turns switching enforcement on from
a gamble into a decision somebody makes having already read the list of what it
would have stopped.

Everything ships Advisory. Not out of timidity: a four-person farm that cannot
book a fuel invoice because nobody has been named an approver does not conclude
that its controls need configuring. It concludes the app is in the way, and
turns the module off — and a module that is off reports nothing at all, which is
strictly worse than an advisory control that names the gap and lets the truck
go.

The switch is a `Compliance Rule` row: same register, same versioning, same
approval trail as every rule since v0.22.0. `update_compliance_rule` flips it,
and flipping it version-copies the rule, so the date enforcement began is on the
record.

## Phase 4 — related parties, and the question the ledger cannot answer

`Related Party` has been the governance register since v0.30.0: who is related
to this company, in what capacity, since when. It answers a question about
*state*. Three questions follow from it that no register can answer, and they
are what this phase adds:

| question | tool |
|---|---|
| which transactions were with those parties | `get_related_party_transactions` |
| was each one priced at arm's length, on paper | `flag_related_party_transaction` |
| what does the schedule say at year end | `generate_related_party_disclosure` |

### The match is never a guess

A payment becomes a related-party transaction by the register row's `supplier`
**link** — not by a string comparison. "T. Polehn Trucking LLC" and "Polehn
Trucking" are the same vendor to a person and different strings to a database,
and a disclosure schedule that silently guessed which is which is worse than one
that admits what it could not resolve, because somebody would file it.

So a name match is offered as a clearly labelled second signal (`match: "name"`),
never as the primary one, and every counterparty that resolved to nothing comes
back in `unmatched_parties` with its total. The commonest way a related-party
schedule is wrong is not a mispriced dealing — it is a relationship nobody wrote
down, and the report says so out loud.

### Transfer Pricing Documentation

The arm's-length case, written before anybody asks for it: the price, the
reference it was tested against, and the sentence explaining why the two agree.
`market_rate_reference` is required, because a justification with no reference
behind it is an opinion.

Three states, and the distinctions earn their keep:

- **Draft covers nothing.** A started-but-unfinished memo is a *different
  finding* from no memo at all — one is a morning's work, the other a season's,
  and the control says which.
- **Complete demands the content.** Promoting a memo to Complete with no
  justification in it is refused. Otherwise the control would be satisfied by the
  act of claiming to have done the work, which is the one failure mode a
  documentation control cannot survive.
- **An amount far over the memo is its own finding.** A memo written for $12,000
  of hauling does not document $140,000 of it. Ten per cent tolerance, because a
  memo written for a season is written in advance and the season does not land on
  the number.

`covers_row()` is the single definition of "documented" on the site. The gate,
the register and the year-end schedule all call it, so none of them can grow its
own opinion — the failure that matters most being an operator told they are
covered by one tool and refused by another.

### The period is the unit

One memo covering a season of hauling is how the work is actually done. A memo
per invoice is how a control gets abandoned in week two.

## Phase 5 — the three ITGCs

Access, change, operations. The same three at a four-person farm as at a listed
company; only the evidence is thinner.

### Access is computed and stored nowhere

`generate_access_control_report` reads User, Has Role and the permission tables
at the moment it is called, says when it read them, and **stores nothing**. A
permissions snapshot in a table is wrong the moment somebody adds a role, and a
stale one is worse than none because it is the document an operator hands an
auditor while believing it.

What *is* stored is that a review happened — a `Change Management Log` row. The
review is an event; the access list is a state.

Custom DocPerm shadows DocPerm rather than adding to it, which is Frappe's own
rule and a merged report would show permissions the site does not grant.
`last_login` is read through `compat.existing_fields`, and where the column is
absent the report says so — "absent" and "nobody has logged in" are the same
empty field and opposite sentences.

### Change management, and the hook this app does not install

`hooks.py` opens with a promise: no `doc_events`, no overrides, no field added to
a doctype this app did not create, so that removing the app gives a site back
exactly as it was. Hanging a hook on every Custom DocPerm write would break that
promise for every site, including the ones that never look at this module.

So the change log is populated from **this app's own dispatcher path** instead.
Those rows carry `source = MCP Tool` and a link to the MCP Action Log row for the
call — the ones that could not have been curated after the fact. Everything else
is `Manual`, and `get_change_management_report` **reports the split rather than
hiding it**, because "how much of your change log is self-attested" is the first
question worth asking about a change log.

One hard rule, enforced in the controller as well as the tool: **an approver who
is the person who made the change is not an approver.** A farm where one person
genuinely does both records it honestly — `Not Required`, with the compensating
control in the notes. A documented exception is defensible; a self-approval is a
finding. `Not Required` is a decision and is counted as one; a change whose
approval nobody can find is not, and the two must never look alike in a sample of
five.

### A green job log is not a verification

`Backup Record` holds the job **and** the test restore, because an unverified
backup is a belief. The failure it exists to prevent is discovered exactly once,
at the worst possible moment, and the sentence is always the same: the job had
been green for months and the restore did not work.

- `Not Tested` is the default and is **not** a failure — it is the honest state
  of most backups most of the time. It is also what the control counts.
- `Partial` does not verify. Recovering some of the data is a finding with a
  silver lining.
- A `Fail` is the most valuable row in the table: found on a day somebody chose
  rather than a day chosen for them.
- An undated verification is refused. It could not be counted by any window, so
  it would either be ignored — reporting an operation that did the work as having
  not — or counted forever, which is worse.

RTO stops being a promise and becomes a measurement: `restore_duration_minutes`
against `rto_hours` is the difference between the number somebody committed to
and the number the system actually did.

## Phase 6 — reporting and disclosure

Four objects, and the distinctions between them are the design:

```
REPORTING TEMPLATE     which SECTIONS a report has, and where each is filled from
MD&A DATA FEED         the numbers a management discussion is written FROM
SEGMENT REPORT         the same numbers cut by the parts of the business
DISCLOSURE CHECKLIST   which DISCLOSURES the filing must make, and who decided
```

A section and a disclosure are deliberately not one table. "Results of
Operations" is a section that may carry four disclosures or none; folding them
together would mean either a report with sixty headings, or a disclosure that
could exist only where somebody had already written a section for it — which is
precisely how a disclosure gets omitted.

### Nothing here files anything

Every generator returns a working paper. The skeleton arrives with its headings,
the tool behind each, and the figures where this site could produce them — and
**no prose, ever**. A management discussion that arrived pre-written is the one
nobody reads before it is filed.

### A feed is honest about its holes

`generate_mda_data_feed` attempts every source and names every failure in
`unavailable`, with its reason. A generator that raised on its first missing
input is a tool nobody on a farm mid-setup could ever run, and would therefore
never be run at all. A feed that is honest about its holes is the useful thing;
one that pretends to completeness is the dangerous one.

### Segments: applied and shown, not decided

ASC 280's quantitative test — ten per cent of combined revenue or of combined
profit — is applied per cost centre with its working shown, plus the 75 %
coverage check. What it does **not** do is return a verdict: whether the orchard
and the packing line are genuinely different operating segments is a judgement
about how the business is managed and how the chief operating decision maker
reviews it. No query can make that call and this tool does not pretend to.

Postings with no cost centre belong to no segment and are reported separately —
which is why the segments can sum to less than the company, and why a large
number there means the segment cut is describing part of the business.

### Not Applicable is a decision; Outstanding is not

The whole value of a checklist is that somebody decided about every line. "We
have no reportable segments" is a decision; an empty row is an omission. So
`Not Applicable` settles an item and **requires a reason** — the reason *is* the
disclosure — while `In Progress` does not settle it, because work started is not
a decision reached.

The completeness control fires at the moment somebody calls the filing done,
because after that the checklist is a historical document.

## Bilingual, where it applies

Section headings and disclosure items carry `label_es`; the three shipped
templates ship with theirs. Where a translation is missing the English is served
and the gap comes back in `untranslated` — the posture `list_wizard_definitions`
has taken since v0.79.0, for the same reason: silently serving English means
nobody finds out until somebody who needed the Spanish did not get it.

The ledger-facing records — transfer pricing memos, change logs, backup records —
are not translated, and that is a decision rather than an omission. They are read
by accountants and auditors in the language of the filing. Translating half of a
financial statement would be worse than translating none of it.

## The five control points

| control point | refuses, when enforced |
|---|---|
| `related_party_transfer_pricing` | booking a related-party transaction with no documentation covering it |
| `access_review` | granting access when the last review is older than the review period |
| `change_approval` | recording a system change with no approver, or with its own author as approver |
| `backup_verification` | declaring recovery readiness with no verified restore in the window |
| `disclosure_completeness` | marking a filing complete with required disclosures outstanding |

Each is seeded as a Compliance Rule in Advisory mode, enabled, approved by
Administrator and attributed to System — the same provenance every seeded rule
has carried since v0.22.0. A gate is never swept: it is consulted at the moment
somebody tries to do the thing, before anything is written.

## Migration

`bench --site <site> migrate`. Seven new doctypes; three reporting templates
seeded per company; five compliance rules seeded in Advisory.

Nothing is overwritten. A template an operator has reworded, reordered or
disabled stays exactly as they left it across every future migrate — the check is
"does this docname exist", made before anything is written. That is the whole
difference between a seeder and a fixture, and it is why the word `fixtures`
appears nowhere in this app.

No existing tool changes behaviour. No field is added to any doctype this app did
not create. An operator who never enables a switch in this release sees no
difference at all.
