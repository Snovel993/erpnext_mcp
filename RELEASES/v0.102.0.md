# v0.102.0 — somewhere to stand while you enrol somebody

Item 20. No new tool, no new doctype, no new column. One Frappe Page, four
whitelisted methods that wrap two tools this app has shipped since v0.17.0, and
two lines added to a third.

---

## The one idea

`create_mobile_user` makes the account, assigns the role, writes a User
Permission per entity and mints the credential. `generate_mobile_login_qr` draws
the card the phone scans. Both have worked for eighty-odd releases. Neither has
ever had **a place for a person to do it from**.

```
  what enrolment needs                 where it could be done, until now
  ─────────────────────────────────    ─────────────────────────────────────
  a farm office, Monday morning        an MCP client
  a worker holding their phone         bench console
  ninety seconds
```

That is not a gap in the tooling. It is a gap in *who can reach the tooling*,
and it lands on the one step that gates every other feature on the handset: a
phone that is not enrolled cannot scan a bucket, close a shift, sign a training
sheet or photograph a spray. So the work went either undone or through the one
person on the farm who has an MCP client open, which is the worst possible place
to put a bottleneck.

`/app/mobile-onboarding` is that place. Name, email, role, entities, **Create &
Generate QR**, and a card sized for one sheet of Letter that the worker scans off
the desk. Below it, the roster — who is enrolled, on what, when they were last
seen, and what is wrong with any of it — with **Regenerate QR** on every row.

---

## A wrapper, and not a second implementation

The rule `badge_sheet.py` states and `asset_tag_sheet.py` repeats, for the third
time and the same reason: **every gate that matters belongs to the tool.**

| still enforced, unchanged, by `tools/mobile.py` |
|---|
| the seven mobile roles, and nothing outside them |
| entity scoping is mandatory — there is no flag that makes an unscoped account |
| the endpoint must be HTTPS |
| a card may be valid to enrol with for at most a week |
| an account that already exists is a refusal, not a retry |

The page adds **one** gate, and it is the one a tool cannot make: a **session**.
An MCP tool is reached through the shared token and the CIDR allow-list and runs
as this app's own System User. A Desk caller is a person Frappe has already
identified, so "may *this* person enrol somebody" has no answer inside the tool
and has to be asked at the door.

---

## The gate is Frappe's own permission table

`frappe.only_for("System Manager")` would have been one line, and it is the wrong
line: it puts the decision in code an operator cannot see and cannot change. A
farm that wants its office manager enrolling pickers would need a release.

| action | needs |
|---|---|
| read the roster | read on `Mobile Access Grant` |
| enrol, or regenerate a card | create on `Mobile Access Grant` **and** create on `User` |

`Mobile Access Grant` ships System-Manager-only and can be widened by adding a
row to its permission table in the Desk.

**The `User` half is what makes widening the other half safe.** However far an
operator opens this app's own register, the page can still only produce an
account they could have produced by hand on the User form. It is not a route
around Frappe's user administration; it is a faster path down the same one.

**The Page record names no role at all.** A standard Page is rewritten from this
app's JSON at every `bench migrate`, so a role list stored there is a decision an
operator makes and then silently loses at the next upgrade. `onboarding_context`
answers `may_enrol: false` with the sentence instead, and the page renders it.
Both phone-only roles ship with Desk access off, so they never reach `/app`.

## The pre-flight, which is the only part that is not a pass-through

`generate_mobile_login_qr` refuses in two ways that have nothing to do with the
person being enrolled:

- the bench has no QR encoder, so there is nothing to draw with;
- `public_url` is empty or is not HTTPS, so the card would point the phone at
  nothing, or at a plaintext endpoint that would carry a live credential in the
  clear at every call, forever.

Both are true or false **before anybody types a name**. And run in the obvious
order — make the account, then draw the card — either one leaves a worker
**half enrolled**:

```
  the login exists      ✓
  the credential exists ✓
  the person standing at the desk has nothing to scan
```

Recovering from that means finding a different screen, which is precisely what
this page exists to spare somebody.

So `enrolment_blockers` is a **pure function over those two facts**. The same
list greys the button out in a banner at page load and refuses at submit with
*No account was created.* One function, so the banner cannot promise a form the
submit then rejects — there is a test that holds both to the same sentence.

### The residual race is a half success, not an error

The encoder present at load and gone by the time the button was pressed is still
possible, and it is reported as what it is: the account was made, it is reported
as made, and the drawing failure comes back in `qr_error` with the Regenerate
button pointed at it. Calling that a failure would invite a second press of the
button and *"this user already exists"* — a worse place to be than the one the
operator is actually in.

## One rotation and not two

`create_mobile_user` mints a credential for a **new** account. Asking
`generate_mobile_login_qr` to rotate a millisecond later would issue two secrets
in order to hand over one, and the first would be dead before it reached paper.
So a new account's card prints the credential the account was created with.

An account that was only **re-scoped** kept its old credential by design — a
phone in somebody's pocket must not go offline because they were moved to another
block — so its card mints a fresh one. `token_issue_count` is 1 after the first
and 2 after the second, and the tests assert exactly that.

**Regenerate QR** rotates by default, matching the tool, and says so in the
confirmation: a phone already enrolled stops working until it scans the new card.
That is the right default, because the ordinary reason somebody asks for a second
card is that they cannot account for the first one.

## What does not come back in the JSON

`api_secret`.

`create_mobile_user` returns it — its caller has nowhere else to get it — and
this page has the PNG, which already carries it. Putting the raw secret in the
response as well would put a live credential in the browser's network log, in
devtools, and in whatever the tab's memory gets swapped to, **to no end**: nobody
types this one in. There is a test that the secret does not appear anywhere in
the serialised response.

The card itself is a live credential and says so **in print, on the card**, where
the person handling it will read it — along with the expiry, because the
mitigation for enrolment-by-QR is time.

## `list_mobile_users` gains `last_seen_on`

Two lines, and it is the roster's "last activity" column.

`api/guard` stamps `last_seen_on` at most once a day and `sweep_idle_grants`
revokes the token of a credential nobody has used for `idle_token_days`. It was
the one column on the grant that the roster did not report — so a list that
showed every other date could not answer the only question anybody asks after a
sweep, which is *why did that phone stop working*.

## The files

```
erpnext_mcp/mobile_onboarding.py                     the four methods, and the printable card
erpnext_mcp/erpnext_mcp/page/mobile_onboarding/      the Page record, its script and its template
docs/mobile-onboarding.md                            the operator-facing half
tests_standalone/test_mobile_onboarding.py           47 tests, eight claims
```

No hook was added. No Workspace was added — this app installs none, and adding
one would rearrange a Desk the operator already had, which is the promise
`hooks.py` opens with. The route and the awesomebar are how you get there.

Two things about the template are load-bearing and neither is obvious, so both
are commented where they live and tested where they can be: Frappe compiles a
page's `.html` into `frappe.templates["<name>"] = '...'` — a **single-quoted** JS
string — so every apostrophe in the visible text is `&#39;`; and the file opens
on its root element, because `$(frappe.render_template(...))` on a leading
comment hands back a collection rather than the wrapper every `.find()` assumes.

## Upgrading

`bench --site <site> migrate`, then `bench build`. The page appears at
`/app/mobile-onboarding`. Nothing else on the site changes: no new switch, no new
scheduled job, no field on anybody else's doctype.
