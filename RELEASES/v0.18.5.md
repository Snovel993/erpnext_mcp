# v0.18.5 — the workflow walks in CI, not at the iPhone

**A prevention release.** v0.18.2, v0.18.3 and v0.18.4 all shipped on
2026-08-02, and every one of them was found the same way: Tim, holding a phone,
in the field. Three bugs, three round trips, one evening. Not one of them was a
hard bug. All three were invisible to a suite of 3,474 tests because the suite
tested each side against itself and nothing tested the seam.

This release fixes one live crash and then spends the rest of its weight making
sure the next three bugs of that shape are found by `python3 -m unittest` instead.

Tim's ask, verbatim: *"make sure we can build out a full workflow from end to
end via MCP."* Item 3 is that, and it is the centre of the release.

---

## Item 1 — Number Card `filters_json` took the dispatch workspace down

**Symptom.** `/app/farm-task-dispatch` answered Internal Server Error on load.

```
File "apps/frappe/frappe/desk/doctype/number_card/number_card.py", line 148, in get_result
    filters.append([doc.document_type, "creation", "<", to_date])
TypeError: 'NoneType' object is not callable
```

**Root cause.** Every Number Card and Dashboard Chart spec in `dashboard.py`
wrote its `filters_json` in Frappe's **dict** shape — `{"state": "Available"}`.
That shape is valid everywhere a filter is *queried with*: `frappe.db.get_list`
accepts it, so every card rendered its number correctly and had done since
v0.16.0.

It is not valid where a filter is *built on*. `number_card.get_result` computes
the period-over-period comparison arrow by appending a date clause to whatever
the card's own `filters_json` parsed to. `frappe.parse_json` turns a JSON object
into a `frappe._dict`, `_dict` has no `.append`, and `_dict.__getattr__` returns
`None` for a missing attribute rather than raising — so `filters.append(...)`
evaluates to `None(...)` and the error message names neither the card nor the
field. One card that cannot compute a delta takes the whole workspace's render
with it.

**The distinction, stated once because it is the whole bug:** a dict is a valid
filter to query WITH and an invalid filter to build ON. Only the list shape is
both.

**Fix.** New `dashboard.card_filters(doctype, clauses)` emits the list shape —
`[["Farm Task", "state", "=", "Available"]]` — and every spec in all four tuples
(`CARDS`, `CHARTS`, `DISPATCH_NUMBER_CARDS`, `DISPATCH_CHARTS`) now goes through
it. The three charts v0.18.3 gave `"{}"` are now `"[]"`: both parse to something
falsy and both render today, but the two timeseries charts among them have their
date range appended the same way, so only one of the two spellings is safe there.

**Fixing the spec is only half the fix, and this is the part that matters for
Tim's site.** `_build` deliberately leaves any card that already exists
completely alone — that is the anti-fixture contract the module docstring
argues for at length. So every site that ran v0.16.0 through v0.18.4 holds
eleven cards with dict filters that a corrected spec would never touch.

New `dashboard._repair_filters` is the second repair clause on these installers
(the first was v0.16.1's empty-workspace fill). It is as narrow as it can be and
still work:

- only `filters_json`, and only when it parses to a `dict`;
- **the operator's own clauses are carried across**, not replaced with the
  spec's — somebody who changed a card to count `Awaiting-Review` gets a working
  card counting `Awaiting-Review`, not this app's card back;
- `document_type` is read off the document rather than the spec, because the
  list shape names the doctype in every clause and the document knows which
  doctype it actually counts;
- a list-shaped `filters_json` is never touched.

`install.py` prints what it repaired, by name. A repair is the one thing these
installers do to a document somebody else may have edited, so it says so.

## Item 2 — `tests_standalone/test_ios_contract.py`

The test that would have caught v0.18.2 in CI.

Eleven mobile methods, each with a Python mirror of the iOS `Codable` it feeds.
Each mirror records the one distinction that decides whether a bad payload is a
blank line on a screen or a crash in somebody's hand:

| | iOS | a miss means |
|---|---|---|
| **STRICT** | `try c.decode(String.self)` | the **whole row throws** |
| **LENIENT** | `c.lenientString(...)` etc. | the field silently is not there |

`FarmTask.name`, `UserContext.user` and `AccessibleCompany.name` are strict.
That is why v0.18.2's `{"name": null, …}` did not degrade to a blank task — it
threw, mid-flow, on a claim the worker had already made.

Each mirror carries the Swift file and line it transcribes, and a failure quotes
it, so a red test points at the source of truth rather than at the
transcription. Beyond the eleven decode tests the file also checks:

- **enum drift** — a `state`, `urgency` or `dispatch_mode` outside the Swift
  enum's cases decodes to `.unknown` and renders as "Unrecognized". Silent, and
  now asserted. (All three currently match the doctype's Select options exactly.)
- **date drift** — a timestamp none of `FrappeDate`'s four formats parse decodes
  to nil, so the app shows no time rather than a wrong one.
- **the payload is put through `json.dumps(..., default=str)` first**, because
  that is what turns a `datetime` into the string the phone parses, and asserting
  against the wrapper's Python return value stops one step before the conversion
  half of this file is looking for.
- **the mirrors are strict enough** — `TheMirrorsAreStrictEnough` feeds each one
  the exact broken payload from the release that shipped it and requires the
  mirror to refuse. Without this the whole file could be a no-op and still green.
- **the mirrors cover the surface** — `TheContractIsComplete` fails when somebody
  publishes a twelfth method and writes no mirror for it.

## Item 3 — `tests_standalone/test_e2e_workflow.py` ← the ask

The whole pipeline, from an empty site, through the mobile-facing endpoints only.

**Fixtures are built, not seeded.** `create_company` → `create_parcel` →
`create_housing_unit` → `create_mobile_user`, through the real registry with the
kill switches an operator actually ticks. A seeded fixture cannot catch an
onboarding path that has drifted, and onboarding an entity is something this
system is asked to do far more often than it is asked to inspect a cabin.

**The walk.** `refresh_compliance_alerts` raises `housing_inspection_overdue` on
`TEST-CABIN-01` → a Farm Task is raised against that alert →
`get_current_user_context` → `list_available_tasks` → `claim_task` →
`start_task` → `list_my_tasks` → a real 1×1 PNG staged **in multiple chunks** →
`finalize_staged_file` → `complete_task_via_mobile` with two evidence files.

**What it asserts is the state of the site afterwards, not the return values.**
That is the entire difference from `test_api_mobile.TheWholeFlowWorks`, which
every one of this week's bugs passed. This one opens the record, walks the child
table and reads the `File` row's own permission fields:

- `claim_task` answers a real `name: str` — the v0.18.2 regression check;
- the Housing Inspection exists, names the unit, and names the source task;
- its `photos` child table holds both evidence rows;
- each `File` has `attached_to_doctype == "Housing Inspection"` and
  `attached_to_name == <the new HI>` — the v0.18.4 regression check — and is
  still private;
- the alert the work answered is gone on the next sweep, **and
  `auto_dismissed` is set** — an alert that was ticked away by hand is not the
  same event as a condition that stopped being true, and the whole architecture
  rests on that distinction.

Also covered: the clean-pass branch (`Recorded`, no corrective action, task
`Completed`, evidence still cascades), the evidence-contract refusal writing no
record at all, upload session ownership between two phones, and cross-entity
scoping on the built fixture.

**What it does not prove**, stated plainly: this runs on the in-memory double in
`harness.py`, not a bench. It proves this app's logic, argument translation,
permission decisions and record-writing are coherent end to end. It does not
prove MariaDB accepts the insert, or that Frappe's own `File.has_permission`
reads `attached_to_doctype` the way v0.18.4 assumes — that assumption is stated
in the code and confirmed on the live site by HI-2026-08-00002.

## Item 4 — what building item 3 turned up

Tim asked for anything found along the way to be bundled. Three things were.

### 4a. The v0.18.4 permission cascade missed the two Attach fields

`_link_evidence_files_to_parent` walked the evidence rows and read `row["file"]`
— which covers the child tables and **nothing else**. Two evidence Files on
these doctypes do not live in a child table:

- **`Housing Inspection.signature`** — the attestation. `complete_farm_task`
  puts `signature_file` there rather than in `photos`, so any completion filed
  through the MCP tool with a signature left the one file an auditor is most
  certain to open readable only by whoever uploaded it. (The iOS path is
  unaffected — the app sends its signature as a Signature-typed evidence row,
  which is why last night's phone testing did not surface this.)
- **`Water Test.lab_report`** — the laboratory's own PDF, which is the entire
  evidentiary content of a water test.

Evidence rows that named a `file_url` rather than a docname were skipped for the
same reason. `_link_evidence_files_to_parent` now takes the attach fieldnames,
and `_file_docname` resolves either spelling. Same silent failure as v0.18.4:
the record renders, the field shows a filename, the Preview refuses.

### 4b. `test_uploads.py` had v0.18.4's old ceiling typed into it

The suite had one failing test before this release started. v0.18.4 raised
`MAX_CHUNK_BASE64` from 200 KB to 800 KB and the assertion still said
`200 * 1024 + 4`. It now reads `uploads.MAX_CHUNK_BASE64 + 4`. A suite that goes
red on a change that was correct is a suite people learn to ignore, which is
expensive in exactly the week you need it.

### 4c. `RELEASES/v0.18.5-spec.md` was a v0.18.3 planning doc

Its own first line said so. Renamed to `RELEASES/v0.18.6-spec.md`; its Item 2
(contract tests) is done here, its Item 1 (`record_training`) is still open and
is the next release's work.

## Deploy sequence — canonical

```sh
# Mac
cd ~/Desktop/Development\ Comms\ Folder/erpnext_mcp
python3 -m unittest discover -s tests_standalone -t . -q   # must be OK before anything else
git add -A
git commit -m "v0.18.5 number card filters + contract and E2E test suites"
git push origin main

cd ~/Desktop/Development\ Comms\ Folder/fafo-umbrel-store/fafo-erpnext/build
docker build --no-cache --build-arg ERPNEXT_MCP_VERSION=0.18.5 -t polehntim/erpnext-umbrel:15 .
docker push polehntim/erpnext-umbrel:15

# umbrel.local
ssh umbrel@umbrel.local
sudo docker pull polehntim/erpnext-umbrel:15
sudo umbreld client apps.stop.mutate --appId fafo-erpnext
sudo umbreld client apps.start.mutate --appId fafo-erpnext
sleep 45
sudo docker exec fafo-erpnext_server_1 grep __version__ /home/frappe/frappe-bench/apps/erpnext_mcp/erpnext_mcp/__init__.py
sudo docker exec -u frappe fafo-erpnext_server_1 bash -c "cd /home/frappe/frappe-bench && bench --site frontend migrate"
sudo docker exec fafo-erpnext_server_1 supervisorctl restart all
```

No funnel changes. **No iOS rebuild** — nothing in this release changes a
payload the app reads; the contract suite exists to prove exactly that.

**The migrate is what repairs the cards.** `after_migrate` runs both installers,
and `_repair_filters` rewrites the eleven dict-shaped `filters_json` values in
place. Watch the migrate output for:

```
erpnext_mcp: rewrote dict-shaped filters into list form on N card(s)/chart(s) …
```

If that line does not appear, the repair did not run and step 1 of the
verification below will still fail.

## Post-deploy verification

Shorter than usual, because the E2E test is now the verification.

1. **The workspace loads.** Open `http://umbrel.local/app/farm-task-dispatch`.
   It renders with all five Number Cards and their comparison arrows, instead of
   Internal Server Error. Then `http://umbrel.local/app/compliance-command-center`
   for the other six.

2. **The suite is green on the built image** — the same command from the deploy
   block, run anywhere the repo is checked out. `test_e2e_workflow` walking is
   the statement that claim → start → upload → complete → Housing Inspection →
   alert-cleared is intact; there is no longer a reason to establish that with a
   phone.

3. **One real completion, once, from the phone** — not to prove the pipeline
   works but to prove the *transport* does, which is the one thing the suite
   cannot speak to. Then open the resulting Housing Inspection **as Tim's admin
   account, not as the worker**, and preview both attachments.

Every future release runs step 2 and knows whether the workflow still walks.
