# v0.18.0 — farmops-api: the mobile methods, off Frappe's request handler

**Released:** 2026-08-01 · **Previous:** [v0.17.2](v0.17.2.md)

v0.17.2 carried the same `<api_key>:<api_secret>` pair **five ways** — the
`Authorization` header, `X-FarmOps-Token`, `_auth` in the JSON body, `_auth` as
a query parameter, form-encoded fields — and resolved all five in an `auth_hooks`
entry, which is the one place Frappe lets an app settle identity before
`is_whitelisted` refuses a Guest.

Every one of them works against `http://localhost:5300` from inside the
container. Every one of them came back as the Desk's HTML login page through
`https://umbrel.tail2b0bb0.ts.net`.

**Five independent carriers do not all fail by coincidence.** The remaining
common factor is `/api/method/*` itself — Frappe's own request handler, behind
that proxy, on this deployment. Isolating it further means instrumenting the
framework, and a farm cannot wait on that.

**Bank Bridge is the proof that the funnel is not the problem.** A plain WSGI
service answering at `/bankbridge/plaid/oauth_return` works perfectly through
the same funnel, on the same box, carrying the same kind of headers. What
differs is that nothing in its request path is Frappe's `/api/method` handler.

So this release is that shape, for the eleven methods a phone calls.

---

## What it is

`erpnext_mcp/farmops_api/` — a Werkzeug WSGI service, its own gunicorn, its own
port, its own routes, and **not one line of Frappe's HTTP layer**.

```
POST /farmops/api/mobile/get_current_user_context
POST /farmops/api/mobile/list_my_tasks
POST /farmops/api/mobile/list_available_tasks
POST /farmops/api/mobile/get_task
POST /farmops/api/mobile/claim_task
POST /farmops/api/mobile/start_task
POST /farmops/api/mobile/complete_task_via_mobile
POST /farmops/api/mobile/reject_task
POST /farmops/api/mobile/list_compliance_alerts
POST /farmops/api/files/stage_file_chunk
POST /farmops/api/files/finalize_staged_file

X-FarmOps-Token: <api_key>:<api_secret>
Content-Type: application/json
```

Frappe is still the database, the permission model and the rule set — it is
imported, connected to, and become-the-user-on. **It is simply no longer the
thing that reads the request.**

### It delegates to v0.17.2's wrappers. It does not reimplement them.

This is the part worth your scrutiny, so it is stated bluntly.

A new transport into a compliance system is the most dangerous kind of change
there is. The obvious implementation copies the gates into the new service, the
two copies drift, and the drift is invisible until an auditor finds a field
worker reading another entity's board.

**There is no copy.** `farmops_api/routes.py` is a table of eleven entries and
each one names the same `@guard.endpoint`-wrapped function in
`erpnext_mcp/api/mobile.py` or `api/files.py` that the whitelisted path calls.

| # | Gate | Runs on the new transport |
|---|---|---|
| 1 | `farm_ops_mobile_enabled` kill switch | ✅ same code |
| 2 | Not Guest | ✅ this is what the token check establishes |
| 3 | Role gate (`Field Worker` / `Farm Worker` / `Foreman` / `Farm Manager`) | ✅ same code |
| 4 | **Active Mobile Access Grant** | ✅ same code |
| 5 | Rate limit per user per method | ✅ same code |
| 6 | Entity scoping on every argument and every returned row | ✅ same code |
| 7 | MCP Action Log row + secret strip | ✅ same code |

An admin holding every role on the site **still** cannot call these without a
grant — v0.17.1's headline check, re-run against v0.18.0's entry point, is in
the suite as `test_administrator_holds_every_role_and_still_cannot_call_this`.

And `ByteIdentical` runs every read **both ways against the same fixture** and
compares the two answers as serialised JSON. A missing key, a reordered list, a
stringified number — any difference fails the build. That is what makes "it is
the same code" a checkable property rather than a claim in a release note.

### Three things Frappe was doing that this now does

1. **Identity.** `X-FarmOps-Token`, verified by `fallback_auth.verify_credential`
   — v0.17.2's verifier, unchanged, sharing v0.17.2's failure counter. One
   credential, one guessing budget, however many transports. `Authorization` and
   `_auth` are read too, so **the shipped iOS build needs no new auth work** —
   it already sends the pair three ways. Only the URL changes.
2. **A Frappe session per request.** `init` / `connect` / `set_user` / `destroy`,
   plus the commit Frappe's handler does at the end of a request. Without it a
   worker claims a task, gets a 200, and finds it unclaimed on the next
   pull-to-refresh. Reads commit too, because `_stamp_last_seen` writes from
   inside one and that stamp is all `sweep_idle_grants` has to go on.
3. **An envelope.** `{"message": …}` on success. On failure, Frappe's
   `_server_messages` shape — a JSON string holding an array of JSON strings,
   each an object with a `message`, which is what the **already-shipped**
   `FrappeClient.serverMessage` decodes. So a refusal still reaches the phone as
   the sentence it was written as.

### Every answer is JSON

There is no path out of this service that renders HTML and none that redirects.
Not a 404, not a 405, not an unhandled exception inside the service's own error
handling. Werkzeug's default 500 page is HTML, and reintroducing it here would
rebuild the exact failure this release exists to end.

### Status codes are a contract with the app

`FarmOpsKit` treats **401 as "this credential is dead — sign out"**, which
discards the offline queue. So:

| Status | When | What the phone does |
|---|---|---|
| **401** | and *only* a credential that did not verify | signs out, re-scan needed |
| **403** | role gate, grant gate, entity scoping | refused, still signed in |
| **404** | a docname that does not exist **or** is not yours — deliberately indistinguishable | "that task no longer exists" |
| **429** | rate limit | backs off, keeps its queue |
| **503** | kill switch | parks, keeps its queue |
| **400** | anything else a caller can correct | shows the sentence |
| **500** | anything nobody anticipated | generic line; detail goes to the log, not the phone |

### No new dependencies

The brief said Flask, to match Bank Bridge, and Bank Bridge is right to use it —
it is a separate image with its own dependency set. **This service is not.** It
runs inside the ERPNext container on the bench's own virtualenv, next to a
production ledger. `pip install flask` there resolves against Frappe's pinned
Werkzeug and can upgrade it, and the failure mode of a Werkzeug upgrade under
Frappe v15 is the whole site, not this endpoint.

Werkzeug ships with Frappe. gunicorn is already in the bench venv — it is what
`supervisord.conf` has been starting Frappe itself with since the image was
built. So this costs **zero new packages**, and eleven fixed routes need a
routing framework about as much as a list of eleven things needs a database.

### The old path stays live

`/api/method/erpnext_mcp.api.mobile.*` and `…api.files.*` answer exactly as they
did in v0.17.2. They work on the LAN and from inside the container, the
standalone suite still drives them, and they are the fallback on the day this
service is the thing that is down. Nothing in `api/` was removed or deprecated;
one additive function was added to `fallback_auth`.

## ⚠️ One thing in the brief was wrong, and it changes a deploy step

The brief said: bind the service to `127.0.0.1:5250` inside the container and
point the funnel at `http://127.0.0.1:5250`. **That would not have worked, and
it would have failed silently — connection refused, with the funnel looking
correctly configured.**

Umbrel's Tailscale app proxies Funnel traffic to **its own localhost**. That is
not a preference, it is what `tailscaled` enforces:

```
error: failed apply web serve: only localhost or 127.0.0.1 proxies
are currently supported
```

(That exact error is quoted in `fafo-bank-bridge/docker-compose.yml`, which hit
the same wall and solved it by giving Bank Bridge its own Tailscale sidecar in a
shared network namespace.)

The Tailscale container shares the **host** network namespace, which is why the
existing funnel entry can say `http://127.0.0.1:5300` and reach ERPNext at all:
**5300 is the port Umbrel publishes for `fafo-erpnext` on the host.** A service
listening on `127.0.0.1:5250` *inside* the ERPNext container is invisible to it
— a container's loopback is its own.

**So the port has to exist on the host's loopback.** `docker-compose.yml` now
publishes it:

```yaml
    ports:
      - "127.0.0.1:5250:5250"
```

The `127.0.0.1:` prefix is not optional. Plain `5250:5250` binds `0.0.0.0` and
puts the mobile API on the farm LAN. Pinned to loopback, exactly two things can
reach it: processes on the Umbrel itself, and the Tailscale container that
shares its namespace. Every gate still runs on every call — this is the layer
*before* any of that, and it costs one prefix.

**Verify this survived Umbrel's compose merge** (step 4 below). If `ports:` is
stripped, the fallback is in "If the port did not publish" at the end.

### 5. Add the eleven Funnel paths

**Only if you are on a path-scoped funnel.** Check first:

```sh
sudo docker exec tailscale_web_1 tailscale serve status --json
```

- **Whole-port funnel** (`"Handlers": {"/": {"Proxy": "http://127.0.0.1:5300"}}`)
  — you still need these, and this is the difference from v0.17.1. The whole-port
  handler forwards to **5300**, which is ERPNext's nginx. The new service is on
  **5250**. A blanket `/` handler will not reach it, so the eleven paths below
  must be added regardless.
- **Path-scoped funnel** — same eleven, same reason.

`--set-path` is an exact mount point, so each method gets its own line. Paste
the whole block:

```sh
for M in get_current_user_context \
         list_my_tasks \
         list_available_tasks \
         get_task \
         claim_task \
         start_task \
         complete_task_via_mobile \
         reject_task \
         list_compliance_alerts; do
  sudo docker exec tailscale_web_1 tailscale funnel --bg --https=443 \
    --set-path=/farmops/api/mobile/$M http://127.0.0.1:5250
done

for M in stage_file_chunk finalize_staged_file; do
  sudo docker exec tailscale_web_1 tailscale funnel --bg --https=443 \
    --set-path=/farmops/api/files/$M http://127.0.0.1:5250
done
```

And the health path, which is what makes step 6 diagnostic rather than binary:

```sh
sudo docker exec tailscale_web_1 tailscale funnel --bg --https=443 \
  --set-path=/farmops/api/health http://127.0.0.1:5250
```

Then read back what you actually mounted:

```sh
sudo docker exec tailscale_web_1 tailscale serve status
```

> **Do not** mount `/farmops/` as one prefix "to save typing" unless you have
> confirmed your Tailscale version treats a trailing-slash mount as a subtree.
> Twelve explicit paths publish twelve things. One prefix publishes whatever
> ends up behind it later.

## The iOS change

Two files. **`namespace` stops being a dotted Python path and becomes a URL path,
and `FrappeClient` stops prefixing `/api/method`.** Nothing else moves — the
headers, the body, the `{"message": …}` unwrapping and every `Codable` are
unchanged, because the server's responses are byte-identical.

### `FarmOpsKit/Sources/FarmOpsKit/Networking/MobileAPI.swift`

```diff
-    /// Dotted Python module path that the whitelisted methods live under.
-    /// Everything below is `namespace + "." + method`.
-    public static let namespace = "erpnext_mcp.api.mobile"
+    /// URL path prefix the mobile methods are served under. Everything below
+    /// is `namespace + "/" + method`.
+    ///
+    /// v0.18.0: this was `erpnext_mcp.api.mobile`, a dotted Python path under
+    /// Frappe's `/api/method/` handler. Through the Tailscale funnel that
+    /// handler answered every request with the Desk's HTML login page no matter
+    /// how the credential was carried, so the methods moved to a separate
+    /// service (farmops-api) that does not go through it. The old path is still
+    /// live on the LAN. The server's QR payload carries this as `api_base`.
+    public static let namespace = "farmops/api/mobile"
 
     /// The file-staging API predates this app (Sprint 6, v0.14.0) and lives in
     /// its own module, so it gets its own namespace rather than inheriting the
     /// mobile one.
-    public static let filesNamespace = "erpnext_mcp.api.files"
+    public static let filesNamespace = "farmops/api/files"
 
     private static func path(_ method: String) -> String {
-        "\(namespace).\(method)"
+        "\(namespace)/\(method)"
     }
```

and at the bottom of the same file:

```diff
-    public static var stageFileChunk: String { "\(filesNamespace).stage_file_chunk" }
-    public static var finalizeStagedFile: String { "\(filesNamespace).finalize_staged_file" }
+    public static var stageFileChunk: String { "\(filesNamespace)/stage_file_chunk" }
+    public static var finalizeStagedFile: String { "\(filesNamespace)/finalize_staged_file" }
```

### `FarmOpsKit/Sources/FarmOpsKit/Networking/FrappeClient.swift`

In `callRaw(_:params:)`, around line 112:

```diff
         var url = credentials.baseURL
-        url.appendPathComponent("api")
-        url.appendPathComponent("method")
-        // Dotted method paths must stay one path component, not be split on
-        // the dots, so append the whole thing at once.
-        url.appendPathComponent(method)
+        // v0.18.0: `method` is now a slash-separated URL path
+        // (`farmops/api/mobile/get_task`), not a dotted Python path under
+        // `/api/method/`. Split and append component by component rather than
+        // passing the whole string: `appendPathComponent` treats its argument
+        // as one component, and whether it escapes an embedded `/` is a
+        // Foundation implementation detail worth not depending on.
+        for component in method.split(separator: "/") {
+            url.appendPathComponent(String(component))
+        }
```

**Nothing else changes.** In particular `X-FarmOps-Token` stays exactly as
v0.17.2 shipped it — the new service reads that header first, which is why the
credential handling needs no work at all.

### The blast radius is exactly those two files

`grep -rl "erpnext_mcp.api" --include="*.swift" .` in `fafo_ios` returns
`MobileAPI.swift` and `FrappeClient.swift` and nothing else. **No test in
`FarmOpsKit/Tests/` references the namespace or any `MobileAPI` path**, so the
change breaks no assertions — which also means the suite will not catch it if
you fluff the edit. Step 6's `curl` is the check that matters.

### Worth updating while you are in there

`FrappeClient`'s doc comment on line 56–57 still says
`POST /api/method/<dotted.path>`. Not load-bearing, but it will mislead the next
person:

```diff
-/// Frappe exposes `@frappe.whitelist()` methods at
-/// `POST /api/method/<dotted.path>` and wraps every result in `{"message": …}`.
-/// This unwraps that envelope so callers deal in payloads.
+/// The farm server exposes the mobile methods at `POST /<path>` (see

```

`API_CONTRACT.md` in the same repo says the same thing twice — line 17
(`POST …/api/method/<dotted.path>`) and lines 25–26 ("**One knob to change:**
`MobileAPI.namespace` (currently `erpnext_mcp.api.mobile`)"). That document is
the contract, so it is worth its own small edit: the knob is still one constant,
it just holds a URL path now.

## The one-flip shutdown, if anything goes wrong

Unchanged from v0.17.1 and it covers **both** transports, because it is gate 1
inside the shared `guard.endpoint`:

```sh
sudo docker exec -u frappe fafo-erpnext_server_1 \
  bench --site frontend set-config farm_ops_mobile_enabled 0
```

Takes effect on the next request. Every phone gets a **503** and keeps its queued
work; nothing is signed out. The MCP endpoint the AI uses is unaffected.

To stop only the new transport and leave the whitelisted path serving the LAN:

```sh
sudo docker exec fafo-erpnext_server_1 supervisorctl stop farmops-api
```

## If the port did not publish

If step 4(b) succeeded and 4(c) failed, `umbreld`'s compose merger dropped the
`ports:` entry. Two ways forward, in order of preference:

1. **Publish it from the host instead**, which does not depend on the merger:

   ```sh
   sudo docker run -d --restart unless-stopped --network host --name farmops-fwd \
     alpine/socat TCP-LISTEN:5250,fork,bind=127.0.0.1 \
     TCP:$(sudo docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' fafo-erpnext_server_1):5250
   ```

   Ugly, and it needs recreating whenever the ERPNext container's IP changes —
   which is exactly the failure mode `db_grant_selfheal.py` exists for on the
   database side. Treat it as a bridge, not a destination.

2. **Give ERPNext its own Tailscale sidecar**, the way Bank Bridge did in
   v0.7.1: a `tailscale` service with `network_mode: "service:server"`, so its
   `127.0.0.1:5250` *is* this service. That is the clean answer and it is a
   compose change of about twenty lines, copied from
   `fafo-bank-bridge/docker-compose.yml`. It also removes the dependency on
   Umbrel's shared Tailscale app entirely.

Tell me which one you hit and I will write it properly.
