# v0.65.0 — one scan, whatever was on the tag

One tool, one route, four registers, and a fifth answer for everything else.

---

## The problem was on the handset, not on the server

Farm Ops has had scanners since v0.24.0. A badge step resolves a card to a
picker. An asset step resolves a QR to a valve. A housing lookup and a block
lookup exist behind the right screens. Every one of them works.

Every one of them also requires the person holding the phone to know what they
are about to scan **before** they scan it, because each of the four calls behind
those screens refuses everything that is not its own: `resolve_badge` refuses a
valve, `scan_asset` refuses a badge, and both refuse a cabin. So a phone pointed
at an unfamiliar sticker had two options, and both are the same bug wearing
different clothes:

- **Ask the worker first.** A menu in front of the camera, answering a question
  the server can answer better.
- **Call all four and read the refusals.** Three refusals per scan, one of which
  is a `last_scan_at` write on the one that happened to hit.

In an orchard the premise is backwards. A worker walks up to a thing with a
sticker on it. *Which register that sticker belongs to* is the question.

## What shipped

`universal_scan` takes the raw string a camera produced and works out what it
names.

```
badge register  →  Asset Register  →  Housing Unit  →  Field  →  unknown
```

Ordered, first match wins, matched on the **exact docname**. The branch that wins
delegates to the tool that already owns that register — `resolve_badge`,
`scan_asset`, `get_housing_unit`, `get_field` — so a badge resolved through a
universal scan and a badge resolved through the badge step get the same answer
and the same refusals, because it is the same code.

### Why the order is what it is

**The badge is first because a badge is a PERSON.** A string that is somehow in
both the badge register and the Asset Register has to resolve to the worker: of
all the confusions available here, attributing somebody's piece work to a sprayer
is the one with a payroll consequence and the one nobody can unpick from a wage
record afterwards. It is also the cheapest probe — the badge register is keyed on
the badge ID itself — so putting it first costs one `exists()`.

**The asset is second because it is the largest register and the only branch that
writes.** `Housing Unit` is also an asset *type*: a cabin with a tag on it is
scanned as the tag it carries, which is the branch whose history an asset
timeline reads.

**Housing and Field follow**, both read-only and both keyed on their own docname.

### The match is an exact docname, deliberately

`asset_row`, `unit_row` and `field_row` each fall back to a `LIKE` search when a
name is not a docname. That is right for an operator typing half a name into a
tool and wrong here: a cascade whose second step matched loosely would let
`MC-Block` scanned at a cabin door resolve to whichever asset happened to contain
those characters, and the answer for a given sticker would depend on what else
was in the register that week.

### A printed tag is a URL

`Asset Register` builds `qr_url` as `<public url>/scan/<name>` with the docname
percent-encoded, so the string a camera actually produces from a printed asset
tag is `https://erp.example.com/scan/MC-Valve-05` and not `MC-Valve-05`. The
`/scan/<tag>` path is unwrapped and decoded before any register is read; a query
string a scanner appended is dropped; everything else — a badge ID, a unit name
typed into a manual-entry box, a supplier's barcode — passes through untouched.

Unwrapping it on the server is the difference between one implementation of that
rule and one per client.

## Unknown is an answer, and one scan is refused

**The scan that resolves to nothing is the interesting one.** A supplier's carton
barcode, a hand-written label, a tag printed by a system this app has never heard
of. A refusal would send the worker back to a menu; instead the answer carries
`entity_type: "unknown"`, the content **whole**, `searched` naming the registers
that were actually consulted — so "unknown" on a site whose Asset Register has not
migrated does not read as "this tag is not an asset" — and `create_task` still in
`available_actions`. An unregistered tag is worth reporting, and the task needs
the string.

**Exactly one scan is refused instead of answered: a credential document.**
`generate_mobile_login_qr` mints `{"url":…,"api_key":…,"api_secret":…}`, and what
a camera reads by accident is whichever QR is nearest. Everything above about
`unknown` is precisely why that string cannot be allowed to reach it: keeping the
scan whole so a task can carry it means, for that one string, handing a live
credential to a screen, a task description and a handset cache. It is refused
before any register is read, and the refusal names what was scanned **without
repeating it** — `bucket_bridge._display`, the same twelve-character bound the
badge step has used since v0.50.0.

## Refusals pass through rather than falling through

A retired badge, a badge belonging to somebody who has left, an asset in another
company: each of those is a **match** whose own tool refuses it with its own
sentence, and `universal_scan` passes that sentence through instead of demoting
it to "unknown tag". A card that *was* issued is a badge whatever its state, and
"that sticker means nothing" is the wrong sentence in all three of the situations
`resolve_badge` was written to tell apart.

## What is written, and where

**Exactly one branch mutates.** An asset scan stamps `last_scan_at`,
`last_scan_by` and — where the handset sent a fix — the asset's GPS position,
which is `scan_asset`'s existing behaviour and the reason a valve knows when
somebody was last standing in front of it. `scan_recorded` in the answer says
which happened rather than leaving a caller to infer it from the entity type.

**The entity check on that branch happens before the stamp, not after.**
`scan_asset` takes no company of its own — it is called from a screen that has
already resolved the asset — so a scan scoped to one company would otherwise
write a worker's GPS fix onto another entity's record and only then hand back a
row the caller may not read. The refusal names the entity the asset actually
belongs to: an operator holding a tag from the wrong farm is better told which
farm than told nothing.

## What comes back

Every key is present on every answer, empty where it does not apply, because the
client decoding this has one struct and a scan screen that changes shape between
scans is a screen that crashes on the fifth one.

| Key | |
|---|---|
| `content`, `resolved_from` | the scan as read, and the docname it was resolved to |
| `entity_type`, `entity`, `entity_name` | one of `employee`/`asset`/`housing_unit`/`field`/`unknown` |
| `pending_tasks`, `overdue_tasks` | live Farm Tasks on this thing, and the late ones |
| `due_compliance` | open Compliance Alerts raised against this record |
| `recent_history` | the timeline for whichever register won |
| `available_actions` | what a client may offer next |
| `scan_recorded` | whether anything was written |

**`overdue_tasks` is a SUBSET of `pending_tasks`, not a partition of it.** A Farm
Task carries no due date of its own — a job is Available or it is not — and the
date a compliance obligation is measured against lives on the Compliance Alert
the task answers. So *overdue* means: a live task whose `source_alert` was due
before today, and a hand-raised task is never overdue. Every task in both lists
carries `due_date` and `overdue`, so a client that renders only `pending_tasks`
still shows the late work and nothing has to be re-derived on the handset.

A task reaches its entity through more than one column and **both are read**: an
asset through `Farm Task.asset` and through the dynamic `location` pair, a cabin
through its own register row and through the asset twin standing for it. A scan
that read one and not the other would say "nothing outstanding" in front of
outstanding work.

## The mobile route

`POST /farmops/api/mobile/universal_scan`.

**Metered as a read, declared as a write**, and both are deliberate. The only
write on any branch is the `last_scan_at` stamp on the asset the worker is
standing in front of, so the route table records it as mutating, because it is.
The *limit* is `resolve_badge`'s sixty a minute rather than `scan_asset`'s ten,
because of what this route is used for: a crew clock scanning a queue at a bin
trailer is forty badge reads in a minute, every one of them a pure read, and
`WRITE_LIMIT` would refuse the crew rather than the abuse.

**The company comes from the caller's scope, never from the body.** A `company` in
the request may narrow what this account already reaches and can never widen it;
`guard.require_company` refuses anything else. Every task and every alert leaving
the route is checked against that scope on the way out, the same belt-and-braces
`list_compliance_alerts` wears.

**All four spellings of the scan argument are declared in the signature** —
`content`, `scan`, `raw`, `code` — because this transport's argument filter keeps
only the keys a signature names, and a handset posting `code` at a method
declaring only `content` would arrive with an empty scan and be told the field is
required while holding a perfectly good tag.

`MobileAPI.swift` does not name this method yet; the handset side is a scanner
screen that stops asking the worker what they are about to scan, and it is
separate, tracked work. The method is listed in `PENDING_IOS_INTEGRATION` so the
test file keeps claiming only what the Swift actually calls.

## Government IDs are deliberately absent

A driving licence's PDF417 and a passport's MRZ are parsed **on the handset** and
routed to the hiring wizard there. That is not an oversight and not a gap to fill
later: those barcodes carry a date of birth, a document number and an address, and
posting them to a server so it can tell the app what it already knows would put a
person's identity document into an HTTP body, an audit row's arguments and a log
file, for no answer the phone did not already have. The cascade has four branches
because there are four registers; identity documents are not one of them.

## Catalogue and migration

414 tools, 189 read. `allow_universal_scan` ships **off**, like every other
mutating tool. Migration is `bench migrate` for the settings switch; nothing is
backfilled and nothing needs to be.
