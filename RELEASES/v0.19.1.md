**Released 2026-08-03. Hotfix on v0.19.0.**

Three items off the v0.19.0 debrief, clustered into one release because none of
them is big enough to be its own and all three are the same kind of work:
closing gaps the last release named rather than fixed.

One of the three turned out not to exist. That is written up here at length
rather than quietly dropped, because "we swept for stale citations and found

gets hits in `docs/` needs to know somebody already looked.

## 2. `farm_location_gps`

**Debrief item 6.** §112.161(a)(1)(i) asks an activity record for the farm's
name **and** its location. The name has been snapshotted since v0.19.0
(`farm_name_snapshot`); the location was not recorded anywhere.

Added as **Data, optional, free text** to:

- **`Farm Task Assignment`** — the record of the activity, so the place the
  activity happened belongs on it. Sits next to `task_name` in the identity
  column on purpose: the regulation asks for the name and the location in one
  breath, and the form now shows them that way.
- **`Water Test`** — next to `block`. The zone names *which water*; this names
  *which standpipe*, and a zone feeding four hydrants does not answer the second
  question.

**`Spray Record` does not exist in this app and was not invented.** The debrief
named it alongside Water Test. The doctype that holds applications is `Spray
Log`, and it ships with `farm_precision_ag` — a separate app this one adds
Custom Fields to (see `hooks.py:16`). Adding a compliance field to somebody
else's doctype from a hotfix is a different decision from adding one to our own,
and it is not made here.

### Why free text rather than two float columns

A coordinate nobody could take is worth less than a place name somebody can
stand in. Cabins have metal roofs; a phone inside one either has no fix or has a
bad one, and the worker still knows they are in MC-Cabin-01. A `Data` column
takes `"45.5152,-122.6784"` from a handset that had a fix and `"MC-Cabin-01"`
from one that did not, and an auditor reads both. Two `Float` columns would have
made the second case unrecordable, which would have meant recording nothing —
and nothing is what this field exists to stop.

### Additive, so no migration

Optional with no default. Records filed before this release have it blank, and a
blank is **an older record, not an invalid one**. Nothing back-fills it: a
location inferred after the fact for a walk somebody did in July is a guess
wearing the clothes of evidence, and it is exactly what §112.161 is written to
prevent.

On `complete_farm_task` the field is written **only when given**. Overwriting a
location already on the assignment with an empty string would turn a recorded
fact into a missing one, which is a worse outcome than never having had it.

### The tools

- `complete_task_via_mobile` (MCP) — accepts `farm_location_gps`, forwards it to
  `complete_farm_task`, which writes it. The wrapper stays thin, as
  `test_fieldwork.TheWrappersAreThin` requires.
- `create_water_test` (MCP) — accepts it, `build_water_test` writes it, and it is
  in the `WATER_TEST` read spec so `get_water_test` reads it back.
- `_describe_assignment` returns it, so every mobile read of a completion carries
  it too.

### The HTTP mobile API: the fix the app was already sending

This is the part worth reading twice.

`POST /farmops/api/mobile/complete_task_via_mobile` has accepted
`latitude`/`longitude` since v0.18. They went to the audit row and **nowhere
else**, and the docstring said why, in as many words: *"Farm Task Assignment has
no coordinate column, and inventing one in a hotfix would be a schema change on
a compliance record."*

It has one now. So the pair the shipped iOS app has been sending all along
becomes `farm_location_gps`, and **the location half of §112.161(a)(1)(i)
arrives with no iOS release at all** — every handset in the field starts
satisfying it on the next server deploy.

Three rules govern it, in `mobile._location`:

1. **An explicit `farm_location_gps` wins over the coordinate pair.** A worker
   who typed a place name did so somewhere the fix was absent or wrong.
   Overwriting that with whatever the GPS settled on once they walked back
   outside would replace a fact with a guess.
2. **A pair that will not parse as numbers is dropped, not raised on.** The
   completion carries photographs, a signature and a compliance record. Failing
   all of it over a malformed coordinate would trade the record for its least
   important field. The pair as sent is in the audit row regardless, which is
   where a bad one is worth looking at anyway.
3. **Coordinates are formatted to seven decimal places** — about a centimetre,
   which is past the point where more digits mean anything about where somebody
   was standing, and matches what `farm.py` already does for parcel centroids.

## 3. The tool count assertion

**Debrief item 8.** v0.19.0 found `docs/tool-catalog.md` claiming 206 tools
against a catalogue of 210, fixed it by hand, and noted the class of bug: the
count is asserted for `registry.TOOLS` in `test_protocol.py` and **nowhere for
the documentation**.

`tests_standalone/test_tool_catalog_count.py` closes it. Three assertions:

- the intro's `All N tools` against `len(registry.TOOLS)`
- the read section's `All N read tools` against `len(registry.READ_TOOLS)`
- total minus reads against `len(registry.MUTATING_TOOLS)` — which catches
  somebody editing one number by hand to make a red assertion go green without
  asking why it was red

The counts are **parsed out of the prose** rather than kept in a constant here.
A constant would be a third place to update and a third place to forget.

Both patterns fail loudly if the sentence they read is gone, and if either count
appears **twice** in the document — two hand-written copies of one number being
how the drift starts in the first place.

### It found one on its first run

`docs/tool-catalog.md` said **85 read tools**. `registry.READ_TOOLS` has **95**.

The total was correct at 214, which is why nobody caught it: the number people
check was right, and the drift was in the one they did not. It is long-standing
and no release can be blamed for it — the read count was simply never updated as
read tools were added, and the only reason it surfaced now is that something
finally looked.

Fixed to 95. Both documented counts now match the registry, and will stay
matched or the suite goes red.

**Tool count at this release: 214** — 95 read, 119 mutating. Unchanged by this
hotfix, which added arguments to two existing tools and no new ones.
