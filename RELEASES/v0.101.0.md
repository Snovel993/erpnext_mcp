# v0.101.0 — the wage lands on the block that earned it

Item 18. No new doctype, no new tool, no new column. One pure module gains the
arithmetic and two existing tools read a chain the app has shipped since v0.53.0
and never once followed.

**This number also carries three commits that landed after v0.100.0 without one**
— `e2a47e7` (`create_break_policy` / `update_break_policy`), `fe77432`
(garnishment compliance) and `49fbac7` (ruff to zero, the format sweep, SPDX
markers, and the two declared dependencies CI never installed). They are not
described below; this note is about item 18. They are named here so the version
they shipped under is written down somewhere rather than inferred from the log.

---

## The one idea

A payroll journal entry carried **one** cost center — the one on the company's
mapping — so a P&L grouped by cost center said the whole fortnight's wages
happened wherever that mapping pointed.

```
  before                              after
  ───────────────────────────────     ───────────────────────────────
  5320 Field Labor                    5320 Field Labor
    Dr 41,300.00                        Dr 22,715.00   Block 7 North
       cost center: Field Work          Dr 12,390.00   Block 9 South
                                        Dr  6,195.00   Field Work
                                                       (paid time no task placed)
```

Labour is the largest cost a block carries and it was the one the ledger knew
least about. Every other input a block consumes already lands on it: chemical
goes out on a Stock Entry, fuel on a Purchase Invoice, depreciation through the
asset's own allocation. Wages — the biggest number of the three — went to a
heading and stopped.

## The record already existed. Nothing read it.

This release adds no source of truth. It follows one:

```
Farm Task Assignment      who, and how many minutes   (actual_duration_minutes)
  → Farm Task             where                       (location_doctype + location)
    → Field               the block, and its cost center
      → Cost Center       what the P&L groups by
```

Each link shipped for its own reason and none of them for this one.
`actual_duration_minutes` became the **sum of the closed time segments** in
v0.79.0, so an interrupted morning no longer bills the valve repair to the
irrigating. `affected_block` started filling the `location_doctype`/`location`
pair in v0.98.0, so a field report says which ground it is about in a column
rather than in prose. `link_field_to_cost_center` has pointed a block at a Cost
Center since v0.53.0 and, until today, only the block's own cost report read it.

The foreman has been recording this for two years. The accountant was retyping
one number a fortnight anyway.

## Only debits split, and that is not a simplification

Eleven components. Every one with a **debit** side is an expense — gross pay is
the wage expense, and each employer component's debit is a tax expense. Every
**credit** is a liability: federal tax withheld, FICA withheld, state tax
withheld, net pay owed, and the employer's own five payables.

| side | what it is | split? |
|---|---|---|
| `Gross Pay` Dr | the wage expense | **yes** |
| `SS Employer` / `Medicare Employer` / `FUTA` / `SUTA` / `State Employer Other` Dr | tax expense | **yes** |
| every credit | a payroll liability | no — keeps the blanket cost center |

A cost center on a liability line is a dimension on a balance sheet row, and no
report anybody runs groups by it. Splitting the credits would double the line
count of every payroll entry to describe nothing.

`EXPENSE_COMPONENTS` is **derived** from the component table rather than listed,
because the rule is structural — in this table a debit is an expense and a credit
is a liability, for all eleven — and a hand-written list goes stale the first
time a twelfth component is added.

## Two hours in Block 7 is not a day in Block 7

This is the part that decides whether the resulting P&L is worth reading.

A picker paid for eight hours who was dispatched to two hours of thinning in
Block 7 did **not** spend the day in Block 7. Splitting by the attributed time
alone — the obvious implementation — books the entire wage to a block that saw a
quarter of it, and does it silently, and does it worst on exactly the farms that
dispatch least.

So the denominator is what payroll **paid for**:

```
attributed   120 min  →  Block 7            25%
residual     360 min  →  the blanket cost center    75%
             ───────
paid         480 min  = the slip's own total_hours
```

**The denominator is the slip's `total_hours`, not a re-read of the shift
register.** Those hours came off each crew row's own `joined_at`/`left_at`
through `payroll_integration`, were bucketed into workweeks for overtime, and
were then stored on the slip — they are the hours the gross was computed from.
Going back to Farm Shift to recount them would be a second source of truth for a
number this run already settled, and the two would disagree the first time
somebody corrected a crew row after a payroll was calculated.

A slip carrying **no** hours has nothing to measure against, and is split by its
attributed time alone.

## Exact, or the entry does not post

A third of $1,000.00 three times is $333.33 three times and a cent unaccounted
for. ERPNext does not take an entry that is a cent out, so the cent is **given**
to somebody rather than lost: largest fractional remainder, ties broken by
position, which also makes the same run produce the same entry every time it is
previewed.

Each component is split on its own remainder, so the per-block totals land within
a cent per component of the ideal ratio rather than exactly on it. What is exact
is what has to be — the sum.

A negative slip (a correction) is split on its magnitude and given its sign back,
so a reversal lands on the same blocks in the same proportions as the posting it
reverses.

## Consolidated is the sum of the per-employee entries, not a blend of them

Both modes agree to the cent, per cost center — and the cheap way to achieve that
would have been wrong.

Blending the run into one set of proportions and splitting the totals by it works
for gross pay, because gross is what the weights are made of. It does **not**
work for the employer taxes: FUTA stops at the first $7,000 per worker and SUTA
at whatever the state's base is, so a run in October has people who have capped
out and people who have not.

Blend it, and the FUTA of the picker who is still accruing gets booked onto the
block worked by the picker who capped out in July. Splitting each slip and
summing the results costs one pass and is right by construction.

## Five ways the chain breaks, and five fallbacks

Every one of these posts the payroll and reports the problem. None of them
refuses, because a refusal here strands a whole crew's wages over one block
somebody pointed at the wrong thing.

| what is wrong | what happens |
|---|---|
| the task is on a Parcel, an Irrigation Zone, a Housing Unit | not block work. Left unattributed. |
| the block has no Cost Center | named in `blocks_without_cost_center`; its time falls to the blanket |
| the block points at a **group** cost center | ERPNext would reject the whole entry. Refused here, named, falls back. |
| the block points at a **disabled** cost center | same |
| the block's cost center is on another company's tree | same — an intercompany allocation is not a dimension |

`link_field_to_cost_center` already refuses a group and a disabled cost center
when the link is *made*, which is the right place for it. It is checked again at
posting time because a link made through the Desk never met that tool.

## What did not change

- **The money.** Same accounts, same amounts, same totals, same balance check.
- **The entry count.** Consolidated is still one entry per run.
- **The refusals.** All five, still reported at once.
- **The idempotency rule.** Still about what is in the ledger, not what the link
  table remembers.
- **Drafts only.** Still never submits.
- **A site that dispatches nothing.** Produces byte-identical entries to the ones
  it produced before this release. That is not a compatibility promise bolted on
  afterwards — it is the fallback path, and it is the same path a farm gets for
  the employees it did not dispatch this fortnight.

---

## Turning it off

`split_by_cost_center=false` on either tool. It ships **on** because it cannot
change anything on a site that has no task time on a block with a Cost Center,
and because `preview_payroll_gl` shows exactly what will happen first —
`cost_center_allocation` carries the minutes behind every share, per employee, so
the split can be read rather than trusted.

Take the preview both ways before the first posting. The money is identical. The
dimension is not.

## Tests

`tests_standalone/test_payroll_cost_center_split.py` — 55 tests in six claims:
the proportions, the cent-exactness, which side splits, the two modes agreeing
across a capped employer tax, the chain end-to-end on a site with all five
breakages seeded, and everything else about the posting staying where it was.

Eight mutations were run against them and all eight were caught: dropping the
largest-remainder correction, never booking the residual, splitting the credits
too, blending the consolidated run, dropping unlinked-block time instead of
counting it unattributed, accepting group and disabled cost centers, dropping the
pay-period filter on the assignment read, and ignoring `split_by_cost_center=false`.
