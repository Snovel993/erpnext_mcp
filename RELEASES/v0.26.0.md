# v0.26.0 — the field report is the asset repair order

**Worker scans an asset's QR tag, taps "Flag needs repair", and the Farm Task
that lands in the dispatch pool already knows what it is, where it is, and what
skill to send.**

Tool surface **270 + 1 = 271** (120 read, 151 mutating). One new mutating tool,
one enhanced tool, one new doctype field.

---

## What changed

### New tool: `report_asset_issue`

Convenience wrapper that takes an asset name instead of asking the caller to
figure out location and skill. It resolves the Asset Register record, maps the
asset type to a default `skill_required` via `ASSET_TYPE_SKILL_MAP`, and
delegates to `report_field_task` with the asset link pre-filled. Same anti-spam,
same photo requirement, same urgency cap.

### Enhanced: `report_field_task` gains an `asset` parameter

When an Asset Register docname is passed, the created Farm Task is linked to the
asset. If `skill_required` and `location` are not given explicitly, they are
auto-filled from the asset record.

### Enhanced: `scan_asset` response

Now includes `can_report` (boolean) and `suggested_skill` (string) — everything
the iOS app needs to show a "Flag needs repair" button with the right skill
pre-selected.

### New field on Farm Task: `asset`

Link to Asset Register. When present, the task appears in `get_asset_detail`'s
history timeline and open-task list, closing the loop between scanning an asset
and seeing what work is pending on it.

## The merge point

This release is where three prior releases converge:

- **v0.23.0** (field-initiated tasks) gave workers the ability to report problems
- **v0.24.0** (universal asset tags) gave every asset a scannable identity
- **v0.25.0** (state-change actions) gave each asset type a state machine

v0.26.0 connects them: the scan that identifies an asset can now create the task
that fixes it, with the skill and location already filled in from what the asset
knows about itself.
