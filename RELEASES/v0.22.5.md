# v0.22.5 — the first rule nobody wrote in Python

**Every compliance rule this app has ever shipped fires on a distance from a
date. This one fires because a thermometer said 82.**

Tool surface **unchanged at 256** (113 read, 143 mutating). Suite **4,277 →
4,330 passing**. Three new columns on one existing DocType, one new
`date_field_role` value, one new rule, and **behaviour drift of zero** on the
thirteen that were already there.

The split is now **12 declarative / 2 built-in-permanent / 0 `custom_python`**.

---

## 1. Why this one matters more than the count suggests

v0.22.0 turned thirteen Python functions into thirteen records. v0.22.1 built the
primitives those records had been waiting for and moved five of them off their
scanners. Both releases were **migrations**: the vocabulary was reverse-engineered
from rules that already existed, and a vocabulary wide enough to describe what you
already have is not yet evidence of anything.

`shift_heat_threshold_crossed` was authored **as a record**. There is no shipped
scanner behind it and there never was. A site that has this app and has not
migrated the Compliance Rule DocType does not run it — and that is said out loud
in the seeder rather than papered over, because the fallback rule set is the
definitions of v0.21.0 and a rule invented afterwards is not one of them.

It is also the shape an AI-proposed rule will arrive in when
`propose_compliance_rule` is wired: a dict of declarative fields, a citation, a
kairotic gate, and nothing executable anywhere in it.

## 2. The primitive, and why it is a sibling rather than an extension

The spec offered two paths: extend `gate_related_table_json` with a field
expression, or add a new primitive beside it. **The new primitive is right, and
the reason is the fold rather than the syntax.**

`gate_related_table_json` folds a related doctype to **one value per subject** —
the maximum date — and asks how old it is. What this rule needs is the temperature
*on the latest row*, and a maximum over dates cannot answer that. Nor can a
maximum over temperatures: the 85 °F reading at noon says nothing about compliance
at four o'clock if a 72 °F reading was written at half past three. **You have to
fold to a row, and then read its other columns.**

Extending the existing field would have meant one column whose fold changed
depending on which of its keys were set. That reads fine and is impossible to
reason about six months later, which is the failure mode this whole framework is
written against.

```json
{
  "child_doctype": "Farm Shift Weather Reading",
  "parent_field": "parent",
  "parentfield": "weather_timeline",
  "order_by": "reading_datetime",
  "context_key": "latest_weather",
  "match": "any",
  "conditions": [
    {"field": "temp_f", "op": "gte", "threshold": 80,
     "threshold_source": "weather.heat_threshold_temp_f"},
    {"field": "heat_index_f", "op": "gte", "threshold": 80,
     "threshold_source": "weather.heat_threshold_heat_index_f"}
  ]
}
```

Folding to a row also puts the row into the message. `latest_weather.temp_f` is
why the alert can say *what the reading was* — an alert that says a threshold was
crossed and cannot say what it read is an alert somebody has to go and look up
before they can act on it.

### `threshold_source`, and the number that must not be in two places

The heat threshold could have been a literal on the rule. It is not, and this is
the part of the design worth arguing.

OR-OSHA's number is 80 °F. An entity that has decided its own is 75 sets it on
**Weather Settings**, per company, which is where the v0.19.4 shift sweep already
reads it. A literal on the rule would make the two layers disagree about what
"hot" means on the same afternoon, on the same shift — the operational sweep
logging a Threshold Crossed event at 76 °F while the compliance rule stayed quiet,
or the reverse. The disagreement is invisible until somebody compares two records,
which is the worst kind.

So `threshold_source` names a setting, out of a **closed registry** of three. It
is closed because "read a number from somewhere" is one sentence away from "read
anything from anywhere", and this app has already spent a module sandboxing the
one place where that is allowed. The literal stays on the condition as the floor
the setting falls back to: a site whose Weather Settings have not migrated gets
the regulation's number rather than nothing, which is the difference between a
rule that is conservative and a rule that is silent.

### Three directions chosen where both were available

- **A subject with no child row is gated out.** A shift whose weather timeline is
  empty is not a cool shift; it is a shift nobody has a reading for, and raising a
  heat alert off no reading would be this app asserting a fact it does not have.
  Same direction `gate_date_field` takes, same reason.
- **A child row whose field is empty does not satisfy its condition**, so
  `match: "all"` fails on it. A reading with no temperature is not a cool reading.
- **The comparison is numeric only.** This is the one place `_passes` is
  deliberately *not* reused. `_passes` falls back to a lexical comparison when a
  side is not a number, which is correct for a scope filter full of ISO dates and
  exactly wrong on a thermometer: a reading somebody typed as `"warm"` is
  lexically greater than `"80"`, and would raise a heat alert off a word.

### Standard child columns, selected by hand

`parent`, `parenttype` and `parentfield` are real columns on every child table and
are **not** in `frappe.get_meta(...).fields` — Frappe keeps them among the
standard fields every DocType gets for free. Passing them through
`compat.has_field` would have dropped them from the SELECT, and a child index with
no `parent` column is an index keyed on nothing: every row folds onto one empty
subject and the rule fires on whichever shift sorted last, on every shift, for
ever. They are listed explicitly, and the test that would have caught it is
`test_parentfield_narrows_the_read_to_the_right_table`.

The index is built **once per sweep**, capped at `SCAN_CAP`, folded in Python —
the same shape as v0.22.1's supersession and gate indexes. Twelve open shifts each
carrying a reading every fifteen minutes is one query, not twelve, and it is the
query that would otherwise run every sweep of every day of August.

## 3. `default_severity` was not enough, and the reason is a database fact

The plan proposed `default_severity` alone: when the gate is true and no
time-based thresholds are set, fire at that severity. It does not work, and the
reason is not a design preference.

`threshold_critical_days` and `threshold_warning_days` are **Int columns**. "No
threshold" and "a threshold of zero" are one value in the database — and zero is a
*real* setting meaning "fire on the due date itself". A shift that started this
morning is zero days from its own start, so a rule read as a clock says **Critical**
about a crew who are merely at work.

Nothing the engine can read off the numbers distinguishes the two cases. So the
rule has to say which it is, and `date_field_role` gains a third value:

| Role | The date is | The severity is |
| --- | --- | --- |
| `Clock` | a deadline; its distance picks the band | the three band severities |
| `Timestamp` | when the thing was found; bands nothing | `severity_expired`, every matching row |
| **`State`** | read for the message only | **`default_severity`**, every row the gates let through |

**v0.22.1 refused a third role value, and this is not the one it refused.** What
it refused was a role that inverted the *sign* of every threshold beside it — a
number meaning days elapsed where the same number on twelve other rules means days
remaining, which is a number somebody will eventually misread. `State` reads no
thresholds at all, so there is no number left to misread. That is why the earlier
refusal stands and this addition does not contradict it.

Two smaller consequences, both asserted:

- **The band it reports is the word `state`**, not a reused `expired`. An alert
  saying "expired" about a condition with no expiry is a word an auditor would be
  right to query.
- **`State` outranks the per-row window**, which is the one thing that outranks
  everything on a clock. A shift is not less hot for having a short lead time.

`default_severity` on the shipped rule is **Warning**, and the default in the
vocabulary is Warning too. A threshold cross is a heads-up. Critical belongs to
sustained exposure and to worker-reported symptoms, which are different facts
watched by rules that do not exist yet — and a default of Critical would put every
hot afternoon at the top of a board where Critical is supposed to mean somebody
stops what they are doing.

## 4. `producer_assigned_to_expression`, and the half of the producer story that was missing

### The two routings are exclusive

Until now a producer task routed one of two ways, and both are **pools**: through
an Inspection Template, claimed by whoever holds the template's skill, or as a
plain Farm Task with a `skill_required`.

OAR 437-004-1131 asks what the *supervisor* did about the heat, and the only
person who can answer is the one who was standing there. So the rule carries
`"producer_assigned_to_expression": "row.foreman"`, evaluated in the same sandbox
as `custom_python` — same grammar, same refusals, same step and clock budget — and
vetted on save rather than on the afternoon somebody needed the task.

Where it resolves, the task is inserted **Claimed**, `dispatch_mode` =
`Dispatched`, with an open Farm Task Assignment and **no skill**. The exclusivity
is enforced at both doors, the controller and the tool, because a task carrying
both is a task whose holder depends on which one the dispatcher read first — and
the failure is silent in the worst direction: the foreman who was standing in the
heat never sees it, and somebody with the skill closes it from a desk.

An expression that names nobody, or names somebody payroll has never heard of,
puts the task back on skill routing and says so in `routing_notes`. It is never
left as `Dispatched` with nobody on it: that combination is a task sitting in
Available which no worker is allowed to claim — visible, urgent, and unreachable,
which is the worst of the three ways for dispatch to fail.

### The bug this release found

`generate_tasks_from_compliance_alerts` read `ALERT_TASK_MAP` and nothing else.
Since v0.22.0, every Compliance Rule has carried `producer_farm_task_type`,
`producer_skill_required` and `evidence_contract` — **seeded from that very
table**, so the two could not disagree — and *nothing ever read them back*. A rule
authored after the framework shipped therefore had a complete producer recipe on
its record and landed in `skipped_unmapped` regardless. That is a framework that
lets you define a rule and not the work it asks for, and it would have bitten the
first operator who wrote one.

`_recipe_for` now falls through to the record. **The table is still consulted
first**, and that ordering is the backward-compatibility guarantee: the thirteen
shipped rules produce exactly the tasks they produced in v0.22.1, out of the same
reviewed table, whatever a site has since edited onto their records. The record is
read only where the table has nothing to say — which is precisely the case the
table cannot cover, because the rule did not exist when it was written.

Both halves — a task type **and** an evidence contract — are still required before
an alert becomes work. A task with a made-up evidence contract is worse than no
task: it produces a compliance record nobody can rely on.

## 5. Two systems observing the same fact at different cadences

v0.19.4's `sweep_open_shifts` runs every fifteen minutes, appends a reading, and
logs a **Threshold Crossed** compliance event on the shift. That is the
operational log and it is **unchanged**.

What v0.22.5 adds sits above it. The rule sweep reads the same open shift and the
same latest reading, raises an **alert**, and turns the alert into a task. The
first captures the fact; the second translates the fact into a required response.

**There is no race and no duplication risk, and not because either defers to the
other.** Three independent keys:

- the shift's Threshold Crossed event dedupes **on the shift** — one per shift,
  not one per reading, which is v0.19.4's own decision and the reason a
  nine-hour hot afternoon does not collect thirty-six identical rows;
- the alert dedupes on **`rule_id` + the shift's docname**, which is
  `alert_key` and carries nothing that moves daily;
- the task dedupes on **the alert it answers**, through `source_alert`.

Run them in either order, or twice each, and there is one of each. That is
asserted rather than argued — `test_the_v0194_weather_sweep_still_logs_its_own_threshold_event`
and step 5 of the end-to-end walk — because "both paths are idempotent" is the
kind of claim that stays true until somebody adds a third path.

The one thing they deliberately do **not** share is a judgement. Neither creates a
Heat Exposure Event. That record says which crew was exposed, what water was
provided, whether the rest cycle was taken and whether anybody showed signs, and
it carries a signature — five judgements by the person who was standing there. The
sweep surfaces; the foreman decides. v0.19.4 drew that line and this release does
not move it: what it adds is that the foreman is now *asked*.

## 6. Auto-dismissal needed no new mechanism

Both directions go through the standard path, and this is worth stating because
the plan allowed for the possibility that one of them would not.

- **The shift closes.** `scope_filters` stop matching it.
- **The temperature drops.** The latest-child gate stops matching it.

In both cases the rule simply does not observe the row on the next sweep, and
`base.py` auto-dismisses every alert of a rule whose key the rule did not observe.
Same code that dismisses a certificate alert when somebody renews the certificate.
`auto_dismissed = 1`, no reason, nobody's name — so six months later the two kinds
of dismissal are still distinguishable — and the **same key** comes back
un-dismissed if the afternoon warms up again, with `first_seen` untouched.

The task the foreman was given **stays**, held by them. A shift that closed is not
evidence that anybody wrote down the water and the shade; that is what the task is
for, and dismissing the alert must not quietly take the errand with it.

## 7. Backward compatibility

`test_weather_triggered_rules.TheThirteenAreUntouched` runs the whole calendar of
one operation twice — once with the fourteenth rule enabled, once with it
deactivated — and compares every alert row field by field: docname, severity,
category, company, source, message, due date, first seen. The thirteen say exactly
what they said.

`TheThirteenMigrateInThreeShapes`, `TheMigrationChangesNothing` and
`TheWholeSweepSaysWhatItSaidBeforeTheRulesBecameData` are unmodified except for
three counts moving from thirteen to fourteen. The v0.22.1 parity oracle — each
migrated rule run against its own shipped scanner — is untouched and still green.

The fourteenth rule has no Python to be compared against, so what is pinned is the
row itself, every column of it, in
`test_the_fourteenth_rule_joins_the_snapshot_field_by_field`.

`patches/migrate_declarative_rules.py` is unchanged and is a no-op against the new
rule: the check is "does this row still name a scanner", and it never did.

## 8. No new tools

The surface stays at **256 / 113 / 143**, and `docs/tool-catalog.md` agrees. Every
one of the three new columns is reachable through tools that already existed:

- `create_compliance_rule` / `update_compliance_rule` accept
  `latest_child_field_threshold`, `default_severity` and
  `producer_assigned_to_expression`, validated by the same parsers the DocType and
  the seeder use — so a malformed blob is refused at whichever door it arrives at,
  and the parser accepts its own output, which is what stops a rule validating
  once and then quietly matching nothing.
- `get_compliance_rule` reports all three in `definition`.
- `list_compliance_rules` gains `state_driven`, `default_severity`,
  `date_field_role` and `producer_assigned_to_expression` at the top level —
  additive, and present on every rule rather than only the ones that use them, so
  a client reads one shape.
- `test_compliance_rule` evaluates the new primitives on the same code path the
  sweep takes. The rule dry-runs to one observation while the shift is hot and to
  zero once it cools, which is exactly what an operator is checking.

## 9. Judgment calls

- **`producer_farm_task_type` is `Compliance-Audit`, not "Document Heat
  Response".** The plan named the latter, but `Farm Task.task_type` is a closed
  ten-value Select and this field is the value the task is *filed under*, not the
  sentence describing the errand. Adding an eleventh option would have changed an
  enum the iOS build switches on, for one rule, and `Compliance-Audit` is already
  where this app files "arrange the retraining" and "sign the supervisor review".
  The errand itself lives in `extra_parameters.producer_task_what` and reads on the
  card as *"Document the water, shade and rest cycle the crew took — SHIFT-…"*.
  The controller now refuses a task type no Farm Task will accept, so the next
  person to make this mistake is told while they are looking at it.
- **`dispatch_mode` is `Dispatched`, not a new `Direct-assigned`.** `Dispatched`
  is this app's existing word for "somebody has to be SENT to this by name" — the
  mode a licence renewal and an I-9 re-verification already take. A fourth value
  meaning the same thing would be a second vocabulary for one idea, on an enum
  three tools and one mobile client branch on.
- **Both `end_datetime IS NULL` and `status = Active` are on the scope filter.**
  v0.19.4's own sweep filters on the first alone and argues for it: `end_datetime`
  is the fact and `status` is a stored summary recomputed on save, which an import
  could leave stale. ANDing both is strictly narrower, so the status filter carries
  `"default": "Active"` — a shift written by an import that never set the column
  is still read as open rather than silently dropped off the hot-day list.
- **The rule's thresholds are `-1`, not `0`.** They are never read, because the
  role is `State`. They are negative anyway, which is the documented way to say
  "this band never fires", so a site that edits the role back to `Clock` gets a
  quiet rule rather than a Critical alert on every crew at work.
- **`sandbox.evaluate` wraps the expression in an assignment** rather than parsing
  it in `eval` mode. `check` is the one place the grammar is enforced and it parses
  in `exec` mode; an expression compiled down a second path would be an expression
  the checker had never seen the tree of.
- **The seeder walks a second list.** `seed_specs()` derives its thirteen from the
  `Rule` objects in `alerts/rules.py`, which is what keeps a gate paragraph edited
  there from going stale on the record. A rule with no `Rule` object cannot come
  from there, so `declarative_seed_specs()` is separate — and being separate is
  what makes "this rule is only data" a structural fact rather than a comment.
