# v0.108.0 — seven hundred switches you can find, and a badge the phone stops guessing

Contract items **S9** (MCP settings UX) and **S11** (role indicator metadata).
One new module, one new block in `roles.py`, two fields on the settings form, and
no new tools — `registry.TOOLS` is unchanged at 757 and every count assertion in
the suite stays where it was.

---

## The two ideas

**S9. A form with 759 checkboxes is a form nobody configures.** Every switch on
"ERPNext MCP Settings" is a real control with a real reason to exist — that is
the promise this app makes about what an AI client can reach — and the honest
consequence is a page an operator scrolls, recognises two section names in, ticks
two boxes, and abandons. The other seven hundred and fifty-five stay at whatever
the release shipped, which means the switches have stopped being a decision and
become a default.

**S11. The phone was working out its own role badge, out of an array.**
`get_current_user_context` has always returned `roles` — every role the account
holds, this app's seven and the site's own — and the app intersected it with a
list of role names compiled into Swift, taking whichever came out first. That is
this app's role vocabulary living in a binary that ships through App Store
review: a role added or renamed here does not exist there until the next build,
and the order the app picks in is its own invention.

```
  before                                 after
  ────────────────────────────────       ────────────────────────────────
  759 checkboxes, one flat page          759 checkboxes, and above them:
  no idea how many are on                  "412 of 757 tools enabled —
  no way to find one by name                no write tools enabled"
  no way to set a working set                7 domain chips with counts
                                             a search box
                                             8 preset profiles

  phone: roles ∩ hardcoded Swift list    phone: role_indicator.label
         → whichever came first                 → decided on the server
```

## S9 — the tool console

### What it adds

Four things, above the first tool section on the settings form. Nothing is
removed and no switch changes behaviour: every checkbox is still there, still
individual, still the thing that decides whether a tool is advertised.

| | |
| --- | --- |
| **Summary** | `412 of 757 tools enabled — no write tools enabled`, recomputed live as you tick. The write count is a separate clause everywhere it appears, because "412 enabled" and "412 enabled, 3 of them write" are different sentences and only the second lets an operator stop reading. |
| **Domains** | Seven chips — Farm Operations, HR & Payroll, Compliance & Safety, Accounting & Finance, Buying/Selling/Inventory, Assets/Property/Governance, Platform & Administration — each with its own `on/total`. Clicking one narrows the whole form to it. |
| **Search** | Type `spray`, `i9`, `garnish`. Matches the tool name and the switch's label, hides everything else, and hides any section left holding nothing. |
| **Presets** | Eight profiles. Each writes every tool switch at once, previews what it will do first, and saves as one Version row. |

Plus `Enable everything shown` / `Disable everything shown`, which act on
whatever the filter is currently showing and are **not** saved until you save the
form — so "turn on the whole compliance domain" is two clicks and still
reversible with a reload.

### The presets

| Preset | Reads | Writes |
| --- | --- | --- |
| Farm Manager | farm, workforce, compliance, commerce, accounting, platform | farm |
| Foreman | farm, compliance, workforce | farm |
| Field Worker | farm | — |
| Bookkeeper | accounting, commerce, workforce, platform | — |
| Compliance Officer | compliance, workforce, farm | — |
| Owner / Family | holding, accounting, compliance, commerce | — |
| Read Only — Everything | every domain | — |
| Nothing Enabled | — | — |

**Write domains are sparse on purpose.** "Mutating tools ship off" is one of this
app's two or three load-bearing promises, and a preset that quietly handed an AI
client three hundred write tools would end that promise while looking like a
convenience. Only the two profiles whose whole job is recording what happened in
the orchard carry a write domain, and `apply_profile` names every mutating tool
it turned on in its answer and in the confirmation dialog before it runs.

### A preset writes the WHOLE surface, and never leaves the tool switches

Two decisions worth stating because the alternatives are both tempting:

**It disables as well as enables.** A preset that only ever added would be a
ratchet — three clicks and an operator holds the union of three profiles with no
idea what is live. Applying one replaces the last.

**It touches nothing but `allow_<tool>`.** Not the master switch, not the token,
not the allowed CIDRs, not the attribution user, not the two compliance packet
types. A profile answers "which tools", and every other field on that form
answers a question a job title does not. `APresetTouchesOnlyToolSwitches` asserts
all thirteen of them by name, before and after — that document is the entire
security surface of the endpoint, and a bug that cleared one of those fields
would take a site down or, worse, bring it up.

### What is derived and what is declared

The maintenance story is the interesting part of `erpnext_mcp/tool_groups.py`:

* **DERIVED** — which section each tool's switch sits in, read out of the shipped
  DocType JSON's `field_order`. A tool added to a section is in that section here
  on the same commit, with nothing to update. There is no second copy of the
  catalogue in this module and there must never be one.
* **DECLARED** — which of the seven domains each of the 105 sections rolls up
  into. No rule reliably turns "Kairotic Compliance Calendar" into "Compliance",
  so that is a table — and `EveryToolIsFiled` fails the build if a section
  holding a tool switch is missing from it. A new section cannot arrive without
  somebody deciding where it belongs.

**It reads the JSON rather than `frappe.get_meta`, and that is not an
accident.** Real Frappe orders `meta.fields` by `idx`, which follows
`field_order`. The standalone test double orders them by the JSON's own `fields`
array, which is a *different* order. A "walk the fields and remember the last
Section Break" written against meta would therefore group tools one way in the
suite and another way on the bench — and every test would pass. This is the same
class of trap as a memory-only shape that MariaDB flattens.

### The browser keeps no copy of anything

The domains, the profiles, and every tool's domain and write-ness come from
`erpnext_mcp.tool_groups.console`, exactly as the write-tool banner has asked
`erpnext_mcp.mcp.mutating_tool_names` since v0.1.0 and for the same reason: a
catalogue transcribed into JavaScript is a catalogue that goes stale, and this
form's whole job is to tell the truth about what an AI client can reach.
`TheFormJSAsksTheServer` asserts the JS hardcodes no tool name, no domain key and
no profile key.

Both new endpoints are `frappe.only_for("System Manager")` on their own, rather
than safe because of where they happen to be called from.

## S11 — the role indicator

`get_current_user_context` now carries a `role_indicator` block, and so does
every roster row `search_employees` returns — so a picker and the account screen
draw the same word for the same person.

```json
"role_indicator": {
  "key": "foreman",
  "label": "Foreman",
  "short_label": "FRM",
  "precedence": 4,
  "description": "Runs the board: what needs doing, who is doing it, and what came back.",
  "has_login": true,
  "is_administrator": false,
  "can_dispatch": true
}
```

### Why the obvious fix was wrong

`capability_of` already reports `primary_role` and `senior_role`, and sending one
of those looks like the whole job. Neither is:

* **`primary_role` is `held[0]`** in `ROLE_SPECS` order — the LEAST of what
  somebody holds. Every account `create_mobile_user` enrols as a Foreman also
  carries Field Worker, so this is not an edge case: it is what the majority of
  dispatchers look like, and they would all badge "Field Worker".
* **`senior_role` is `held[-1]`**, and `ROLE_SPECS` is ordered by when each role
  was WRITTEN, not by capability. There are **two** inversions in it, not one:
  it ends with `Family Member` and `Advisor` — and `roles.py` itself calls
  Advisor "the narrowest role in the app" — so a Farm Manager who also advises an
  entity badges "Advisor"; and `Crew Leader` was added after `Foreman` and sits
  after it, so a Foreman who also leads a crew badges "Crew Leader", which
  `roles.py` describes as the board-less half of a Foreman that cannot raise,
  assign or cancel work.

The comment above that line calls the ordering "ascending capability", which is
what makes it a trap rather than a wart: it reads as a deliberate invariant, so
the next person builds on it. Nothing server-side consumes `senior_role` today
and it still ships in the user-context payload, so a client branching on it would
be wrong with nothing failing here.

All three are asserted in `test_role_indicator.py` as negative controls — along
with the `ROLE_SPECS` order they rest on, so a reorder cannot leave them green
and empty — and nobody can re-derive the badge from `senior_role` in a later
release without going red. **`capability_of` is unchanged**: it has other callers,
and the fix is a `capability` rank on `RoleSpec` or dropping the field, which is
a decision for whoever owns it rather than a side effect of this release.

### The precedence table

Stated explicitly in `roles.ROLE_INDICATORS`, and it answers exactly one
question: *of everything this person holds, which one word describes them on a
screen the size of a phone?*

| | Badge | Role |
| --- | --- | --- |
| 1 | Administrator (`ADM`) | System Manager |
| 2 | Farm Manager (`MGR`) | Farm Manager |
| 3 | Compliance Officer (`CMP`) | Compliance Officer |
| 4 | Foreman (`FRM`) | Foreman |
| 5 | Crew Leader (`CRW`) | Crew Leader |
| 6 | Field Worker (`FLD`) | Field Worker |
| 7 | Family Member (`FAM`) | Family Member |
| 8 | Advisor (`ADV`) | Advisor |
| 99 | No Role (`—`) | — |

Two consequences, both deliberate:

* **Administrator outranks every farm role.** Somebody carrying System Manager on
  a handset is the operator, and a badge saying "Field Worker" over an account
  that can do anything is the badge lying.
* **Family Member and Advisor come last, below Field Worker,** because they are
  not on the operational ladder at all. Somebody holding one of them *and* an
  operational role is holding a phone in an orchard, and the operational word is
  the useful one. Somebody holding only one of them badges as it, which is the
  case that made them worth listing.

`precedence` is the order the badge is PICKED in and must not be read as
seniority — Family Member below Field Worker is not a claim about authority.

### `has_login` is the field a foreman actually needs

`""` is not "no roles". A worker with no `user_id` has no login and therefore no
roles to read, which is most of a picking crew. "Nobody has given this person an
account" and "this person's account holds no role" send a foreman to two
different places, and only `has_login` tells them apart. The badge is `none`
either way, and it is a real answer rather than a null, because the phone has to
draw something.

### It is a display fact, not a permission

`guard.require_dispatch_role` still runs on every dispatching call and is
unchanged. `can_dispatch` inside the badge is computed off `DISPATCH_ROLES` — the
same frozenset that gate refuses on, not a second list — so a picker can grey a
row out instead of letting somebody discover the refusal after they have chosen.
A client that trusted the badge instead of the server would be a sign on a door
with no lock.

**It is additive.** `roles` and `mobile_roles` are untouched, so a build of the
app that has not been updated yet keeps working exactly as it did.

## What this release does not do

* **No new tools.** `registry.TOOLS` stays at 757, `READ_TOOLS` and
  `MUTATING_TOOLS` are unchanged, and none of the seven count assertions or the
  two prose lines in `docs/tool-catalog.md` move.
* **No new mobile route.** S11 extends the shape of a call the app already makes
  at login and on every manual refresh, which is the cheaper half of what the
  item allowed — the badge arrives as often as it can change and costs no extra
  request on a tethered connection in an orchard.
* **`capability_of` is not repaired.** Its `senior_role` is wrong for anyone
  holding Advisor or Family Member alongside an operational role, and for any
  Foreman who also leads a crew. That is worth fixing — an explicit `capability`
  rank on `RoleSpec`, or dropping a field nothing reads — and it is not this
  release's brief. Both inversions are now pinned by tests so neither can be
  quietly relied on in the meantime.
* **No `bench migrate` behaviour changes.** The two new fields are a Section
  Break and an HTML block, which `settings.seed_defaults` skips by fieldtype, so
  nothing is written to `tabSingles` and no patch is needed.
