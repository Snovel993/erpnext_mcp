# v0.62.0 — seven doors the app was already knocking on

`MobileAPI.swift` names sixty-odd routes. On 2026-08-12 the iOS side audited
every one of them against erpnext_mcp v0.61.0 and found **seven that answer
404**. Not seven features nobody had built — seven paths a shipped handset posts
to today, on screens a foreman is standing in front of.

The audit's own conclusion is the part worth reading twice:

> NOTHING HERE WAS RENAMED, and that is deliberate. Two of the three mismatches
> need a PARAMETER change to be correct and not merely reachable, so a bare
> rename would swap a loud 404 for a quiet 400 or a silently-dropped flag —
> which is worse, because the 404 is the reason anybody is looking.

That is the whole shape of this release. Three of the seven exist here under
another name; four did not exist at all. All seven are now routes, and not one
of them is a rename.

---

## 1. What each 404 actually cost

| The app calls | The server had | What the operator saw |
|---|---|---|
| `list_org_reference_data` | `list_onboarding_reference_data` | Four empty pickers and *"these will have to be set in the office"* — on every hire since v0.54.0 |
| `list_housing_units` | `list_available_housing` | No Housing step at all |
| `create_housing_assignment` | `assign_housing` | Nobody could be put in a cabin from a handset |
| `set_employee_org_fields` | *nothing* | Four questions asked, four answers dropped |
| `set_employee_contact_fields` | *nothing* | A phone number collected on a hire day and never filed |
| `list_attachments` | MCP tool only, never routed | The folder could be filled and never opened |
| `get_attachment_content` | MCP tool only, never routed | Every private file unreachable from the device that took it |

The first is the one that says most about how this drift happens.
`list_onboarding_reference_data` has served those four dropdowns correctly since
v0.54.0. It was tested. It worked. It was reached by nobody for six releases,
because the caller spelled it differently and a 404 on a phone in an orchard
degrades into a polite sentence rather than a crash report.

---

## 2. Why aliases and not renames

**A rename fixes the next TestFlight build and breaks every phone already in an
orchard.** This surface's contract with a handset in the field is that a method
it can reach today it can still reach tomorrow — the same promise
`collect_signature` kept in v0.57.0 when `submit_form_signature` arrived carrying
the argument spellings `API_CONTRACT.md` actually posts.

So: **same act, two doors, one implementation.** Each of the three aliases
delegates to a private function the older wrapper now also calls —
`_onboarding_reference_data`, `_available_housing`, `_house_one_person` — so the
camp rules, the capacity ceiling and the entity scoping cannot come to differ
between the two names. Two copies of a rule that decides where somebody sleeps
is two answers to the same question a season from now.

**And an alias is not a bare forward,** because `routes.bind` reduces a request
body to the keys a signature declares. That is the mechanism behind the audit's
warning, and it is why two of the three needed a parameter change to be *correct*
rather than merely *reachable*:

* **`list_housing_units` declares `assignable_only`** where the older name
  declares `include_full`. Sent at a signature that does not name it, the flag is
  not an error — it *vanishes*, and the camp list comes back looking fine and
  full of cabins nobody can be put in. The sense is inverted with the name, so
  the default flips too: the handset sends the flag only to NARROW, so the
  ordinary call asks for the whole camp with the full and condemned units marked
  and greyed out. A foreman who cannot find the cabin they expected needs to be
  told it is condemned, not shown a shorter list.
* **`create_housing_assignment` declares `unit`, `assigned_date`, `company` and
  `allow_multi_occupancy`** where the older name declares `housing_unit`,
  `check_in_date` and neither of the last two. Under the old signature the body
  the app actually posts arrives with **no cabin and no date in it**, and every
  hire is refused for want of a start date it was sent.

## 3. The barracks flag, and the one line that does not move

`allow_multi_occupancy` is now on the wire, and it is **not** an override.

`assign_housing` cannot receive the flag, so it passes `true` on the caller's
behalf — a four-bunk cabin with one person in it is the ordinary case, and that
wrapper had no way to tell a bunk room from a double-tap. **The handset can tell
them apart, because the foreman is standing there.** So on the new door the
default **refuses** the second body, naming who is already in the cabin, and the
flag is the deliberate second tap.

**The capacity ceiling is not the flag's to lift, on either door.** The count is
taken before the write and a unit already at capacity is refused whatever the
body said. The MCP tool *warns* and writes the row, which is right on a console
where an operator can see the warning, weigh it and mean it — a barracks really
does take a fifth bunk some seasons. It is wrong on a phone: nothing on the
Housing step displays a warning, the foreman has already walked away, and a bed
that does not exist becomes somebody sleeping in a truck.

## 4. The two writes the wizard has never had

`set_employee_org_fields` and `set_employee_contact_fields` are thin subsets of
`update_employee` — the tool runs its own HR role gate, its own company scoping
and its own Link validation against *this* site's Branch, Department, Designation
and Employment Type records. A second copy of the personnel rules is a second set
to keep in step.

**An unsent field is left alone and an empty one is not an answer.** Both steps
are shown to returning workers — in tree fruit the returning picker is the common
case — and a call that wrote `""` for every untouched box would clear columns
somebody set deliberately in the office last season.

**`skipped` is what came back rather than what was sent.** All four org fields are
Links, and a site missing one of the doctypes leaves that column unset while the
call as a whole succeeds; a step that assumed its own optimism would show a green
tick over a department nobody has.

### `employee.WRITABLE` grows by three, and that is a decision

The contact method names five fields and the allowlist carried two of them. So
`current_address`, `person_to_be_contacted` and `emergency_phone_number` join it
— the nineteen become twenty-two.

That list is closed on purpose and this is not a convenience. **An emergency
contact is the same kind of fact as the cell number beside it**: how somebody is
reached, and by whom, on the day it matters. An operation that cannot answer the
second question at four in the afternoon in August has a real problem, and the
answer is collected on the day somebody is hired or it is not collected at all.
None of the three is payroll, tax or banking, which is the boundary that list
actually defends.

The argument names are the handset's and the columns are Frappe HR's —
`emergency_contact_name` is `person_to_be_contacted` on the doctype — because a
phone should not have to know the docname of a column to file a number in it.

## 5. Reading the folder back

Six routes on this surface file documents against an Employee. **None could ask
what was already there.** A badge issued on a hire day was never visible from a
handset again, and *"is there work authorization on file for this picker"* was a
Desk question.

`list_attachments` and `get_attachment_content` have existed as MCP tools since
v0.1 and were never routed. They are now, with three gates the tools cannot run
themselves:

1. **A closed list of parent doctypes.** The tools take any doctype on the site,
   which is right on a console and would be a way to walk the File table one
   docname at a time from an orchard. `ATTACHMENT_PARENTS` names the records this
   app actually files against.
2. **A personnel parent carries the HR role.** An Employee's folder and an I-9's
   are the photographs of somebody's identity documents — the same read
   `search_employees` and `assign_housing` both gate. A Farm Task's evidence and
   a Housing Inspection's photographs are field work and do not.
3. **`get_attachment_content` re-checks the parent the File is actually attached
   to.** A File docname is a global handle. Without that check a caller could
   name the id of a document hanging off another entity's Employee, and the tool
   alone would decide it on Frappe roles a Farm Manager legitimately holds. An
   unattached file is refused outright — there is no parent to scope it by.

**The bytes travel, and that is not sugar over `file_url`.** Every file this app
writes is private by design, the handset authenticates to the sidecar with
`X-FarmOps-Token` rather than to Frappe, and a `/private/files/…` link answers
that with a login page. Without this route the list is a list of things that
cannot be opened.

## 6. `HR User` joins Farm Manager's companion roles

`tools/files.py` is the one family of tools in this app that consults **Frappe's**
permissions rather than treating the bearer token as the read authorization —
deliberately, because `is_private` is a promise the framework makes about who may
see a passport scan. That check asks whether the account may read the Employee,
and a Farm Manager holding only this app's roles and the site's own `Employee`
role may read its **own** record and nobody else's. So the manager running a hire
could file a licence photograph and could not read the folder back.

**It is named as a companion role and not granted here, and that is not
timidity.** `roles.py`'s rule 1 is the most important line in the file: a Custom
DocPerm written by this app on `Employee` — a doctype Frappe HR owns — would make
Frappe ignore **every standard permission that doctype has, for every role on the
site**, silently, during `bench migrate`. `create_mobile_user` assigns a
companion role only where the site actually has it and reports the ones it does
not, so a bench without hrms enrols a Farm Manager exactly as before and says why
the folder reads will refuse.

---

## Upgrading

```bash
bench --site <site> migrate
bench restart
```

Nothing to configure. Existing enrolments keep working, every route that answered
before still answers under the same name with the same arguments, and the three
older spellings keep their routes.

**Re-run `create_mobile_user(..., update_existing=true)` for any Farm Manager who
needs to read an employee's document folder** — that is what assigns `HR User`
where the site has it. Everything else on this list works on the next call.
