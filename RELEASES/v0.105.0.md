# v0.105.0 — the feedback queue on every phone finally has somewhere to go

`fafo_ios/SERVER_CHANGES.md` item 24. One doctype, one tools module, one mobile
route, and one transport change so the form door reaches the same method the JSON
door does.

---

## The one idea

The handset half of the in-app feedback loop shipped first, and shipped complete:
a bubble on every screen, a form that captures the screen, the person, the role,
the time, the app build and the handset model **for** the worker, dictation in
English and Spanish for a crew working in gloves, and an optional screenshot.

It has been posting to a 404 ever since.

```
  before                              after
  ─────────────────────────────       ─────────────────────────────
  worker taps the bubble              worker taps the bubble
  worker says the thing               worker says the thing
    → queued on the phone               → queued on the phone
    → POST → 404                        → POST → 200
    → parked, retried in 6h             → App Feedback record
    → parked, retried in 6h             → the owner's feed
    → …                                 → the queue empties
```

---

## Publishing this route collects a backlog, not a note

**This is the requirement everything else here is shaped around**, and it is a
property of the doctype rather than a courtesy.

A 404 on this client does not **fail** a note, it **parks** it: retried every six
hours, forever, and the attempts are not counted against the give-up bound. That
is deliberate on the iOS side and it is why publishing this route collects what
the farm has already written rather than starting from empty.

So the first call that answers 200 does not receive one note. It receives weeks
of them in one burst — and it receives them **again, from the start**, if that
burst is interrupted before the phone records the acknowledgements. Which it will
be, because the burst happens the moment a pocketful of parked notes finds the
yard's wifi.

One worker's considered complaint filed three times is how a feed becomes noise
nobody reads. The whole feature would be wasted on its first day.

### Three things make the burst safe

1. **`entry_uuid` is `unique` on the doctype.** The read-then-write in the tool
   loses a race between two drains; the index does not.
2. **A resend is answered with success and the record already held.** Never a
   refusal. The app treats any non-2xx as "not filed" and would queue it again,
   so a 409 on a duplicate is indistinguishable, from the handset, from never
   having built this route at all.
3. **`UPLOAD_LIMIT`, not `WRITE_LIMIT`** — the same choice `sync_bucket_entries`
   makes and for the same reason. Ten calls a minute would refuse most of a
   backlog and send the phone away for another six hours.

## The login on a note is the one that was proved

A shared handset is normal on a farm, so the app sends its own idea of who is
holding the phone. `SERVER_CHANGES` is explicit that this is a claim rather than
proof, and asks the server to record its own authenticated caller **beside** it.

* `user` is **not on the signature**. `routes.bind` drops the body's copy and
  `guard.endpoint` injects the authenticated caller, so there is no key to send.
* `employee`, `employee_name` and `user` on the record are all resolved from that
  caller.
* What the handset claimed is kept in `claimed_employee` /
  `claimed_employee_name`, and **only where it disagrees**. Two identical columns
  on every row would hide the disagreement, which is the only reason the claim is
  worth storing at all.

`role` and `designation` are stored as sent and checked against nothing. They are
half of what the owner filters by and the server cannot reconstruct them — one
login holds several roles and only the app knows which hat was on. Nothing on
this site authorises anything off those columns, and the field descriptions say
so where somebody looking at the record will read them.

A login with **no** Employee record still files a note. `_employee` would refuse
the call, and somebody whose record has not been linked yet is exactly the person
whose feedback about being onboarded is worth reading.

## A refusal is a note parked forever, so there are only two

The ordinary instinct on this surface is to refuse anything malformed. It is the
wrong instinct here, and the reason is the same as the reason for the dedup: the
client cannot fix what it already queued, so a refusal is not a correction, it is
a note re-sent every six hours until the app is uninstalled.

The whole list of refusals is **no `entry_uuid`** and **no `comment`**. Everything
else is recorded and filed:

| what went wrong | what happens |
|---|---|
| screenshot is not base64 | `screenshot_omitted = not_base64`, note filed |
| screenshot is not an image | `screenshot_omitted = not_an_image`, note filed |
| screenshot over the 1 MB ceiling | `screenshot_omitted = too_large`, note filed |
| the `File` insert threw | `screenshot_omitted = store_failed`, note filed |
| the app dropped it at its end | its own reason is stored, note filed |
| the note is longer than the column | shortened, marked, filed |
| the company named is out of scope | falls back to the caller's own entity |

That last one is the only place this route differs from every other write on the
surface, which 403 there. `company` here is a filter column on a feedback feed
rather than a fact anything is posted against, and a 403 is a note that never
lands from a handset that will keep naming the same company forever.

The note being longer than the column is refused **at the controller** and
shortened **at the wrapper**. That is not an inconsistency: a Desk edit that hits
the cap can be corrected by whoever is making it, and a handset cannot.

Screenshots are stored as **private** `File` rows. A screenshot of the app is a
screenshot of whatever roster, wage or task list was on the screen at the time.
The extension is read off the first bytes and the stored filename is composed
from the docname, so `screenshot_filename` and `screenshot_content_type` are not
on the signature — `api/files.py`'s fourth refusal, and there is nowhere for a
caller-supplied name to land.

## Both doors reach the same method

The sidecar has been JSON-only since v0.18.0 and the shipped iOS build sends
base64 in a JSON body, which is the path that matters for draining the queue. But
a feedback endpoint that only a Swift client can post a picture to is a narrow
thing, so `farmops_api/app.py` now reads `multipart/form-data` too.

It reads it as a **translation**, not a second path. A file part is base64'd in
the transport and lands on the key its own part is named — a part called
`screenshot` arrives as `screenshot`, with `screenshot_filename` and
`screenshot_content_type` from the part's own headers — so no handler branches on
how the bytes arrived, and every method on the surface gains the door at once.

Nothing widens. `routes.bind` still reduces whatever comes out of the parser to
the keys the method declares, so a form part naming an argument no signature has
is dropped exactly as a JSON key would be. `TheSurfaceIsClosed` is unchanged and
still asserts the route table in both directions.

## The owner's half is a list view

Item 19 also asks for a feed the farm owner reads, sorted by recency and
filterable by screen and by role. Nothing on the handset depends on it, and
`SERVER_CHANGES` is specific that `screen` and `role` are sent as filterable
columns **so that feed is a list view rather than a report**.

So it is one, and it is a property of the doctype JSON:

* `sort_field: timestamp`, `sort_order: DESC` — sorted by when **Send was
  pressed**, not by when the note landed. Those are weeks apart on a farm whose
  blocks have no signal, and the newest complaint is the one most recently made.
  `received_at` keeps the other date, because the distance between them is worth
  seeing when somebody asks why nobody acted on a note.
* `screen_name` and `role` carry `in_standard_filter`, and so do `language`,
  `was_dictated`, `app_version`, `device_model`, `company`, `has_screenshot` and
  `screenshot_omitted`.
* Farm Manager gets `read`, `report`, `export`, `print` and `share` — and not
  `write`, `create` or `delete`. A note is what a worker said, and a feed the
  reader can edit is not evidence of anything.

`has_screenshot` is written by the controller from the `screenshot` field on
every save and is never set by a caller: a client that ticked the box without
sending a picture would put a note in the "has a screenshot" filter that has
none, and that note is the one nobody would ever find again.

`was_dictated` is stored because it is the measurement that says whether the
gloves-on path is used at all. Dictation was built for a crew that cannot type in
a row of trees, and this column is the only way to find out whether that was
right.

## The funnel needed nothing

Worth stating plainly, because three releases shipped silent 404s on exactly this
step. v0.58.1 mounts `/farmops` as **one prefix**, which is what makes a route
published by having been added — the mount is not the boundary, `routes.ROUTES`
is, and every route in it runs `guard.endpoint` before it does anything.

`test_every_route_is_covered_by_a_mount` asserts that property rather than a
list, so it covers `submit_app_feedback` without a line being written, and it
still fails loudly if somebody narrows the prefix back.
