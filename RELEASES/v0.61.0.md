# v0.61.0 — what the operation pays

A piece rate lived on one worker's **Farm Salary Structure**. $1.25 a bucket,
typed once per picker, a hundred times a season. Three consequences, and the
third is the one that costs money:

1. **A raise was a hundred edits.** Mid-season, mid-harvest, one structure at a
   time, with no record of who changed what or when.
2. **The question had no answer.** *What does this farm pay for a bucket* is a
   question with one answer, and the only place it was written down was a
   hundred rows that could disagree with each other.
3. **A structure created without a rate paid the minimum wage makeup and looked
   fine.** The slip balanced. The run reported no failure. The only symptom was
   a makeup figure that reads as a rate set too low rather than a rate that was
   never set at all.

This release is two registers and the order payroll reads them in.

---

## 1. Two tables, read at opposite moments

| | Keyed by | Read | Editing it |
|---|---|---|---|
| **Piecework Rate** | `(company, activity)` | on **every payroll run**, for every worker whose structure names no rate | the next run pays the new number |
| **Position Wage Default** | `(company, designation)` | **once**, when a salary structure is created | changes nothing that already exists |

**That asymmetry is the whole design, and it is not an inconsistency.**

A **piece rate is a property of the WORK**. A bucket is a bucket; the operation
pays what the operation pays; and a table that governs it live is precisely what
turns a mid-season raise into one row. `effective_from` / `effective_to` rather
than an edit in place, because a payroll for a period that ended in May must
still be able to find what May paid.

An **hourly wage is a property of the EMPLOYMENT**. It is what a person was
hired at. It is what a wage claim asks about. A table that could silently restate
somebody's agreed hourly rate for a period already worked would be a table that
rewrites history — so the default is **copied onto** the new structure and from
then on the number is that worker's, and editing the default does not reach back
through it.

Both carry `is_active` as a kill switch, and **neither has a delete tool**. A rate
that paid a period is the record of what that period paid; `is_active=false` takes
a row out of every future lookup and leaves it readable. Same posture as
`remove_authorized_signer`, for the same reason.

## 2. The lookup order

```
1. the employee's Farm Salary Structure base_rate, where it is > 0
2. the active Piecework Rate for that employee's company and activity
3. neither — and that is an error, reported by name
```

**Step 1 wins because it is the more specific record.** A rate on one person's
structure is a rate somebody negotiated with that person; a company table cannot
know about it and must not overrule it.

`> 0` rather than *is set* is what makes the fallback reachable at all.
`base_rate` is a **required** Currency field on Farm Salary Structure, so a
structure created without one holds `0.0` and not `None` — a test for `None` would
never fire on a real record.

**Step 3 is an error and not a zero.** This is the third consequence above, and
refusing is the only way to surface it: paying at zero produces a slip that
balances, a run that reports no failure, and a minimum wage makeup that looks
deliberate. `resolve_piece_rate` refuses instead, and names the company and the
activity it could not find a row for.

**What a batch run does with that refusal is not to abort.** `run_payroll_for_period`
has said since v0.35.0 that one worker's problem does not hold up everybody else's
pay — a picker with no salary structure is reported, not thrown. A picker with no
RATE gets the same treatment and lands in `employees_missing_piece_rates`. A
single-employee `preview_payroll` has nobody else to carry on for, so there the
refusal is the answer.

## 3. Which activity, when the hours do not say

Neither Bucket Log Entry nor Farm Task Assignment records what KIND of piecework a
count is — a bucket row is a bucket, full stop. So the activity comes from the
salary structure, which gains an optional **`piecework_activity`**: the worker's
half of the `(company, activity)` pair, in the same vocabulary `ML Model` already
uses.

**Where a structure names none, one unambiguous company rate is used and several
are refused.** That is not a guess — it is the observation that a company with one
piecework rate in force has already answered the question and a company with three
has not. The refusal lists the candidates, because

> set `piecework_activity` on this structure to one of: `bucket_segmentation`,
> `thinning`

is an instruction somebody can act on and *"no rate found"* is not.

Activities are compared case-folded, with spaces and hyphens read as underscores.
`Bucket Segmentation` typed into the Desk and `bucket_segmentation` posted by the
iPad are the same activity, and a rate table that paid one and not the other would
be a rate table that failed on a capital letter.

## 4. A raise is a new row

`select_effective` gives the row with the **latest `effective_from` that covers the
date**. Add a row from 1 June, leave the old one open-ended, and June onwards pays
the new rate without anybody having to remember to close the old one — while the
old row goes on explaining the periods it paid. `create_piecework_rate` names what
it superseded.

`update_piecework_rate` is for a rate **typed wrong**, and says so loudly whenever
the rate moves on a row that has already been in force: any re-run over a period
inside that window will now compute a different number than it did.

**At most one ACTIVE row per `(company, activity, effective_from)`**, enforced by
the controller so it holds whichever door a save came through. Two rows starting
the same day for the same activity are not a raise — they are two answers to one
question, and `select_effective` would have to break the tie on a docname. A rate
that depends on which row was created first is a rate nobody can predict.

`company` and `activity` cannot be edited on an existing row: they are the pair
every lookup resolves by, and moving one would restate which workers a period was
paid under.

## 5. Eight tools

| Tool | Default | |
|---|---|---|
| `list_piecework_rates` | **on** | every rate, plus `in_force` — the one row per (company, activity) a run dated `on_date` would read |
| `get_piecework_rate` | **on** | one rate, whether it is the live row, and what covers `on_date` instead if not |
| `list_position_wage_defaults` | **on** | every default, plus what a structure created on `on_date` would be seeded from |
| `get_position_wage_default` | **on** | one default, and whether it is the row a new hire in that job starts on |
| `create_piecework_rate` | off | sets what a unit pays from a date; also how a raise is made |
| `update_piecework_rate` | off | corrects a rate typed wrong, or retires it |
| `create_position_wage_default` | off | sets the default hourly rate for a job title from a date |
| `update_position_wage_default` | off | edits or retires a default; seeded structures are untouched |

`wage_defaults.py` holds the ORDER and **touches no database at all** — it takes
rows and returns answers, the same discipline `budget_engine.py` and
`model_registry.py` keep, so the ordering is testable without a bench and the same
functions serve the doctype controllers, the MCP tools and the payroll run.
`tools/wagedefaults.py` is the only place that reads or writes either doctype.

## 6. What payroll now reports

| | |
|---|---|
| `create_salary_structure` | takes `piecework_activity`; seeds `hourly_rate` from the position wage default; **accepts `base_rate` 0 on a Piece Rate structure** and checks at creation that the inheritance resolves — a structure that would fail on payday fails in front of the person creating it |
| `get_salary_structure` | `effective_rate` and `rate_source`, because a read that showed the zero and stopped would be a read that says a picker earns nothing |
| `list_salary_structures` | `inheriting_company_piecework_rate` — flagged, not resolved: one rate-table read per company per list call buys nothing `get_salary_structure` cannot answer |
| `preview_payroll` | `piece_rate_source`, the rate's docname, and a sentence saying where the number came from |
| `preview_payroll_for_period`, `run_payroll_for_period` | **two lists, because they are opposite facts** — `piece_rates_from_company` is the fallback working, `employees_missing_piece_rates` is the fallback finding nothing |

Every optional column goes through `compat.existing_fields`, so a site that has
not run `bench migrate` yet reads exactly as it did before and the fallback is
simply unreachable there rather than an exception on payday.

## 7. Permissions

**Farm Manager: read and write. Compliance Officer: read. Neither may create.**

No name appears on either row. These are not somebody's pay — they are what the
OPERATION pays for a bucket and for an hour of a job title, which is the thing a
manager is actually asked about in a packing shed at six in the morning. That is
what makes the tables safe in front of a role that cannot read Farm Salary
Structure and still cannot.

The `create` distinction looks pedantic until you notice what it means here.
Adding a row is **how a raise happens** — one insert changes what the whole
company's next payroll pays, for everybody on that activity, with no second party
to it. Editing an existing row is bounded by comparison: the rate was already set
by somebody who could set rates, and a manager fixing a typo is fixing this
season's number rather than opening next season's. So the person who runs the
operation may correct the table, and the person who sets what the operation pays —
System Manager or HR Manager, through the doctypes' own standard permissions — is
who adds to it.

The Compliance Officer's read is one they need rather than a courtesy: the piece
rate is the input to the minimum wage makeup on every slip, and *was the rate high
enough that these hours cleared the floor* is an ORS 653.025 / RCW 49.46.020
question that cannot be answered from the slip alone. They may not touch either
table — the officer who checks whether a rate was lawful must not be the account
that set it.

---

## Upgrading

```
bench --site <site> migrate
```

**Nothing changes for a site that creates no rows.** Every existing salary
structure names its own rate, step 1 of the lookup answers every time, and the
fallback is never reached. The tables start empty and take effect the first time
somebody adds a row.
