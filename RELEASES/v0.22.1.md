# v0.22.1 — the vocabulary reaches its own problem domain

**v0.22.0 shipped six declarative rules, seven built-in scanners and zero
`custom_python`, and its §5 named the four primitives that would move most of the
seven. This release built them. Five rules moved. Two did not, and this release
says permanently rather than later.**

Tool surface **unchanged at 256** (113 read, 143 mutating). Suite **4,187 →
4,277 passing**. Ten new columns on one existing DocType, one new scope-filter
operator, one migration patch, and **behaviour drift of zero** — asserted per
rule, against the shipped scanners themselves.

The split is now **11 declarative / 2 built-in-permanent / 0 `custom_python`**.

---

## 1. Why a point release, and why this one

The v0.22.0 notes ended with a ranked backlog and a claim: that the seven
remaining built-in scanners were not evidence of a framework that had run out of
ideas, but a list of primitives somebody had not written yet. A backlog is a
cheap thing to write. This release is the part that makes it a claim rather than
a hope.

It also settles the harder half. Two of the seven are argued here as **permanent**
built-ins — not "not yet", not "when somebody has time". Being able to say which
questions do not belong in a rule record is what stops a configuration vocabulary
growing until it is a programming language nobody reviewed.

---

## 2. The four primitives

### `superseded_by_later_clean_json` — the gate about *other rows*

**Took two rules declarative.** `housing_corrective_action_open` and
`water_test_contamination` share one gate: *is this finding still true?* It stops
being true when a later clean record for the same subject supersedes it — a cabin
re-inspected in September with nothing found says more about July's water stain
than a checkbox does, and it requires nobody to remember a field.

```json
{
  "subject_field": "unit",
  "clean_state_field": "workflow_state",
  "clean_state_values": ["Recorded"],
  "unreadable_counts_as_dirty": true
}
```

`doctype` and `date_field` default to the target's, which is what lets one rule
walking two doctypes supersede each on its own date column.

`unreadable_counts_as_dirty` defaults to **true** and the default is the point: a
record whose state is empty or unreadable does **not** supersede. A result nobody
can interpret is not evidence that the water is safe, and treating it as clean is
how a compliance file becomes a clean record of nothing.

The index is built **once per sweep** and folded to a per-subject list, not
queried per candidate. Fifty cabins and four years of history is two queries, not
four hundred — and that is an argument for the field over the escape hatch, where
the obvious way to write this is the per-row query.

### `regime_heuristics_json` — an ordered lookup on a *name*

**Took `certification_expiring` declarative.** `regimes_from_field` copies tags
off a column. Here there is no column, only a name to read: a certificate's
audits come from its TYPE through an ordered eleven-row table.

```json
[
  {"if_field_contains": {"field": ["cert_type", "cert_name"], "value": ["wps", "worker protection"]},
   "then_regimes": ["WPS"]},
  {"if_field_contains": {"field": ["cert_type", "cert_name"], "value": ["globalgap", "global gap"]},
   "then_regimes": ["GlobalGAP"]},
  {"if_field_contains": {"field": ["cert_type", "cert_name"], "value": ["gap"]},
   "then_regimes": ["GAP"]},
  {"default_regimes": ["Internal"]}
]
```

**First match wins and the order is the whole content**: `globalgap` before
`gap`, because "GlobalGAP" contains "GAP" and a USDA GAP packet must not be
handed another scheme's certificate.

**Where entries name several fields, the field order is the OUTER loop** — the
whole table is tried against `cert_type` before any of it is tried against
`cert_name`. That is not an implementation detail. A certificate typed "Food
Safety Training" and named "WPS refresher" is a food-safety certificate, and a
table that scanned entry-first would retag it from a word somebody typed on the
day. The legacy Python read the type first and the name only as a fallback; the
data structure now says so.

The heuristics say what an **alert** is. The rule's own `regimes` stays the
**union** of what the table can emit, because that is what a one-regime sweep
matches on to decide whether the rule has to run at all. Two questions, both
answered, on one record.

The table is **derived from `CERT_REGIME_HEURISTICS` in `rules.py`** rather than
restated beside it, so a needle added there reaches the seeded rule without
anybody remembering to copy it.

### `gate_date_field` + `gate_within_days` — a second date, used only as a gate

**Took `water_test_stale` declarative.** The engine has one cadence anchor; this
rule's gate is a conjunction over two independent dates — the block was sprayed
inside the season **and** its water was tested outside the cadence — and neither
half fires alone.

**A row whose gate date is empty is gated OUT**, and the asymmetry with
`missing_date_behaviour` is the interesting part. No inspection ever recorded is
the most overdue cabin there is; no spray ever recorded is the *least* urgent
block there is. Subpart E is engaged by water contacting a crop and not by a date
passing, so the gate is a claim that the condition matters now — and no date is
no claim.

`gate_scope: "Latest Related"` reads the newest date off another doctype pointing
back at the row, for a site keeping a spray *log* rather than a spray *column*.
Same one-query-per-sweep fold as the supersession index.

### `date_fields_json` — several anchors of the same kind

**Took `housing_detector_test_stale` declarative.** A cabin has a smoke detector
and a CO detector, tested independently; either being stale fires, and the
message must name which.

```json
[{"field": "smoke_detector_last_test", "label": "smoke"},
 {"field": "co_detector_last_test", "label": "CO"}]
```

The severity folds to the worst of them. The template is handed `stale_dates` —
**only** the fields that actually reached a band — so a cabin whose smoke test is
current and whose CO test is four hundred days old produces one alert naming the
CO detector and not the other. "The CO detector was last tested 400 days ago" is
a different errand from "no smoke detector test has ever been recorded", and an
alert saying only "a detector is overdue" sends somebody to test the wrong one.

## 3. Three things the four turned out to need

Each of these came out of an actual migration rather than out of the plan, and
each is small.

- **`date_field_role`** (`Clock` / `Timestamp`). A finding's date is *when the
  thing was found*, not a deadline. Left as a clock, a corrective action recorded
  today has zero days remaining, reaches no band on a rule whose thresholds are
  negative, and **silently stops firing on exactly the day somebody needs to see
  it**. `Timestamp` reads the date for the message and for the supersession test,
  bands nothing, and raises every matching row — including one with no date at
  all, because a finding nobody dated is still a finding.
- **`target_doctypes_json`**. `housing_corrective_action_open` walks Housing
  Inspection *and* Detector Test under one `rule_id`, deliberately: a cabin with
  a water stain and a cabin with a dead CO detector are the same conversation
  with the same person on the same walk round the camp. Two rule_ids would be two
  lists for one afternoon — and would change every alert docname on every site.
  `target_doctype` stays singular by design; this is the exception, with a
  per-entry `label` so the message says "the detector test" rather than
  "Detector Test".
- **`category_heuristics_json`**. The same ordered shape producing the alert's
  category. One rule fires on eleven kinds of certificate; an applicator licence
  is a Workforce item and a GlobalGAP certificate is a Certifications one, and a
  constant on the rule would file most of them under the wrong heading.

And one new **scope-filter operator**: `istrue` / `isfalse`, the only correct way
to filter on a Check box. A Check read back before it has been through the
database layer carries the *string* `"0"`, which `isnotnull` — and every other
truthiness test — calls true. On the rule that needed it the wrong answer is
"this shed is a worker facility", which puts a building nobody sleeps in on the
camp's inspection list.

## 4. One bug the migration found

`_band` checked the critical threshold **before** the outer window. That is
indistinguishable from the shipped scanner until the per-row window
(`window_field`) is *narrower* than the rule's critical threshold — a certificate
whose issuing body turns renewals round in ten days, sitting twenty days out.
The scanner said nothing; the declarative engine would have said Critical.

The window is now checked first, which is what the Python always did. The window
is the claim about when the work can usefully start, and nothing inside the rule
outranks it. No shipped rule's behaviour changes — none has a critical threshold
without a wider warning window — and the parity tests would not have caught it
without a fixture written for it, which is why one exists
(`TheOuterWindowOutranksTheCriticalBand`).

## 5. The two that stay built-in, permanently

**`audit_action_overdue`** walks an Audit Event's corrective-action child rows,
keeps the overdue ones, picks the worst, takes its severity from that finding's
own severity, and raises **one alert per audit** — five open items on one
PrimusGFS audit are one conversation with one auditor, and five rows would look
like five problems. Every part of that is an aggregation, and an aggregation is
not a filter. The primitive would be a second engine: group-by, fold, pick. That
is a fair description of "write it in Python".

**`supervisor_review_lapsed`** walks a *table* of doctypes rather than one; its
condition is an `OR` of two nulls and scope filters are ANDed deliberately; and
its clock runs on `creation` because §112.161(b)'s own words are "after the
records are made". The strongest argument is the one about the numbers: this
rule's thresholds mean days **elapsed**, not days **remaining**. A number on a
record that means the opposite of what the same number means on the other twelve
is a number somebody will eventually misread — and `date_field_role` deliberately
did not grow a third value to paper over it. Two readings of a date field is a
choice; a third that inverts the sign of every threshold beside it is a trap.

Both keep every tunable on their record. Only the shape of the join is code, and
it is code that was reviewed, tested and shipped.

**Two out of thirteen is the honest measure of a vocabulary**: wide enough that
the exceptions can be named, narrow enough that naming them is worth doing.

## 6. Backward compatibility, proven per rule

`test_ccf_primitives.TheMigrationOfEachRuleChangesNothing` runs each of the five
migrated rules twice on a fixture built to make that rule speak in as many of its
shapes as it has — once with the rule pointed at its **shipped scanner**, once
with it pointed at its declarative definition — and compares the alert rows field
by field: docname, severity, category, company, source, message, due date, first
seen.

**The oracle is the shipped code, not a pasted expectation.** The scanners are
still in the app as the pre-migration fallback, so the comparison is against what
v0.22.0 actually ran rather than against a file somebody transcribed a run into
and which nothing then keeps honest.

`test_e2e_workflow.TheWholeSweepSaysWhatItSaidBeforeTheRulesBecameData` then does
it once over a whole operation with all thirteen rules running together, because
the interesting failures of a migration like this are not inside one rule — they
are two rules that used to read a doctype in a particular order, or a category one
rule wrote and another defaulted.

**Behaviour drift: zero.** Every alert docname, severity, category, due date and
word is what it was.

Also unchanged: the six rules that were already declarative, the two permanent
built-ins, the `list_compliance_rules` return shape, and every existing test in
`test_alerts.py`, `test_inspections.py`, `test_regimes.py` and `test_dispatch.py`
— none was modified.

## 7. The upgrade a v0.22.0 site actually gets

**The seeder cannot perform this migration, and that is the same property that
makes it safe.** `seed_compliance_rules` leaves alone anything already on the
site — the reason an operator's raised threshold is not corrected back on every
upgrade — so a v0.22.0 site's `certification_expiring` row, which names a
built-in scanner, would never be looked at again.

`patches/migrate_declarative_rules.py` does it deliberately:

- **operator edits survive.** Everything both shapes share is carried across from
  the row on the site: thresholds, severities, cadence, citations, regimes,
  retention, packets, producer recipe, approval, switch. A site that contracted
  its annual detector cycle at ten months still has ten months.
- **`scope_filters` is concatenated, not replaced.** In v0.22.0 a built-in seeded
  with an *empty* filter list because its scoping lived in the scanner, so
  anything in that column was added by an operator on top. Replacing the list
  would silently widen a rule somebody deliberately narrowed.
- **`extra_parameters.spray_season_days` is read across into `gate_within_days`.**
  It lived there because v0.22.0 had no column for it; a site that tuned its spray
  season would otherwise have that tuning quietly ignored by the new gate. The key
  stays in `extra_parameters` too, so anything reading it by name still works.
- **the old row is superseded, not edited** — an alert raised last April can still
  be read against the definition that raised it, and a sweep already running
  against v1 finishes against v1.
- **a rule somebody switched off stays off.**

Listed in `patches.txt` **and** called from `after_migrate`, the same
belt-and-braces `migrate_training_types` gets, and a no-op the second time: the
check is "does this row still name a scanner". A rule it could not migrate keeps
its built-in scanner — which still ships, still runs and still raises exactly the
same alerts — and is named on the console.

## 8. No new tools

The surface stays at **256**. Every one of the ten new columns is reachable
through the tools that already existed:

- `list_compliance_rules` — return shape unchanged, `shape` now reports
  `declarative` for five more rules;
- `get_compliance_rule` — `definition` carries every new primitive, and reports
  an **empty** rather than a null for the ones a rule does not use, because an
  operator reading two rules side by side should not have to know that a blank
  column and an empty list are one thing;
- `create_compliance_rule` / `update_compliance_rule` — accept all of them as
  optional arguments, validated by the same parsers the DocType and the seeder
  use, so a malformed blob is refused at whichever door it arrives at;
- `test_compliance_rule` — evaluates them on the same code path the sweep takes.
  A rule with a supersession test dry-runs to one observation before the clean
  record exists and to zero after it, which is exactly what an operator is
  checking: that the rule goes quiet by itself.

**Every parser accepts its own output.** These columns are parsed on save,
stored, and parsed again on every sweep — a parser whose output it could not read
would be a rule that validates once and then quietly matches nothing, which is
the worst failure available to a compliance rule. The heuristic tables are also
normalised back into the vocabulary they were written in, so the stored JSON uses
the same words the documentation does.

## 9. Judgment calls

- **Primitive composition, and the order of evaluation.** Scope filters, then the
  gate date, then supersession, then the clock — and the order is documented as
  contract rather than left to read off the code. It is not only a performance
  ordering: running supersession before the scope filters would mean a rule
  narrowed to one company reading another entity's records to decide what it can
  see, which is the kind of thing nobody notices until an auditor asks why an
  alert went quiet.
- **`regime_heuristics_json` versus the rule's static `regimes`.** They are not in
  competition and both are kept. The heuristics decide what an *alert* is tagged
  with; the static list is the *union* of what the rule can emit, and is what
  `refresh_compliance_alerts(regime=…)` matches on to decide whether the rule
  runs at all. Dropping the static list would make a one-regime sweep skip the
  rule that would have produced the alert.
- **Field order as the outer loop.** The alternative — evaluate each table entry
  against every field it names — is the obvious implementation and is wrong. It
  would let a certificate's free-text *name* override what its *type* already
  said. The engine's loop reproduces the legacy Python's reading, and a test pins
  it with the exact case that distinguishes the two.
- **`gate_related_table_json` at scale.** Read once per sweep, per rule, capped at
  `SCAN_CAP` (2,000) and folded to a per-subject maximum in Python — the same
  shape as the supersession index. A per-candidate query would have been simpler
  to write and is the failure mode that makes people reach for `custom_python`
  and then blame the framework for the night the sweep took. The cap is real: a
  site past it is a site this rule set is not shaped for, and `RULE_CAP` on
  observations would have bitten first.
- **Ten columns rather than four.** The plan scoped four primitives. Three more
  fields and one filter operator came out of the migrations themselves, and each
  is on the record because the alternative was a behaviour change: without
  `date_field_role` the two supersession rules stop firing on the day a finding is
  written; without `target_doctypes_json` half of `housing_corrective_action_open`
  disappears; without `category_heuristics_json` every applicator licence moves
  shelf on the calendar; without `istrue` a shed becomes a bunkhouse.
- **The shipped scanners stay in the app.** All thirteen, including the five now
  unused by any seeded rule. They are the fallback a site runs before it has
  migrated the DocType — the thing that stops the calendar going blank during an
  upgrade — and they are now also the parity oracle. Deleting them would have
  made the release look tidier and the proof weaker.
- **`custom_python` still ships used by nothing**, and §4 of the framework doc now
  answers "when should I reach for this" with a table of eleven questions that
  are already fields. The honest remaining uses are aggregations and arithmetic
  across three or more columns, and the first of those is exactly what
  `audit_action_overdue` is — which is in Python, reviewed, rather than in a text
  field.

  edits.
