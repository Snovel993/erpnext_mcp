# v0.18.1 — the Employee register, because a working credential is not a working task board

**Released:** 2026-08-02 · **Previous:** [v0.18.0](v0.18.0.md)

v0.18.0 got a phone all the way through. The funnel answered, the credential
verified, `get_current_user_context` returned JSON, and then `list_my_tasks`
refused the account with:

> This account has no Employee record. Set `user_id` on their Employee record to
> this email address.

**The refusal is correct.** Every Farm Ops method scopes work by **Employee**,
not by User: a task board is a list of what a *person* is assigned, and the
Employee record is the only thing on a Frappe site that says which person a login
belongs to. An account with no Employee behind it has nothing to be shown.

**What was wrong is that there was no way to fix it from here.** This app could
create the User, one of six mobile roles, a Company User Permission per entity,
the Mobile Access Grant, the API credential and the login QR — **six things** —
and could not create, edit or link the **one** record that makes the other six
useful. Same-session onboarding of a mobile user hit a data-setup wall and the
only way over it was to leave the conversation and open a Desk form.

This release is those three tools, plus the orchestrator step that was missing.

---

## The four tools

### 1. `create_employee`

```
create_employee(
  employee_name,            # required — first and last
  company,                  # required — validated against what you can see
  first_name = <first token of employee_name>,
  last_name  = <last token of employee_name>,
  date_of_joining = <today>,
  date_of_birth, gender, department, designation, employment_type,
  status = "Active",
  user_id, personal_email, cell_number,
  allow_unenrolled_user = false,
  allow_duplicate_name  = false,
) -> { employee, fields_set, defaults_applied, fields_not_on_this_site, linkage }
```

**Fourteen fields, and everything else refused by name.** Identity and assignment
only. Payroll, tax and banking fields — salary structure, income tax slab, CTC,
bank account, provident fund — get their **own** refusal, because each has a
form, an approval and a retention rule this app knows nothing about. A tool that
set `ctc` because the number appeared in a sentence would be a tool that quietly
moved money.

A field that is real on this site but outside the fourteen gets a *different*
refusal from a field that does not exist at all. Those are different mistakes.

**The schema is asked, never assumed.** Every Link is checked against this site's
own records and the refusal lists what is actually there
(`Known Department: Administration, Operations`). Every Select is matched
case-insensitively against this site's own options and stored in the site's
casing, so a list-view filter finds it. A Link whose target doctype is not
installed here is **not** validated rather than refused — the value cannot be
checked against a schema that is absent, and Frappe does not validate it either.

**A field this site's Employee doctype does not carry is reported, not swallowed**
(`fields_not_on_this_site`). A tool that quietly dropped a value would report
success for nothing having happened.

**Mandatory fields are the site's, not this file's.** Stock Frappe HR marks
`gender` and `date_of_birth` **required**; plenty of operators clear that. The
tool reads `reqd` off `frappe.get_meta` and refuses *before* the insert with a
sentence naming the fields, instead of handing back a controller's
`MandatoryError`. → **See "One thing to check on your site" below.**

**It refuses a second record** for the same name at the same company, naming the
one that exists. Two Employee records for one person puts them on the dispatch
board twice and in the payroll register once. The same name at a *different*
entity is a second record on purpose. `allow_duplicate_name=true` covers two real
people with one name.

### 2. `update_employee`

```
update_employee(
  name,                     # docname, employee number, employee name, or the linked login
  ...the same fourteen fields...,
  replace_user = false,
  allow_unenrolled_user = false,
) -> { employee, changed: [{field, from, to}], unchanged, linkage }
```

Same allowlist, same refusals, same schema checks. **Reports field by field what
actually moved, with the previous value** — a value that was already what you
asked for lands in `unchanged` rather than being reported as a write.

Re-pointing an Employee at a different login needs `replace_user=true`: it moves
that person's whole task history with it.

### 3. `link_employee_to_user`

```
link_employee_to_user(
  employee_name,            # docname, employee number, name, or a login already on it
  user_id,
  replace_user = false,
  allow_unenrolled_user = false,
) -> { employee, user_id, action, linkage: {farm_ops_ready, …}, note }
```

**It reports whether the phone will now work, not whether the field was written.**
`linkage.farm_ops_ready` is true only when all three hold:

| | Condition | Fixed by |
|---|---|---|
| 1 | the account holds a Farm Ops role (Field Worker / Foreman / Farm Manager) | `create_mobile_user` |
| 2 | its Mobile Access Grant is **Active** | `create_mobile_user(update_existing=true)` |
| 3 | the Employee is **Active** | `update_employee(status="Active")` |

When it is false the `note` says *which* of the three is missing and which tool
fixes it. "The link was written" was never the fact anybody wanted.

**One person, one login, in every direction.** Refused when the User already
belongs to another Employee — two records naming one login gives `list_my_tasks`
two answers where it needs one. Refused when this Employee already has a
different login, unless `replace_user=true`. **A no-op that says so** when the
link already says exactly what you asked for, which is what makes re-running an
orchestration safe.

**Refused for a User with no Farm Ops role and no grant.** The link's entire
purpose is to make the mobile methods answer; a User who cannot reach them is a
link that changes nothing today and silently grants a task board on the day
somebody grants that account a role for an unrelated reason.
`allow_unenrolled_user=true` is the deliberate escape, and it is real — linking
ahead of the enrolment is a legitimate order of operations.

### 4. `onboard_employee` — the orchestrator, with the step it was missing

**It already existed** (v0.17.1). What it lacked was the link, and what it had was
an ordering bug.

**THE ORDERING BUG.** Until now it created the Employee with `user_id` **already
filled in** and *then* created the User. `Employee.user_id` is a Link to User, so
on a real bench Frappe validates it on insert and the very first step raises —
**any onboarding that named an email could not complete at all.** The standalone
suite modelled that field as plain `Data` and called it a pass. v0.18.1 models it
as the Link it is, which is what turned a live failure into a failing test.

The order is now the only one that can work:

1. **the Employee**, with no login on it yet — delegated to `create_employee`, so
   the allowlist, the schema checks and the mandatory-field message are the same
   code you get calling that tool by hand
2. **the paperwork**, still filed **privately on the Employee record** and never
   in the governance archive — unchanged, and still asserted against the parsed
   module rather than against behaviour
3. **the scoped mobile account** — `create_mobile_user`
4. **the link** — `link_employee_to_user`
5. **the QR**, on request (`issue_qr=true`)
6. **the first-day tasks**, on request

**Fully idempotent.** A second run with the same arguments finds the Employee (by
login, then by name and hiring company), finds the account, finds the link
already made, and reports each as reused. Nothing is duplicated. The one thing a
re-run does differently is mint a fresh QR — and only when asked, because issuing
a credential twice is the point of asking twice.

**`issue_qr` defaults FALSE, deliberately.** Minting a QR rotates the account's
API secret, so a default-true would mean re-running an onboarding to add a W-4
silently knocked a phone already in somebody's pocket offline.

**What comes back is the image, not the payload.** `png_base64`, `expires_at`,
`endpoint`, `grant` — and *not* the decoded payload, which carries `api_secret`
as readable text. The PNG encodes the same secret unavoidably, because that is
what enrolment by QR *is*; the difference is that nobody pastes a PNG into a chat
window by accident.

## Tim — the exact call for your situation

`list_employees` on Orchard Meadow, LLC returns **zero records**, so there is
nothing to link to yet. It is `create_employee`, not `link_employee_to_user`:

```
create_employee(
  employee_name = "Tim Polehn — Mobile",
  company       = "Orchard Meadow, LLC",
  user_id       = "tim.polehn+mobile@gmail.com",
)
```

Two ways this can come back other than a docname:

- **"…has no Farm Ops role and no Mobile Access Grant"** — the login exists but
  was never enrolled. Run `create_mobile_user` for it first, or add
  `allow_unenrolled_user=true` to link ahead of the grant.
- **"this site's Frappe HR marks gender, date_of_birth mandatory on Employee"** —
  see the next section. Pass them:

```
create_employee(
  employee_name   = "Tim Polehn — Mobile",
  company         = "Orchard Meadow, LLC",
  user_id         = "tim.polehn+mobile@gmail.com",
  gender          = "Male",
  date_of_birth   = "1900-01-01",
)
```

If an Employee record **does** already exist by the time you read this:

```
link_employee_to_user(
  employee_name = "<existing docname or name>",
  user_id       = "tim.polehn+mobile@gmail.com",
)
```

Either way, read `linkage.farm_ops_ready` in the response. `true` means
`list_my_tasks` will answer on the next pull-to-refresh. `false` means the `note`
tells you which of the three conditions is still missing.

## One thing to check on your site, rather than something I invented

**Every field named in the brief exists on Frappe HR's Employee doctype.** Nothing
had to be invented. But two of them behave differently from how the brief
described, and both are worth knowing before you call the tool:

1. **`gender` and `employment_type` are Links, not free text.** `gender` points at
   the **Gender** doctype and `employment_type` at **Employment Type**. So does
   `department` (Department) and `designation` (Designation). The brief expected
   this for department, designation and employment type, and described `gender` as
   "must match Gender doctype values" — which is exactly right. What follows from
   it is that a site which never installed HR's masters has **no Employment Type
   records at all**, and the tool will say so by name rather than accepting a
   string that Frappe would reject a layer down.

2. **`gender` and `date_of_birth` are `reqd: 1` on a stock Frappe HR Employee**,
   and the brief listed both as optional. They may well be optional on your site —
   whether a field is required is an operator's setting, not a property of the
   app — so the tool does not carry its own opinion. It reads `reqd` off
   `frappe.get_meta("Employee")` at call time and, if this site wants them,
   refuses **before** writing anything with:

   > this site's Frappe HR marks gender, date_of_birth mandatory on Employee, and
   > the call did not supply them. Which fields are required is an operator's
   > decision on the doctype, not this app's: pass the values, or clear the `reqd`
   > flag in the Desk. Nothing was created.

**No `farm_i9` or `farm_hr` app exists in the Development Comms Folder.** The
brief asked to delegate to their Employee creation flows if they had any; there
is nothing to delegate to. The two farm apps present are `farm_app` (the FastAPI
server) and `farm_app_scanClock` (iOS), neither of which owns an Employee
register. If either grows one, `create_employee` is the single place to route
through it — `onboard_employee` already delegates there rather than duplicating,
so there would be exactly one call site to change.

## Security

Every one of the three new tools goes through the same gates as the rest:

| Gate | How |
|---|---|
| **Kill switch** | `allow_create_employee`, `allow_update_employee`, `allow_link_employee_to_user` on ERPNext MCP Settings. All three **default OFF**, per the mutating-tool rule. |
| **Role gate** | System Manager, HR Manager, HR User or Farm Manager on the principal this app acts as. The refusal names the account *and* the roles, because permission denied on a principal the operator chose themselves is a one-line fix they cannot make without knowing which line. |
| **Company scope** | Refuses a company the principal cannot see. Frappe's own rule applies — no User Permission means unrestricted — which is deliberately the *opposite* of `api/guard.accessible_companies`, and `docs/security.md`'s argument for that difference is unchanged: the mobile surface faces the open internet with a closed list of callers, where fail-closed is affordable; a personnel tool that refused every correctly-configured operator would be switched off within the hour. |
| **Audit** | Every call — success, refusal and error — gets an MCP Action Log row through `registry.dispatch`, with the docname in `result_summary`. There is no second row, because a duplicate is noise in the log an operator actually reads. |
| **Enrolment gate on links** | Read from `api/guard.FARM_OPS_ROLES` rather than re-listed, so the set this file refuses against and the set the eleven mobile methods gate on cannot drift apart. There is a test asserting they are the same object. |

## Tests

**78 new tests** in `tests_standalone/test_employee.py`, across seven claims:
creating the record, the schema as arbiter, what it refuses to write, the guards,
updating, linking, and onboarding end to end — plus the module's own closed-list
assertions.

**Suite total: 3,474, all passing** (was 3,396).

Two changes to the double are worth calling out, because both turned a silent
pass into a real check:

- **`Employee`'s six Links are now modelled as Links** (`company`, `department`,
  `designation`, `employment_type`, `gender`, `user_id`). `user_id` is the one
  that mattered: modelled as `Data`, it let `onboard_employee` insert an Employee
  naming a User that did not exist yet and the suite called that a pass. This is
  the same class of gap `ERPNEXT_FIELD_LINKS` was created for in v0.12.1 and that
  `_validate_selects` closed for Selects in v0.16.1.
- **`Employee.status` now carries its four options**, and the seven personal
  fields (`first_name`, `last_name`, `gender`, `date_of_birth`, `personal_email`,
  `cell_number`) were added to the doctype's field list — without them,
  `compat.has_field` would have dropped every value the new tool wrote and the
  tests would have asserted against nothing.

The four HR master doctypes (Department, Designation, Employment Type, Gender)
are seeded by `install_hrms()`.

## Deploy

**No DocType, no new dependency, no schema patch** beyond three Check fields on
the settings Single — which `bench migrate` picks up and `seed_defaults` fills in
as **off**.

### 1. Push, then build

The Dockerfile cache-busts on the **pushed** commit. A local-only commit leaves
the layer cached, you build the old code, and nothing tells you.

```sh
cd "~/Desktop/Development Comms Folder/erpnext_mcp"
git push origin main
```

```sh
cd "~/Desktop/Development Comms Folder/fafo-umbrel-store/fafo-erpnext/build"

docker build \
  --build-arg ERPNEXT_MCP_VERSION=0.18.1 \
  --no-cache \
  -t polehntim/erpnext-umbrel:15 \
  .

docker push polehntim/erpnext-umbrel:15
```

> Check the platform flag against what your Umbrel runs — add
> `--platform linux/amd64` or `linux/arm64`.

### 2. Pull and restart

The compose did not change this release, so a restart is enough:

```sh
sudo docker pull polehntim/erpnext-umbrel:15
umbreld client apps.restart.mutate --appId fafo-erpnext
```

### 3. Migrate — required this time

Three new settings fields:

```sh
sudo docker exec -u frappe fafo-erpnext_server_1 \
  bench --site frontend migrate
```

### 4. Turn the three switches on

They ship **off**. Either in the Desk (ERPNext MCP Settings → Mobile write
section) or:

```sh
sudo docker exec -u frappe fafo-erpnext_server_1 bench --site frontend console
```

```python
doc = frappe.get_single("ERPNext MCP Settings")
doc.allow_create_employee = 1
doc.allow_update_employee = 1
doc.allow_link_employee_to_user = 1
doc.save()
frappe.db.commit()
```

### 5. Confirm they are advertised

```sh
sudo docker exec -u frappe fafo-erpnext_server_1 \
  bench --site frontend execute erpnext_mcp.registry.tools_list \
  | grep -c employee
```

Or, from the MCP client, just call `create_employee` — a tool that is switched
off says so by name and tells you which box to tick.

### 6. The end-to-end check

```
create_employee(employee_name="Tim Polehn — Mobile",
                company="Orchard Meadow, LLC",
                user_id="tim.polehn+mobile@gmail.com")
```

then pull-to-refresh on the phone. `list_my_tasks` should return a list rather
than a banner.

### Rollback

Untick the three switches. Nothing else in the app changed behaviour — except
`onboard_employee`'s step order, which was previously broken on any real bench
for the case that named an email, so there is nothing there to roll back to.

## HR MCP Roadmap

**User and Employee data management is a standing role for this server, not a
one-off patch.** The four tools above are the START of that pattern — enough to
unblock a phone — and not the complete answer. This section exists so the rest
does not have to be re-requested item by item, and so it can be prioritised by
reading rather than by remembering.

### The rule the roadmap is written under

**Every doctype `farm_hr` adds gets a corresponding MCP tool in the same
release. No Desk-only workflows.** A record an operator can only reach through a
Desk form is a record this server cannot help with, cannot audit through MCP
Action Log, and cannot include in a compliance packet — and the whole argument
for v0.18.1 is that "leave the conversation and open a form" was the wrong answer
once already.

**Every tool below wears the same five guards as the three above**, and none of
them is optional:

| | Guard | Where it comes from |
|---|---|---|
| 1 | **Role gate** — System Manager, HR Manager, HR User or Farm Manager | `employee.require_hr_role()` |
| 2 | **Company scope** — refuses an entity the principal cannot see | `employee.require_company_scope()` |
| 3 | **Kill switch** — `allow_<tool>` on ERPNext MCP Settings | `registry.dispatch` |
| 4 | **Audit row** — success, refusal and error alike | `registry.dispatch` → `audit.record` |
| 5 | **Mutating, default OFF** | `_tool(..., mutating=True)`, and NOT in `DEFAULT_ON_MUTATING_TOOLS` |

A sixth applies to anything touching the personnel file: **the fourteen-field
allowlist is the model.** New writers declare what they write, refuse the rest by
name, ask this site's schema rather than assuming it, and keep payroll, tax and
banking behind the HR module's own approvals.

### Expected, in no fixed order — prioritise as you read

| Tool | What it is for | The hard part, noted now |
|---|---|---|
| **`disable_employee(name, effective_date, reason)`** | Offboarding. Sets status and relieving date, and records WHY. | `reason` is mandatory and load-bearing, exactly as it is on `revoke_mobile_user`: "left at the end of harvest" and "dismissed for cause" are different answers to the same auditor question. It must also decide what happens to the linked login — almost certainly *offer* `revoke_mobile_user` rather than fire it, since ending a job and killing a credential are two decisions. |
| **`create_user(email, roles, …)`** | Supervisors and office staff, who need a Desk login and not a phone. | **Deliberately separate from `create_mobile_user`.** A Mobile Access Grant is an enrolment for the field API; a bookkeeper needs neither. Conflating them is how an office account ends up on a dispatch board. |
| **`assign_role` / `revoke_role`** | Role changes without rebuilding an account. | `create_mobile_user(update_existing=true)` currently rewrites roles AND scoping together, which is a blunt instrument for "promote a picker to foreman". These are the scalpel. Revoking must not silently strip what `revoke_mobile_user` deliberately leaves behind as evidence. |
| **`set_role_company_scope(user, companies)`** | The Company User Permissions that decide what an account can see. | The one refusal that cannot be softened: **an empty list means UNRESTRICTED in Frappe**, so this must refuse an empty scope for the same reason `create_mobile_user` does. Additive-and-subtractive like `_sync_user_permissions`, and it must keep touching only `allow=Company` rows. |
| **`list_employee_documents(employee)`** | An audit-ready view of what is on somebody's file — I-9, W-4, photo ID, training certificates. | READ, and the first read tool in this group. It has to report what is MISSING as loudly as what is present: an I-9 that was never filed is the finding, and a list of three attachments does not say which three were expected. |
| **`record_disciplinary_action(…)`** | The HR file writer. | Private on the Employee, never the governance archive — the v0.17.1 rule, and this is the record where getting it wrong is worst. Probably wants its own doctype in `farm_hr` rather than a free-text note, so that "what was said, when, by whom, and did they sign" survives as fields. |
| **`record_training(employee, training_type, completed_date, expires_date)`** | Certifications that expire — forklift, pesticide handler, first aid, WPS. | **This is the one that feeds the compliance calendar**, and it is the highest-value item on the list for that reason: an expiring certificate is exactly the thing nobody notices until an inspection. It should raise the same shape of alert the housing and water registers already do, so an expiry lands on the same board as an overdue inspection. |
| **`bulk_import_employees(csv_url)`** | Pilot-season mass hire — forty people in a morning. | Must be a DRY RUN by default, reporting every row it would create and every row it would refuse, before writing anything. A bulk writer that half-completes across forty people is the failure mode `onboard_employee` was designed to avoid at a scale where nobody can check by hand. Per-row refusals must not abort the batch. |
| **`reactivate_employee(name)`** | The returning worker, which on a tree-fruit farm is most of them. | REUSES the existing record rather than making a second — the same argument as everywhere else in this file, and here it is the common case rather than the edge case. Their history, training records and expired certificates all have to come back with them, and the expired ones have to come back *flagged*. |
| **`transfer_employee(name, from_company, to_company)`** | Inter-entity moves. | Both entities have to be in the caller's scope — this is the one tool that can move a person OUT of what the caller can see, and it must not be a way to make somebody invisible. It also has to decide whether the mobile account's entity access follows, and say which it did. |

### What this implies for `farm_hr`

Three of the ten above (`record_disciplinary_action`, `record_training`, and the
retention half of `list_employee_documents`) want doctypes that do not exist yet.
When `farm_hr` adds them, the MCP tool ships in the **same** release — not the
next one — and `create_employee` is the single place any HR-module creation flow
gets routed through, so the compliance overlays live in one call site rather than
in every caller.
