# v0.18.2 — iOS workflow hotfix

**Two blockers Tim's iPhone testing surfaced tonight (2026-08-02).** Both root-caused
against the live umbrel and patched at the layer where the drift originated.

---

## Bug 1 — `claim_task` returned `{"name": null, ...}`

**Symptom.** iOS showed a red banner: "The farm server sent something Farm Ops
didn't understand. Bad value at 'name'." The task detail rendered, but a
strict-`String` field on `FarmTask` refused a null and the whole response
decoded as garbage. Tap Claim → banner → the app is confused about which task
it just claimed.

**Root cause.** `dispatch.claim_farm_task` in `tools/dispatch.py` returns task
fields at the TOP LEVEL of its `data`, not nested under a `"task"` key:

```python
data = {
	**_describe_task(dict(task_doc.as_dict())),
	"assignment": assignment,
	"concurrent_claims": ...,
	"claims_remaining": ...,
	"evidence_you_will_need": ...,
}
```

But `api/mobile.py:claim_task` was asking for the wrapped shape:

```python
return shape.task(result.data.get("task") or {}, result.data.get("assignment") or {})
```

`.get("task")` returned `None` → `{}` → `shape.task({})` emitted `{"name": null, ...}`.
`start_task` and `get_task` don't have this bug because their inner tools DO wrap
`data["task"] = task` explicitly (see dispatch.start_farm_task line 636+ and
fieldwork.get_task_with_evidence_contract).

**Fix.** `api/mobile.py:claim_task` — extract the task fields from the flat
response body instead of asking for a wrapper that isn't there. Preserves the
top-level shape `dispatch.claim_farm_task` deliberately produces for MCP
operators; the mobile wrapper does the shape correction on the way out.

Same class of test added: contract check that decodes every mobile method's
response against Python models mirroring iOS's Codable expectations, so a strict
field landing as None fails CI instead of Tim's iPhone.

## Bug 2 — Photos and signatures never landed on the server as attachments

**Symptom.** Tim claimed two housing-inspection tasks (MC-Cabin-01,
MC-Cabin-02), started one, captured a photo + signature, tapped Complete.
Zero Housing Inspection records exist. Zero staged upload sessions left over.
Tasks stayed in Claimed / In-Progress. Evidence never reached the server.

**Root cause.** `inspections.normalise_evidence` reads `entry.get("file")` for
the File docname (line 269), but iOS's `CompletionSubmission.StagedFileRef`
serializes to `{"file_token": ..., "file_name": ..., "sha256": ..., "kind": ...}`.
`file` is empty → normalise_evidence raises
`ToolError("names neither a file nor a file_url")` → the whole completion is
rejected → nothing is saved. The rejection JSON is what iOS then tried to
decode into a completion-success response, which is where the shape mismatch
became visible.

The iOS side is right (finalize_staged_file returns the File docname as
`file_token` — that IS the name the phone knows). Rather than rename the iOS
serializer on a shipped TestFlight build, the shim lives on the server:
`normalise_evidence` now accepts both spellings.

**Fix.** `tools/inspections.py:normalise_evidence` — read
`entry.get("file") or entry.get("file_token")`. Same treatment for
`evidence_type` / `kind` (iOS sends lowercase `"photo"` / `"signature"`; we
title-case it before `as_choice` validates against the Farm Task Evidence
doctype's Select field).

## What iOS sends → what the child row gets, after v0.18.2

| iOS field       | Backend child row field | Notes                                |
|-----------------|-------------------------|--------------------------------------|
| `file_token`    | `file`                  | Link to the File docname             |
| `file_name`     | (not stored)            | The File record already has the name |
| `sha256`        | (not stored)            | The File record's own hash matches   |
| `kind`          | `evidence_type`         | "photo" → "Photo", "signature" → "Signature" |
| (not sent)      | `file_url`              | Filled from the File record if `file` known |
| (not sent)      | `caption`               | Left empty; the phone doesn't collect one yet |
| (not sent)      | `captured_on`           | Left empty; TODO iOS to send capture timestamp |

Result: `_produce_record` calls `build_housing_inspection(payload, evidence)`,
which calls `_attach_evidence(doc, "photos", evidence)`, which appends
child rows with proper File links. The Housing Inspection appears in
`/app/housing-inspection` with attachments visible in the Desk's evidence panel
and the compliance alert auto-dismisses on the next sweep.

## Bug 3 — Three dashboard charts failed to build every migrate

**Symptom.** Every `bench --site frontend migrate` printed three warnings, and the
Command Center dashboard was missing the three charts:

```
erpnext_mcp: could not build Compliance Alerts Raised Over Time — MandatoryError: [Dashboard Chart, Compliance Alerts Raised Over Time]: filters_json
erpnext_mcp: could not build Certificate Expirations Ahead — MandatoryError: [Dashboard Chart, Certificate Expirations Ahead]: filters_json
erpnext_mcp: could not build Regulatory Filings by Agency — MandatoryError: [Dashboard Chart, Regulatory Filings by Agency]: filters_json
```

**Root cause.** Frappe's `Dashboard Chart` doctype has `filters_json` as a
mandatory field, and refuses insertion where it is None. The three chart
specs in `dashboard.py`'s `CHARTS` tuple didn't set it — they don't need
filters, so leaving it off felt harmless. Frappe disagreed every deploy.

**Fix.** `dashboard.py` — each of the three chart specs now carries
`"filters_json": "{}"` (JSON-encoded empty dict is what Frappe accepts as
"no filters"). Migrate now installs all four charts cleanly and the Command
Center renders complete.
