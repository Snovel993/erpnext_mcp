# v0.22.0 — the rules themselves are data

**Released 2026-08-04. A compliance rule used to be a Python function, so moving
a threshold, correcting a citation or switching a rule off for a season was a
code change, a release and a deploy. Regulations do not move on a release
cadence. Now neither does this.**

Tool surface **249 → 256** (113 read, 143 mutating). Suite **4,121 → 4,187
passing**. One new doctype, a declarative rule engine, a restricted-Python
sandbox, and the thirteen shipped rules migrated into records that produce
**byte-identical alerts**.

---

## 1. The problem, in one paragraph

Oregon OSHA renumbered heat illness from OAR 437-004-1130 to -1131. Oregon Tilth
added a Fraud Prevention Plan requirement. The FDA re-phased FSMA Produce Safety.
Each of those is a **data** change — a citation string, a threshold, a new
condition to watch for — and until this release each one needed a developer, a
release and a deploy before the operation was watching for it.

Tim's framing, 2026-08-03:

> "Rules change so we need to be able to make this a pipeline we can update
> without updating code per say… That way we can leverage the power of AI going
> forward to focus on conforming to a dynamic regulatory, political, and market
> environment."

---

## 2. What changed, and what deliberately did not

**Changed.** A rule is now a `Compliance Rule` record (`CRULE-2026-0001`). Its
thresholds, scope, citations, regimes, message, producer task and switch are
fields somebody edits. `create_compliance_rule` writes one; it is live on the
next sweep after a human approves it.

**Did not change.** `alerts/base.py` — the sweep, the reconciliation, the
idempotent docnames, the auto-dismissal, the regime filter's refusal to dismiss
rules it did not run. Only *where the rule set comes from* moved. Every currently
firing rule fires identically, with the same docname, severity, due date and
words.

---

## 3. The non-negotiable: no model runs at sweep time

There is no classifier, no embedding, no natural-language interpretation of
anything in the trigger path. A rule fires because a date crossed a threshold or
a column matched a filter, and the report can name which.

That is not squeamishness about AI. It is what makes an alert defensible: for
every alert an auditor questions, the answer traces to a **row**, its
`regulation_citations`, its `human_approved_by` / `human_approved_on`, and the
specific field on the specific record that crossed a threshold — not to a model
output nobody can explain.

**AI's role is confined to authoring**, behind a human approval.
`propose_compliance_rule` ships **declared and refusing**, exactly as
`propose_inspection_template_from_regulation` did in v0.21.0 and for the same
reasons.

---

## 4. The split: how the thirteen migrated

| Shape | Count | What is on the record | What stays code |
| --- | --- | --- | --- |
| **declarative** | **6** | everything | nothing rule-specific |
| **builtin_scanner** | **7** | every tunable | the shape of the join |
| **custom_python** | **0** | — | — |

### The six that are now pure data

`policy_review_overdue`, `housing_inspection_overdue`, `i9_expired`,
`flc_license_expiring`, `filing_response_due`, `training_expiring`.

Each of these paid for a primitive:

- **`missing_date_behaviour`** exists because of `housing_inspection_overdue`. A
  cabin nobody has ever inspected is the most overdue cabin in the camp, and
  every naive date-driven engine answers "no date, no alert". The opposite
  reading is right for an expiry — a training with no expiry does not lapse — so
  it had to be a choice on the record rather than a convention in the engine.
- **Scope-filter `default`** exists because in SQL `status != 'Active'` excludes
  every row whose status was never set. A Compliance Policy with no status **is
  in force**; a Regulatory Filing with no status is **neither Draft nor
  Withdrawn**; a Housing Unit with no condition is **not Uninhabitable**. Filters
  are therefore evaluated in Python against a documented default, which is what
  the legacy `str(row.get("status") or "Active")` said in an idiom.
- **Per-band severities** exist because `filing_response_due` escalates Info →
  Warning as the deadline passes — the only one of the thirteen that does. A
  fixed Critical/Warning ladder could not express it.
- **`requires_fields`** exists because of `i9_expired`. `i9_status` is installed
  on demand, and a rule that scanned a site without it would report every
  employee as clean — the single most dangerous wrong answer in the file. It
  returns an *empty scan* instead, which still auto-dismisses stale alerts,
  rather than a failure, which would not.
- **`regimes_from_field`** exists because of `training_expiring`. The tags are
  copied off the training record, because the record says what that afternoon
  actually covered — a heat session that ran out of time before the
  emergency-response topic did not satisfy OAR 437-004-1131 that day.
- **`window_field`** carries a per-row lead time (`renewal_window_days`), because
  the turnaround an issuing body takes is a property of the certificate.
- **`message_template`** is the primitive `training_expiring` proves the value
  of. Its text is three branches, a per-regime consequence clause and a coverage
  clause, and it is the alert somebody reads on a phone at seven in the morning.
  All of it is now editable in the operation's own words, in their crew's
  language, without a release.

### The seven that keep a shipped scanner

`certification_expiring`, `water_test_stale`, `housing_detector_test_stale`,
`audit_action_overdue`, `housing_corrective_action_open`,
`water_test_contamination`, `supervisor_review_lapsed`.

**"Built-in" does not mean "not configurable."** Every one of these still carries
its thresholds, scope filters, citations, regimes and switch on the record —
`certification_expiring`'s 30/90 day windows, `water_test_stale`'s 90-day cadence
and 120-day spray season, `housing_detector_test_stale`'s annual cycle,
`audit_action_overdue`'s grace period, `supervisor_review_lapsed`'s 14/30 day
thresholds. Only the *shape of the join* is code, and it is code that was
reviewed, tested and shipped rather than typed into a text field.

`docs/configurable_compliance_framework.md` §5 argues each of the seven and names
the primitive that would shrink the list. The ranked backlog:

1. **`superseded_by_later_clean`** — takes *two* rules declarative at once
   (`housing_corrective_action_open` and `water_test_contamination`). Their gate
   is "is this finding still true", and it stops being true when a later clean
   record for the same subject supersedes it. Four values:
   `(doctype, subject_field, date_field, clean_state)`.
2. **`regime_heuristics_json`** — takes `certification_expiring` declarative. Its
   regimes come from an ordered eleven-row needle table on the certificate's
   TYPE; `regimes_from_field` copies tags off a column, and here there is no
   column, only a name to read.
3. **`gate_date_field` + `gate_within_days`** — takes `water_test_stale`
   declarative. Its gate is a conjunction over two independent dates: sprayed
   inside the season **and** tested outside the cadence, and neither half fires
   alone.
4. Plural **`date_fields`** — takes `housing_detector_test_stale` declarative.
   More machinery, one rule.

Two are probably never worth it, and saying so is part of the design:
`audit_action_overdue` walks a child table and folds it to its worst row, which
is an aggregation rather than a filter; `supervisor_review_lapsed` walks a
*table of doctypes*, needs an OR of two nulls, and runs its clock on `creation`
rather than on any field — and its thresholds mean days *elapsed* rather than
days *remaining*, which on a record beside twelve others is a number somebody
would eventually misread.

### `custom_python` ships used by nothing, and that is the point

It exists for rules an operator or a proposer writes that the primitives do not
reach. A framework that needed it for its own thirteen rules would be a framework
whose vocabulary does not reach its own problem domain.

## 5. The sandbox

`alerts/sandbox.py` is an **AST interpreter** — never `exec`, never `eval`.

Refused by name, each with a sentence saying why: `import`, `exec`, `eval`,
`compile`, `open`, `globals`, `getattr`, `type`, `object`, `super`; **every
underscore-prefixed attribute** (`x.__class__.__bases__[0].__subclasses__()` is
the standard escape and needs no imports at all); `while` (unbounded by
construction); `def`, `class`, `lambda`, `yield`; `try`/`except` (a rule that
swallows its own errors is a rule that goes quiet, which is the failure this app
is written against); `with`, `del`, `global`, `nonlocal`, `assert`, `raise`,
`await`, `:=`.

Bounded at 200,000 node visits and 5 seconds. `frappe` is a facade with five
readers and a `utils` namespace, and **`get_doc` hands back a plain dict** — a
Document has `.save()` on it, and a read-only sandbox that returns a live
document is read-only in the same sense a locked door with the key in it is
locked.

A refused or failed program does not silently observe nothing: it raises a
Warning against the rule saying the condition is now **UNWATCHED**.

**Why not RestrictedPython or asteval.** Both are good and neither is on this
bench. `pyproject.toml` has three runtime dependencies, each argued for and each
imported defensively. Adding a fourth for a field that ships used by zero rules
would be the tail wagging the dog; the subset needed is small and closed, and an
interpreter for it has no supply chain.

## 6. Provenance, approval and versioning

- **The gate.** `enabled` cannot be set without `human_approved_by` *and*
  `human_approved_on` — the DocType refuses it. `create_compliance_rule` always
  writes a Draft whatever the caller asked for. There is no path by which a rule
  starts firing without a person having put their name to it, which is the
  property that has to exist *before* a model can propose rules.
- **Versioned by copy**, exactly as Inspection Templates are.
  `update_compliance_rule` writes v+1 and points the old row's `superseded_by` at
  it; the old row is disabled, never edited, never deleted. A sweep that started
  against v1 finishes against v1, and an alert from April is still readable
  against the definition that raised it. The new version inherits the old one's
  approval — a threshold moved is not a new rule, and forcing re-approval on
  every tuning edit trains people to click through approvals.
- **One live row per `rule_id`**, enforced in the controller and materialised as
  the indexed `active_row_flag`. Two enabled unsuperseded rows are two
  definitions of one rule, and the one tonight's sweep ran would be whichever
  sorted first.
- **Off is not deleted.** `deactivate_compliance_rule` requires a reason and
  dismisses **nothing** — the alerts the rule raised stay exactly as they were,
  the same reading a rule skipped for a missing DocType gets. Switching a rule
  off is not evidence that anybody did the work.
- **Audit.** Every call writes an MCP Action Log row; `update_compliance_rule`
  additionally returns a field-by-field before → after, so the log records what
  the rule said *before* rather than only what was asked for.

## 7. Backward compatibility, proven rather than promised

`TheMigrationChangesNothing` builds one fixed database, runs the sweep with the
shipped Python rules, snapshots every alert row, deletes the alerts, seeds the
thirteen records, runs the sweep again through the record-driven engine, and
compares the two snapshots **field by field** — docname, severity, category,
company, source, message, due date, first seen.

Not counts. Not "an alert of this type exists". The rows.

**Behaviour drift: zero.** No migrated rule fires differently from the Python it
replaced.

Also unchanged: alert docname format (`<rule_id>:<source_doctype>:<source_name>`),
the `list_compliance_rules` return shape (retrofitted with filters and
provenance, every prior key meaning what it always meant), and every existing
test in `test_alerts.py`, `test_regimes.py`, `test_inspections.py`,
`test_dispatch.py`, `test_training.py` and `test_shifts.py` — none was modified.

**Upgrade window.** Until the migrate runs, the sweep falls back to the shipped
definitions **and says so** in `engine_notes` on its report. A compliance calendar
that quietly emptied itself for the length of an upgrade would be the single
worst failure this app could have.

**Migrated rules arrive enabled**, against this app's usual instinct that
everything mutating ships off. They were already running — as Python — the night
before, and seeding them disabled would silently switch the whole calendar off
during an upgrade.

## 8. Seven new tools

**Read:** `get_compliance_rule`, `test_compliance_rule`.
**Mutating (all shipping OFF):** `create_compliance_rule`,
`approve_compliance_rule`, `update_compliance_rule`,
`deactivate_compliance_rule`, `propose_compliance_rule` (declared and refusing).

`list_compliance_rules` was **retrofitted, not replaced**: it reads the records,
takes `regime` / `category` / `target_doctype` / `shape` / `active` / `limit`,
and every key it returned before means what it always meant.

`test_compliance_rule` is the read between authoring and approving. It runs the
rule down **the same code path the sweep takes** — a dry run with its own second
implementation is a dry run that can disagree with the real one — and reports
what it *would* raise, with the docname each alert would take, writing nothing.
A rule that observes four hundred rows is a rule whose condition is wrong,
usually a field that is empty everywhere rather than stale on a few, and finding
that out here costs nothing.

**Who may call them.** The Compliance Rule DocType is granted to System Manager,
Compliance Officer and Farm Manager, and to nobody else. A Foreman reads the
calendar and cannot rewrite what fills it; a Field Worker cannot see it at all.
That is the dispatch separation this app already keeps, moved one layer up: the
person who can silently redefine what "required" means must be fewer people than
the people who answer to it.

## 9. Judgment calls

- **A third shape.** The plan asked for declarative-or-`custom_python`. Forcing
  the seven cross-doctype rules into sandboxed strings would have made the system
  *worse*: the supersession logic in `housing_corrective_action_open` is exactly
  the kind of thing the framework's own notes say must stay code, and nobody
  would safely edit it in a text field. `builtin_scanner` keeps every tunable on
  the record and only the join in reviewed code. `custom_python` is fully built,
  sandboxed and tested — and used by none of the thirteen, which is the honest
  measure of an escape hatch.
- **Approver is a `User`, not an `Employee`.** The migration needs Administrator,
  who is not on any payroll. `approver_employee` is a second, optional field for
  sites that keep one, and `approver_signature` is a File attach using this app's
  existing evidence idiom rather than a Data field — the difference between a
  record of an approval and evidence of one.
- **`audit_packet_types` is a validated JSON list**, not a new child doctype. The
  packet vocabulary already exists as a Python registry; validating against
  `audit_packets.names()` gives the same refusal without a table whose only job
  is to hold eight strings. Same reasoning for `scope_filters_json`.
- **No new child tables at all.** `Compliance Regime Link` already exists and is
  reused; scope filters and the evidence contract are JSON blobs validated at
  authoring time, which is where a malformed one is cheap to fix.
- **`extra_parameters_json`** was added for the two rules carrying a second
  interval `cadence_days` cannot hold — `water_test_stale`'s spray season and
  `audit_action_overdue`'s grace period. Deliberately not a general-purpose
  configuration bag: every key in it is documented on the rule that reads it.
- **Compliance Rule carries no Company link**, and `test_permissions.py` records
  why: one rule raises alerts across every entity on the site. Per-company rows
  would mean either thirteen copies per entity — thirteen places to update when a
  citation is renumbered — or one entity's rule silently governing another's
  records. Narrowing is a `scope_filters` entry, on the record an auditor is
  looking at.
- **The AI stub is scoped so it cannot be called accidentally.** It has a switch
  that ships off, a schema, a catalogue entry and an implementation that raises —
  the same treatment `propose_inspection_template_from_regulation` got. A surface
  an operator cannot see in the settings form is a surface nobody can refuse.

## 10. Verification

```
git log --oneline -2        v0.22.0 on top of v0.21.0
git status                  clean
python3 -m unittest discover -s tests_standalone -t . -q
                            4,187 passing (was 4,121), 75 skipped
```

- Tool count assertion: 256 / 113 / 143, and `docs/tool-catalog.md` agrees.
- Backward compat: `refresh_compliance_alerts` output identical before and after,
  row by row, on a fixed snapshot.
- Fixture migration idempotent: seed twice → 13 created, 0 duplicated; an
  operator-edited rule keeps its edit; a disabled rule is not seeded back on.
- Sandbox refuses `import`, `exec`, `eval`, `open`, dunder attributes, `while`,
  `def`/`class`/`lambda` and `try`, each with its own test.

**Docker is not built here.** That is Tim's step after committing.
